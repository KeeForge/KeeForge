# Models Folder

This folder holds the data and logic that the rest of the app depends on. It is the most security-sensitive part of the repo.

## High-Risk Core

The canonical high-risk file list (kept in sync with `AGENTS.md`): `KDBXParser.swift`, `KDBX3Parser.swift`, `KDBXWriter.swift`, `KDBXXMLSerializer.swift`, `KDBXCrypto.swift`, `KDBXOuterCipher.swift`, `OpaqueXMLNodes.swift`, `DatabaseDraft.swift`, `EntryEdit.swift`, `Entry.swift`, `Group.swift`, `EncryptedValue.swift`, `TOTPGenerator.swift`.

- `KDBXParser.swift`, `KDBXWriter.swift`, and `KDBXCrypto.swift` implement KDBX read/write, KDF handling, XML extraction (parser side), HMAC checks, payload framing, and decompression guards. Read supports KDBX 3.1 and 4.x; write is KDBX 4 only — the writer throws `unsupportedSourceFormat` for 3.1 sources and emits only the ChaCha20 inner random stream.
- Header fields whose type IDs KeeForge does not model are preserved, not dropped: the outer header's land in `Header.unknownOuterHeaderFields` and are re-emitted after the modelled fields, and the KDBX4 inner header's (any ID other than 0x00–0x03) land in `Header.unknownInnerHeaderFields` and are re-emitted after the inner random stream ID/key and before the binary pool, byte-exact and in their original relative order. That normalizes a field the source spliced between pool entries, which is deliberate: KDBX4 defines no ordering semantics for inner-header items and KeePassXC skips IDs it does not recognize, while pool entries move as attachments change. `TestFixtures/compatibility/unknown-inner-header.kdbx` pins the behavior end to end.
- `KDBX3Parser.swift` is the legacy KDBX 3.1 read path (TLV header, AES-KDF master key derivation, stream-start-bytes authentication, hashed block stream, Salsa20/ChaCha20 inner streams), dispatched from `KDBXParser.parseWithMetaAndHeader`.
- `KDBXXMLSerializer.swift` owns all XML emission (invoked by `KDBXWriter`): protected-field re-encryption under the inner ChaCha20 stream, unknown-XML insertion-index replay, and re-emission of the diverted passkey private-key PEM at its original sorted custom-field position.
- `OpaqueXMLNodes.swift` holds the unknown-XML preservation type plus `KPMeta` (custom icons, recycle-bin element tracking) and `KPDeletedObject` tombstones.
- `CustomIconXML.swift` adds an image to `Meta/CustomIcons` without rewriting the icons already there. That element is preserved as one opaque fragment and replayed verbatim, which is why a foreign database's icons survive a save untouched; rebuilding it from `KPMeta.customIcons` would normalize `<Icon>` child order, KDBX 4.1's optional `<Name>`/`<LastModificationTime>`, and each writer's own base64 wrapping — none of which this app models. So the new icon is spliced in before the closing tag instead, and only the appended element is ours. Base64 cannot contain `<` or `>`, which is what makes searching the fragment's own text for its closing tag unambiguous. The written `<Icon>` deliberately carries only `<UUID>` and `<Data>`: `<Name>` and `<LastModificationTime>` are 4.1 additions that would oblige `KDBXWriter.requiredMinorVersion(for:)` to raise the file's minor version, turning an icon download into a format upgrade the user never asked for. The parser renders every preserved fragment through a start/end tag pair, so a captured `<CustomIcons>` always closes explicitly even when the source file wrote `<CustomIcons/>` — that is the one shape the splice handles. Anything else returns `nil` and the edit fails: a fragment this cannot splice is one it does not understand, and rebuilding the element from `KPMeta.customIcons` would drop every icon whose bytes this app does not model, which is the silent data loss the type exists to prevent.
- `KDBXUUIDEncoding.swift` is the one place a UUID becomes the base64 of its 16 raw bytes, which is how KDBX stores every UUID. Single-sourced on purpose: `KDBXXMLSerializer` writes structured elements from it and `DatabaseDraft` builds the preserved `<CustomIconUUID>` fragment from it, and two encoders would be free to drift on a detail the format does not forgive.
- `KDBXOuterCipher.swift` centralizes outer-cipher UUID recognition, IV sizing, diagnostics, and AES-256-CBC, ChaCha20, and Twofish-256-CBC dispatch. The Twofish primitive lives in the locally vendored `Vendor/KeeForgeTwofish` package and is shared with AutoFill.
- `Entry.swift`, `Group.swift`, `EncryptedValue.swift`, and `TOTPGenerator.swift` define the in-memory representation of secrets and time-based codes. `Group.swift` also carries the tri-state `<EnableSearching>` flag (`KPInheritableBool`): `nil` means the source group had no such element and the writer must not invent one, while `.inherit` is an element that is present and explicitly defers to the parent. Making it structured shifts the opaque-XML insertion indices of the unmodelled group siblings around it, so the parser only counts it as known when its value parsed, and the writer emits it in the same position KeePass does — after `<Times>`/`<IsExpanded>`, before the children. Deliberate scope decision: the flag gates AutoFill (`KPGroup.autoFillEntries`) and the in-app search corpus (`DatabaseViewModel.rebuildDerivedState`, which resolves the same inheritance in the same order), matching KeePass's reading of the field as "exclude from search". In-app browsing and the tag browser keep using `allEntries` — hiding a group from search is not the same wish as hiding it from the person who owns the database. When a user edit makes the element structured for a group that previously held an unparsable value, `DatabaseDraft` drops the preserved copy from `unknownXML` (`OpaqueXMLNodes.removeDirectChildren(named:)`) so the writer cannot emit two `<EnableSearching>` children. `KPGroup` additionally carries KDBX 4.1 group `<Tags>` (`tags` + `hasTagsElement`, the same three-state empty-element semantics `KPEntry` has) and group `<Notes>` (`notes` + `hasNotesElement`, same three-state rule). Both are readable and writable: `DatabaseViewModel` folds group tags into effective tags (own plus every ancestor group's), and the group editor authors both through `EntryEdit.updateGroup`. The serializer emits `<Notes>` immediately after `<Name>` and `<Tags>` right after the `<EnableSearching>` block, before the child entries — the KeePass positions the parser's opaque-XML insertion indices are recorded against, so the read handler's guards and the `case "Group":` counter arm in `recordOpaqueXML` must stay byte-identical in their conditions or every opaque fragment after the element shifts. A group whose source had neither element never gains one, because the flag is only raised when content exists. Authoring a group tag *does* force the written header up to KDBX 4.1: `KDBXWriter.requiredMinorVersion(for:)` scans the tree and `resolveHeader` writes `max(required, existing)`, never a downgrade (`<Notes>` predates 4.1 and does not count). The parser splits stored tag text with the entry rules (`,`/`;`, trim, drop empties) and deliberately does NOT dedupe or reorder — read-time rewriting is forbidden; `TagNormalizer`'s dedupe is edit-side policy, applied to `updateGroup`'s payload. Group notes parse untrimmed: leading and trailing whitespace is the author's. Every `KPGroup` construction site must forward `tags`/`hasTagsElement`/`notes`/`hasNotesElement` (`copyGroup`, `deepCopy`, `replacingChildGroup`, `applySetGroupSearchingEnabled`, `applySetGroupIcon`, `applyUpdateGroup`, the parser's `GroupBuilder`) or the fields silently vanish on the first unrelated edit; `KDBXCompatibilitySupport.GroupScalars` pins this.
- `DatabaseDraft.swift` and `EntryEdit.swift` stage in-memory entry/group creates, updates, and deletes while preserving recycle-bin behavior, protected fields, and unknown XML for later save. `restoreEntryVersion` makes a stored `<History>` version current again: user-visible fields come from the snapshot while `id`, `creationTime`, `unknownXML` and `customIconUUID` stay with the live entry (the serializer writes an entry's `<CustomIconUUID>` only from the preserved XML, so the display copy must match those bytes), and the replaced state is pushed onto the history unless `HistoryMaxItems`/`HistoryMaxSize` discard it — `restoreKeepsReplacedState` reports whether the snapshot itself survives the trim, so the confirmation does not promise an undo it cannot deliver. History trimming decides *which* versions survive by recency, then re-emits the survivors in storage order: KDBX fixes no `<History>` order — KeePass appends oldest-first where this app prepends — so choosing by position discarded the newest versions of a KeePass-authored file, while sorting the array would rewrite that file's bytes on every save. Both caps (`HistoryMaxItems` and `HistoryMaxSize`) use the same order, and it matches `DatabaseViewModel.history(forEntryID:)`'s: undated versions last, ties by storage position. Two group edits deliberately *drop* a preserved element rather than round-tripping it, because the structured field would otherwise be written alongside a duplicate that outranks it: `setGroupSearchingEnabled` removes any preserved `<EnableSearching>`, and `setGroupIcon` removes both `customIconUUID` and any preserved `<CustomIconUUID>` (a custom icon takes precedence over `<IconID>` in KeePass, so leaving it would write the chosen standard icon but never show it). `updateGroup` carries the whole group-editor payload and drops the custom icon only when `iconID` actually changed — renaming a group must not replace the icon it displays. `setEntryIcon` is the entry-side counterpart and is the only edit that *writes* a `<CustomIconUUID>`: because the serializer emits that element solely from the preserved XML, an `EntryIconSelection.custom` has to land there or it is lost on the next save, so the edit removes any existing element and appends a fresh one at the position `serializeEntry` reaches directly after `<IconID>`, which is where KeePass puts it. That position is *not* a constant: a parsable `<Binary>` advances the opaque-XML position space while leaving the anchor `KPAttachment.insertionIndex` is expressed against alone, so an entry whose source interleaved attachments before `<IconID>` shifts everything after them — `customIconUUIDInsertionIndex(for:)` counts those slots, and a fixed 2 writes the element ahead of `<IconID>` on exactly those entries. `.standard` clears both the display copy and the element, exactly as `setGroupIcon` does. `addEntryCustomIcon` is the one edit that puts a *new* image into `Meta/CustomIcons` (via `CustomIconXML.swift`) and points the entry at it in the same edit — the halves are not independently useful, since an unreferenced icon is dead weight in the file and a reference to an icon that was never stored renders as each client's own fallback. It updates the decoded dictionary and the preserved XML together: the dictionary is what the UI reads before the next save, the XML is what the writer emits. An identical image already in the database is reused rather than stored twice, so the same favicon downloaded onto three entries leaves one icon in the file; when a foreign file already holds the same bytes under two UUIDs the lowest one wins, because `Dictionary` iteration order varies per launch and `EntryEdit` documents itself as a pure function of its input. The `add-entry-custom-icon` compatibility scenario pins the whole cycle through a real write and re-parse. Like every other entry edit it pushes a `<History>` version, which is what makes an icon change undoable from the history viewer. `EntryDraftPayload.protectedCustomFieldKeys` marks which custom-field keys must serialize with `Protected=True` on the create path (AutoFill passkey registration relies on it for the `KPEX_PASSKEY_*` secrets); `DatabaseDraft` intersects it with the keys that actually serialize — including the diverted passkey PEM key — before handing it to the serializer as `protectedStringKeys`.
- Changes here should be small, test-backed, and motivated by a real bug, format update, or security requirement.

## Other Models Here

- `DatabaseReference.swift` is the persisted identifier for a known database, including bookmarks, nicknames, quick-launch state, read-only and edit-acknowledgment flags, the per-database `autoFillEnabled` AutoFill publication gate (shipped v1.10.4), and cloud metadata.
- `CloudSyncModels.swift` describes cloud provider files and sync metadata used by the database list and sync coordinator. Optimistic concurrency uses a single opaque `rev` field; the provider-specific mapping (Dropbox rev, OneDrive cTag/eTag, WebDAV ETag → `rev`) happens in the `Services/Cloud` providers.
- `PasskeyCredential.swift` parses KeePassXC-style custom fields into passkey data used by the app and AutoFill extension, with ordered fallback to legacy Strongbox/older-KeePassXC field names (`KPEX_PASSKEY_GENERATED_USER_ID`, `KPXC_PASSKEY_USERNAME`) when the current KPEX keys are absent. The private key PEM (`KPEX_PASSKEY_PRIVATE_KEY_PEM`) is diverted out of `customFields` at parse time into the session-key-sealed `KPEntry.passkeyPrivateKey` and only decrypted just-in-time for signing; the serializer re-emits it at its original sorted custom-field position.
- `KDBXFileSummary.swift` is a credential-free summary of a KDBX file's plaintext outer header (format version, cipher, compression, KDF settings) for display in Database Details; it reuses the parser's header routines read-only and accepts a bounded file prefix.
- `KDFExecutionPolicy.swift` is the resource budget for running an attacker-controlled Argon2 configuration (peak memory, memory × iterations total work, parallelism). Every parse/write entry point takes an explicit `kdfPolicy` — `.mainApp` in the app targets, `.autoFillExtension` in the AutoFill coordinators. The two policies differ only in peak memory (the extension's ceiling backstops `AutoFillMemoryLimit`'s runtime check and covers macOS); work and parallelism bounds are deliberately identical so the static policy never refuses a vault in one context that the other opens. Format validity (RFC 9106 minimums, Argon2 version byte) is checked separately and throws `kdfParameterOutOfRange`; a config over budget throws the localized `kdfResourceLimitExceeded` instead. Never clamp — run the exact stored values or reject.
- `TagNormalizer.swift` is the single implementation of the tag identity policy shared by the editor and `DatabaseViewModel`'s tag index: split free-form text on `,`, `;`, and newlines, trim, drop empties, and dedupe exact-string (so `Work` and `work` stay separate) keeping first occurrence. Normalization applies to edit-side input and derived lists only — parsed `KPEntry.tags` and `KPGroup.tags` are never rewritten on read (the parser has its own dedupe-free split for exactly that reason).
- `Attachment.swift` defines `KPAttachment` (name + pool ref, structurally parsed from `<Entry>/<Binary>`) and `BinaryPool`, which lazily decodes `Header.innerHeaderBinaryFields` (stripping the leading protection-flag byte) on subscript access by ref. Read-only in Phase 1: the writer only ever re-emits the inner-header binary pool verbatim: no ref renumbering, no new pool entries. Dangling refs (no pool entry at that index) are tolerated and resolve to `nil` rather than failing the parse.

## Notes For Agents

- The entire folder compiles into all four app/extension targets via folder globs in `project.yml`, so any new file here is automatically extension- and macOS-resident. Keep it Foundation/CryptoKit-only: no UIKit/AppKit imports, no `@MainActor`.
- Secrets should stay encrypted in memory until the exact point of use; keep parsing and crypto work off the main actor.
- If a format or compatibility change is unclear, check `../../docs/README.md` and the related spec before changing code.
- Twofish uses strict PKCS#7 validation. Do not add permissive padding recovery without a sanitized interoperability fixture that proves it is required.
- Relevant unit tests usually live in `../../KeeForgeTests/KDBXParserTests.swift`, `../../KeeForgeTests/KDBXWriterTests.swift`, `../../KeeForgeTests/KDBXRoundTripTests.swift`, `../../KeeForgeTests/DatabaseDraftTests.swift`, `../../KeeForgeTests/EncryptedValueTests.swift`, `../../KeeForgeTests/TOTPGeneratorTests.swift`, `../../KeeForgeTests/KeyFileProcessorTests.swift`, `../../KeeForgeTests/PasskeyTests.swift`, `../../KeeForgeTests/AttachmentTests.swift`, `../../KeeForgeTests/TwofishTests.swift`, `../../KeeForgeTests/ChaCha20Tests.swift`, and `../../KeeForgeTests/KDBXFileSummaryTests.swift`.
- Per `AGENTS.md`, parser/writer, protected-field, or unknown-XML changes must also update `../../KeeForgeTests/KDBXCompatibilityTests.swift` and `../../KeeForgeTests/KDBXCompatibilitySupport.swift` (the matrix tests also emit the artifacts consumed by the external `keepassxc-cli` gate).
