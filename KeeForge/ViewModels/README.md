# ViewModels Folder

Observable app state lives here. Keep business rules here and keep views thin.

## Main View Models

- `DatabaseListViewModel.swift` owns the database list screen: add/remove/reorder, quick launch, nicknames, read-only toggles, key-file association, cloud database selection, row-status derivation, pending-upload counts/conflicts, and manual "push pending changes". `setAutoFillEnabled` invokes its `autoFillEnabledRefreshHandler` (the refresh bridge `../Views/README.md` references) so an open session republishes its AutoFill identities immediately after a per-database toggle.
- `DatabaseViewModel.swift` owns one database session: unlock state machine, local/cloud file resolution, draft/save state, entry/group deletion state, local-vs-cloud save routing, expected Dropbox rev tracking, save-conflict detection, synced-folder edit acknowledgments, search, sorting, compact + regular-width selection/navigation state, inactivity lock, biometric unlock, shared AutoFill cache refresh after both unlock and save, and the decoded inner-header `BinaryPool` used to resolve read-only entry attachments (`attachmentData(for:)`). The pool and any cached attachment preview temp files are cleared on lock. It also resolves per-group Search & AutoFill exclusion (`<EnableSearching>`): `autoFillExcludedGroupIDs` is recomputed on every tree rebuild alongside `recycleBinGroupIDs`; entries under an excluded group are dropped from the search corpus (KeePass's reading of the flag) but deliberately stay in the tag index and normal browsing and never gain recycle-bin state, and `isGroupExcludedFromAutoFill` / `isGroupExclusionInherited` back the group row's badge and context-menu wording. The same rebuild pass records each entry's folder path below the visible root (`folderPath(forEntryID:)`, `" / "`-joined, `nil` at the top level), which `EntryListView` renders as a subtitle on search and tag-browser rows. Inheritance is resolved there in the same order as `KPGroup.autoFillEntries`; if you change one, change both. `setGroupExcludedFromAutoFill` writes an explicit `True` when re-enabling rather than `inherit`, so a group inside a hidden parent can actually be turned back on. It also derives the tag index (`allTags`, `entryCount(forTag:)`, `entries(withTag:)`) in that same rebuild pass, over live entries only — recycled entries and history snapshots contribute nothing, and tags carried only by the recycle-bin group (or groups inside it) never surface because the accumulator only feeds entries on the `includeInSearch` branch. The index is over **effective tags**: an entry's own tags first (source order), then every ancestor group's KDBX 4.1 tags (root-most first), exact-string deduped keeping first occurrence — group tags are resolved once per group by threading an `inheritedTags` accumulator through the one recursive pass (like `autoFillEnabled`), never per entry. `effectiveTags(for:inheritedGroupTags:)` is the single seam feeding both the index and the entry's searchable text, so search and browsing can never disagree about an entry's tags. The same pass also records what the entry editor's suggestion strip needs: the accumulated tags per group and each entry's owning group, read back through `inheritedTags(forGroupID:)` (the tags an entry stored there inherits — ancestors' plus the group's own) and `inheritedTags(forEntryID:)`; the suggestion pool itself is just `tagsInDisplayOrder`, so recycled-only tags are never offered. `detailTags(forEntryID:)` splits that same effective list in two for the entry detail screen — the entry's own tags, then the ones it carries only because of where it sits — so the chips on screen and a hit in the tag browser cannot disagree; a tag on both the entry and an ancestor group lands in `own` only. `tagsInDisplayOrder` is the browser's presentation sort (Finder-style `localizedStandardCompare` with an exact-string tiebreak, since that comparator can call two distinct tags equal and `sorted(by:)` is not stable). `selectedTag` is the macOS sidebar's tag selection and is mutually exclusive with `selectedGroupID` — setting either clears the other plus `selectedEntryID`; it is cleared by `lock()` and `reloadDiscardingDraft()`, and `synchronizeSelections()` drops it as soon as its last live carrier is gone, then lets the group selection fall back to the visible root (that fallback is deliberately skipped while a tag is selected, or it would clear the tag on every rebuild). A `selectedEntryID` whose entry has vanished is deliberately **not** cleared by `synchronizeSelections()` (nor by `deleteGroup` for permanently deleted entries): the mounted `EntryDetailView` closes itself and clears the selection through `onClose`, because clearing it in the same update that deletes the entry unmounts the regular shells' detail column — and with it the entry editor's presentation host, wedging a pushed editor (see `../Views/README.md`). The file also declares `BiometricAutoUnlockPolicy`, the platform gate folded into `isEligibleForBiometricAutoUnlock` that keeps lifecycle biometric prompts off compatibility platforms (iOS on Mac / Vision Pro), where an `.active` scene does not prove the window is frontmost. It also owns `changeMasterKey(newPassword:newKeyFileData:newKeyFileBookmarkData:newKeyFileFilename:)` — the rekey flow (#59): typed `RekeyError` guards (unlocked, writable non-KDBX-3.1, no in-flight save, no dirty draft, non-empty new credentials, no pending AutoFill upload markers on cloud references), a clean working draft routed through the same local/cloud save seams with the derived new composite key, then on success the session key/hash update, a stored biometric key refresh only if one already existed (deleted on store failure), and the key-file association persisted on the reference (stamping `lastMasterKeyChangeAt`, which `PendingUploadDrainer` uses to refuse markers older than the rekey). A draft that grew behind the in-flight rekey is flushed by a follow-up save, mirroring `save()`'s grown-draft loop. A cloud apply failure after the upload landed surfaces as `SaveError.rekeyAppliedRemotely` — keychain and association still switch to the new key, since the remote already requires it. A save conflict aborts with `RekeyError.conflict` and never enters the conflict-copy machinery. The session also retains `sessionKeyFileData` (a key file supplied manually at password unlock, cleared on lock) so the rekey flow can keep a key file that was never persisted as an association. It also owns `mergeAndSave()` — the "Merge Changes" branch of the save-conflict alert (#58): it parses `SaveConflict.remoteData` with the live `sessionKey` off the main actor, runs `../Models/KDBXMerger.swift` over the draft's tree and the fresh parse (local pool fields come from the session's `binaryPool`, which is the pool the file was opened with), and saves the merged tree through the same local/cloud seams as a pristine draft — but gated on the conflict's `remoteSHA512` rather than the stale `openTimeSHA512`, threaded as `reconciledRemoteSHA512` into `SaveBaseline`. Exactly one attempt per invocation: a save that conflicts again republishes `saveConflict` with the fresher bytes and stops, so the optimistic-concurrency loop only advances when the user asks. A parse failure, a KDBX 3.1 remote, or a declined merge sets `DatabaseMergeFailure` and leaves the draft *and* the conflict standing, so Reload and Save as Conflict Copy are still there; success adopts the merged tree, clears the conflict, replays any edit that landed behind the save onto the merged tree, and reports through `mergeSummaryMessage`. Entry and group moves go through `moveEntry(entryID:toGroupID:)` / `moveGroup(groupID:toGroupID:)` — no-ops for vanished IDs or the current parent, while draft-level refusals (cycles, protected groups, duplicate sibling names) propagate for the UI to present — and `moveDestinationOptions(forEntryID:)` / `moveDestinationOptions(forGroupID:)` supply the picker's flattened tree (recycle bin pruned, a moved group's own subtree pruned, current parent flagged). `sortedGroups(_:)` is the single ordering seam both folder lists use (`../Views/GroupListView.swift` and the Mac/iPad sidebar tree in `../App/RegularDatabaseWorkspaceView.swift`), and it pins the recycle bin to the front of whichever list contains it, ahead of the chosen sort order and direction.
- `DatabaseOpenFailure.swift` owns unlock-failure classification (`DatabaseOpenDiagnostics`, `DatabaseOpenFailure.classify`), consumed by `DatabaseViewModel`, `../Views/UnlockView.swift`, and `../Services/AppSupport/FeedbackSubmissionService.swift`. Its privacy contract — `privacyNote` plus the `sanitized(_:)` redaction — keeps file names, paths, and other user data out of diagnostics and feedback payloads; preserve it in any diagnostics change.
- `EntryEditViewModel.swift` owns entry form state for both create and edit flows, including custom-field normalization, tag normalization via `../Models/TagNormalizer.swift` (the shared split/trim/dedupe rules), TOTP field shaping, passkey-preserving round trips, and dirty-state tracking for the edit UI. TOTP enrollment from a scanned/pasted URI goes through `applyOTPAuthURI(_:)` (fills the form from a parsed `../Models/OTPAuthURI.swift` and remembers the verbatim URI for storage — unless the entry is KeeOTP-sourced, which keeps its query-rewrite path), its string-taking wrapper `applySetupLink(_:)` (parses and applies, or returns the `OTPAuthURIError` for the editor's inline message without touching the form), and `removeTOTP()`; the payload carries the URI only while its parsed values still match the form, decided at payload time with no invalidation bookkeeping. `supportedTOTPDigits` is what the entry's storage format can actually hold (`[6, 8]` for a KeeOTP-sourced entry, whose query the parser only reads back at those sizes) and `unsupportedTOTPDigitsMessage` blocks `canSave` while the form asks for anything else — the payload's last-resort behavior there is to revert the whole TOTP edit, which must never be something the user can reach silently by picking a digit count or enrolling a 7-digit link. It also owns the tag-suggestion strip's state: `knownTags` (the database's tags in display order) and `inheritedTags` are snapshotted at construction — the editor is modal over a stable tree and deliberately does not chase concurrent external changes — while `tagSuggestions` re-reads the applied tags on every access so a chip leaves and returns as the user edits. Tag state is split in two: `tags` is the committed list the pill strip renders (exact-string identity, arrival order, seeded from the file), and `pendingTagText` is the half-typed token in the field. `commitPendingTag()` (Return, or a suggestion tap) splits the field on every separator and appends the results. Committing deliberately never happens from the field's setter: rewriting a focused `TextField`'s bound text races the keystrokes still in flight and silently drops them — reproduced on device, where typing `alpha,beta,gam` kept only `alpha`. `normalizedTags()` — what the payload, dirty tracking, and suggestion exclusion all read — is the committed pills plus the pending token, so saving mid-typing never drops a tag. `appendTagSuggestion(_:)` commits the pending token first and then appends, so a tapped tag and a typed one normalize identically and land in the order the user acted; `removeTag(_:)` drops a pill and ignores unknown tags.
- `GroupEditViewModel.swift` owns group form state for `../Views/GroupEditView.swift` and emits one `GroupDraftPayload`; `DatabaseViewModel.updateGroup(groupID:draft:)` owns applying and saving it. Tag handling is `EntryEditViewModel`'s, deliberately copied rather than reinvented — committed `tags` pills plus a `pendingTagText` token, `commitPendingTag()` never called from the field's setter, `normalizedTags()` folding the pending token into the payload and the dirty check — with one divergence: `tagSuggestions` excludes only the group's own applied tags, because re-stating an ancestor's tag on a child group is legitimate authoring. `knownTags` is a construction-time snapshot, same as the entry editor's. The AutoFill switch is seeded from the *effective* exclusion, so a group hidden by an ancestor opens with it on and `isExclusionInherited` explains why; an untouched switch replays `originalSearchingEnabled` verbatim — including "no `<EnableSearching>` element at all" — because `GroupDraftPayload.searchingEnabled` is absolute rather than a delta, and anything else would silently author or clear the flag. `canSave` requires a non-empty trimmed name (the draft layer rejects an empty one) and a dirty form. `Identifiable` + `Hashable` on a stable `id` so `sheet(item:)` / `navigationDestination(item:)` can carry it.
- `TOTPViewModel.swift` owns live TOTP code refresh and countdown state for entry-detail UI.
- `TOTPEnrollmentViewModel.swift` owns the decision logic behind `../Views/TOTPEnrollmentDestinationView.swift` (the incoming `otpauth://` destination sheet): entry candidates in tree order with recycle-bin subtrees excluded and folder paths derived the same way as `DatabaseViewModel.folderPath(forEntryID:)`, local case-insensitive search over title/username/URL (its own `searchText`, never the session's; `hasActiveSearch` tells the sheet whether an empty result is a missed query or an empty database), the flattened indented group-option list (visible root first, recycle bin excluded), new-entry prefill derivation from the URI (title = issuer ?? account, username = account), and the replace-confirmation predicate (`requiresReplaceConfirmation`, true only when the target already has TOTP). Built as a snapshot over `KPGroup` so it is pure and unit-testable (`../../KeeForgeTests/TOTPEnrollmentViewModelTests.swift`); a convenience init pulls the tree from a `DatabaseViewModel`.
- `CloudFileBrowserSession.swift` owns account selection plus cloud-provider authentication state for the cloud database picker, including the manual-connection-form branch (`usesManualConnectionForm`/`adoptManualAccount`) used by WebDAV.
- `WebDAVConnectViewModel.swift` owns the manual WebDAV connect form's field state, HTTPS-by-default validation with explicit unencrypted-HTTP opt-in, and submit-to-provider (`WebDAVConnecting.connect`) flow.
- `CloudFolderBrowserViewModel.swift` owns folder browsing, search text, loading, and load-error state for the cloud file browser.
- `DatabaseCreationViewModel.swift` owns new-database form validation, local export preparation, cloud creation requests, and the advanced cipher/KDF preset selection threaded into both request types.
- `MasterKeyChangeViewModel.swift` owns the Change Master Key form (`../Views/MasterKeyChangeView.swift`): new password/confirm state with the creation flow's strength warning, key-file keep-current/replace/remove state (`selectKeyFile(url:)` mirrors `DatabaseCreationViewModel`'s security-scope + bookmark handling; keep-current falls back to the session's manually picked key file when no association exists), submit validation modeled on the creation validator, and `performChange()`, which captures the password before any suspension point, resolves the effective key-file bytes (loading the kept current key file through an injected loader), and aborts if `cancelPendingChange()` ran mid-flight (the view calls it on Cancel and on disappear, so a dismissed sheet can never rekey with cleared form state) and maps `DatabaseViewModel.RekeyError` / `SaveError` to user-facing messages. The rekey itself is an injected closure over `DatabaseViewModel.changeMasterKey`, so the model tests without an unlocked session (`MasterKeyChangeViewModelTests.swift`).

## Guidance

- These types are `@MainActor @Observable`; heavy work should delegate to services or detached tasks and only publish the final UI state back here.
- `DatabaseViewModel.State`, `failedAttempts`, `lockCycleID`, `draft`, `openTimeSHA512`, `saveConflict`, the captured cloud `expectedRev`, the session-key lifecycle, and the selected group/entry state are the main security and navigation invariants.
- Clipboard scrub on lock is another security invariant: `lock(manuallyTriggered:preservingClipboard:)` calls `ClipboardService.clearOwnedContents()` on every lock; `preservingClipboard` is the one deliberate exception, set only by iOS backgrounding so the copy-then-switch-to-paste flow still delivers the copied secret. This has regressed twice — read the comment block on `lock` in `DatabaseViewModel.swift` before changing it.
- Stage entry and group edits through `DatabaseDraft` plus `save()` rather than mutating `rootGroup` directly and reconstructing save state afterward; `EntryEditViewModel` should only emit `EntryDraftPayload` and local dirty-form state.
- If you change sort, search, or navigation/selection state, verify the matching unit tests and the targeted UI test class.
- Search for `CloudFileBrowserViewModelTests` before changing the cloud browser flow.
- Relevant tests usually live in `../../KeeForgeTests/DatabaseListViewModelTests.swift`, `../../KeeForgeTests/DatabaseViewModelTests.swift`, `../../KeeForgeTests/PendingUploadDrainerTests.swift`, `../../KeeForgeTests/EntryEditViewModelTests.swift`, `../../KeeForgeTests/GroupEditViewModelTests.swift`, `../../KeeForgeTests/TOTPViewModelTests.swift`, `../../KeeForgeTests/AutoLockTests.swift`, and `../../KeeForgeTests/SortOrderTests.swift`.
