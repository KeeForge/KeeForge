# Views Folder

This folder contains the SwiftUI screens for all supported app UIs: the compact iPhone-style flow, the regular-width iPad workspace, and the macOS app. Most feature screens are shared across those presentations, so account for every shell rather than assuming a single navigation structure.

## Supported UI Shells

- Compact UI: iPhone-sized layouts push from the database list into one active unlock or database session at a time.
- Regular-width UI: iPad layouts keep the database list visible while the selected unlock or database session renders in a dedicated detail workspace.
- macOS app: the `KeeForgeMac` target compiles this entire folder and always uses the regular (split-view) layout; it has its own `KeeForgeMacTests` and `KeeForgeMacUITests` targets.
- Treat all three shells as first-class product surfaces. If a feature adds navigation, chrome, editing, or status UI, verify how it lands in each presentation.

## Screen Map

- `DatabaseListView.swift`, `DatabaseRowView.swift`, `DatabaseDetailsView.swift`, and `CloudFileBrowserView.swift` own database picking, cloud browsing UI, rename/remove actions, read-only toggles and badges, the per-database AutoFill toggle (`database-details.autofill-toggle`, routed through `DatabaseListViewModel.setAutoFillEnabled`), pending-upload badges/conflict copy, "Push pending changes" actions, and settings entry points. `DatabaseDetailsView` is the one per-database settings screen behind two entry points: the list's "Database Details" context action (passes the `DatabaseListViewModel` plus an `onSelectKeyFile` closure; the list owns the key-file importer) and the unlocked database's gear button (`settings.button` in `GroupListView.swift`; passes `sessionViewModel`, which routes nickname/read-only edits through the open session, adds the App Settings link, and creates its own list view model with the `autoFillEnabledRefreshHandler` bridge). The read-only toggle reads KDBX 3.1 from the session's parsed header or, from the list, from `KDBXFileSummary`. Session context adds a Master Key section whose "Change Master Key…" row (`database-details.change-master-key`, disabled while read-only) pushes `MasterKeyChangeView` inside the details sheet's `NavigationStack`. `CloudFileBrowserView.swift` presents `WebDAVConnectView` for providers that use a manual connection form instead of hosted OAuth.
- `WebDAVConnectView.swift` owns the manual WebDAV connect sheet (server address, username, password with `PasswordInputRow`, advanced unencrypted-HTTP opt-in, inline error, Connect/Cancel), backed by `WebDAVConnectViewModel`.
- `DatabaseCreationView.swift` owns local and cloud database creation, including master-key input, key-file selection, destination choice, a collapsed Advanced section for cipher (AES-256/ChaCha20) and Argon2id preset selection (`database-create.cipher-picker`, `database-create.kdf-preset-picker`), and handoff to Files export or provider folder picking.
- `MasterKeyChangeView.swift` owns the Change Master Key screen, pushed from `DatabaseDetailsView`'s Master Key section — never a nested sheet — and backed by `MasterKeyChangeViewModel`. The system back button is hidden: Cancel is the single dismiss affordance, which also disables the edge-swipe pop that could abort a change mid-edit. Two `PasswordInputRow`s with the creation flow's strength warning, a key-file section (Select via its own `.fileImporter`, Clear), an error banner, and a busy overlay. Save presents a destructive confirmation dialog (extra key-file-only wording when the password fields are blank), then device-owner confirmation (`BiometricService.canAuthenticateDeviceOwner`, no-op under `-ui-testing`) before `performChange()`; an authentication failure other than a user cancel surfaces the error banner. Cancel and `onDisappear` call `cancelPendingChange()`, so dismissal mid-authentication aborts the change instead of rekeying with cleared fields. Identifiers: `master-key.new-password-field` / `master-key.new-password-visibility-button`, `master-key.confirm-password-field` / `master-key.confirm-password-visibility-button`, `master-key.keyfile.select`, `master-key.keyfile.clear`, `master-key.save`, `master-key.cancel`, `master-key.confirm-change`, `master-key.error`. Covered by `MasterKeyChangeUITests`.
- `KDBXExportDocument.swift` is the `FileDocument` wrapper around raw KDBX bytes for `.fileExporter`, shared by database creation and the export-copy / export-backup flows.
- `DatabaseExportPresenter.swift` owns the export-to-Files flow: `.databaseExporter(request:)` takes a `DatabaseExportRequest` (`.currentCopy` or `.backup`), loads the bytes through `DatabaseExportService`, presents `.fileExporter`, and shows a "Couldn’t Export Database" alert (`database-export.error.ok`) on failure. Entry points: the list row's "Export Copy…" context action (`database-row.export-copy-action`), the pending-upload conflict alert's Export / Discard / Cancel buttons (`pending-upload-conflict.export|discard|cancel`; Discard hands off to the row's "Discard Pending Upload?" dialog after a short delay so the alert has dismissed), and `DatabaseDetailsView`'s Export section (`database-details.export-copy`) plus its Backups section, which lists `DatabaseExportService.backups(for:)` as `database-details.backup-row` buttons (or `database-details.backups-empty`). The details view attaches its own presenter because it is presented from two places.
- `UnlockView.swift` owns password/key-file entry and biometric affordances for one database. Its header padlock: `isSealed` starts shut, and `sealShutIfArrivingFromLock` replays open-to-shut only when `DatabaseViewModel.didManuallyLock` says the user pressed Lock (cleared on open in `../App/KeeForgeApp.swift`); regular shells only — compact returns to the database list on lock and gets its own transition there. On macOS the master-password field is `MacUnlockPasswordField.swift` (`NSSecureTextField`/`NSTextField` `NSViewRepresentable`): a focused `NSSecureTextField` turns on secure event input, which bypasses every app-level key hook (`NSEvent` local monitors, `.keyboardShortcut`, `.onExitCommand`, `.onKeyPress`), so Return (submit) and Escape (back to the list) are caught at the field editor's `doCommandBySelector`.
- `GroupListView.swift`, `EntryListView.swift`, `EntryDetailView.swift`, and `SearchView.swift` own post-unlock navigation, entry/group creation and deletion affordances, expired-entry list/detail warnings, enabled expiration timestamps, detail presentation, and the global read-only + unsaved-change surfaces shown while a database is open. On macOS the sidebar column cannot host pushed `NavigationStack` levels (zero-height; see `../App/README.md`), so `../App/RegularDatabaseWorkspaceView.swift` builds its own three-column layout (`macSplitView` + `MacGroupTreeRow`) and `GroupListView` (toolbar, `.searchable`) renders on iOS/iPadOS only; `usesRegularLayout` in `../App/KeeForgeApp.swift` is hardcoded `true` on macOS, so the compact/`DatabaseNavigationView` paths are unreachable there. The entry editor is a sheet on macOS instead of a push. Because `GroupListView` never renders there, anything wired only into it is invisible on macOS — `macSplitView` therefore carries its own Move to Group items (`entry-row.move-context`, `group-row.move-context`), delete confirmations, and a Database Details toolbar button (`database-details.button`) that passes the live `DatabaseViewModel`; that last one is what makes Change Master Key reachable on macOS, since `DatabaseDetailsView` only shows the master-key section when it has a session. On the iPad split view `GroupListView` hands New Entry and Edit Group to `RegularDatabaseWorkspaceView` through its optional `onCreateEntry` / `onEditGroup` closures so they open in the detail column, and pushes them itself (compact) when the closures are nil. Group row context menu: "Edit Group" first (`group-row.edit-context`, opens `GroupEditView.swift`), then "Change Icon" (`group-row.change-icon-context`, presents `GroupIconPickerView.swift`) and the AutoFill exclusion toggle (`group-row.autofill-exclusion-context`; excluded rows show a `key.slash` badge, `group-row.autofill-excluded`). All three share the `canEditGroup` predicate — not read-only, not the recycle bin, not inside it — so a row never shows a badge it cannot act on (the Recycle Bin row always draws a trash can regardless of `iconID`).
- `TagListView.swift` and `TagEntriesView.swift` own the tag browser. `TagListView.swift` also declares `TagDestination` — the `Hashable` navigation value both stack shells register (`UUID` already means "group" and `KPEntry` "entry") — and `TagAccessibility`, the shared per-tag identifier-suffix normalizer. Entry points: the root-only "Tags" row in `GroupListView.swift` (`group-list.tags-row`, in-file `TagBrowserRow`, visible even at zero tags), the macOS sidebar's Tags section in `../App/RegularDatabaseWorkspaceView.swift` (`MacTagRow`, selection through `DatabaseViewModel.selectedTag`), and the entry-detail tag chips. Those chips are `Button`s in every shell, never `NavigationLink`s: several `NavigationLink`s in one `List` row let the row own the link, so a tap opens the wrong tag or several at once and the whole row highlights (`TagBrowserUITests` asserts which tag opens); the compact shell appends to `DatabaseViewModel.navigationPath`. `TagEntriesView` re-derives its entries from the view model on every render, never from a push-time snapshot, so a tag whose last carrier is edited away shows its empty state instead of crashing or popping; it wraps `EntryListView`, so rows keep `search.entry.navlink`. Identifiers: `tag-list`, `tag-list.row.<normalized-tag>` (iOS list and macOS sidebar alike), `tag-entries.list`, `entry-detail.tag.<normalized-tag>`, `entry-detail.inherited-tag.<normalized-tag>`. macOS renders the tag name as a `navigationSubtitle` where iOS uses the navigation title.
- `PendingRowActions.swift` is the single home for the row-action state the three shells share: `PendingEntryDeletion`, `PendingGroupDeletion`, `PendingDeletion` (with `confirmationAlert(viewModel:)`), and `PendingMove`. `GroupListView.swift`, `EntryListView.swift`, and the macOS `../App/RegularDatabaseWorkspaceView.swift` all build their delete confirmations and move sheets from it, so the alert titles, messages, and destructive-button wording cannot drift per shell. Before this the macOS rows deleted (and autosaved) straight from the context menu with no confirmation at all, including permanent deletes out of the recycle bin. The macOS menu-bar Delete (⌘⌫, `../App/KeeForgeCommands.swift`) routes here too — it signals `DatabaseViewModel.requestDeleteSelection()`, and the workspace builds the same `PendingDeletion` a row context menu would; a menu-bar delete must never bypass the confirmation.
- `EntryDetailView.swift` is the shared entry-detail screen on all three shells (compact push, iPad workspace detail, Mac detail column); on macOS its Edit button (`entry-detail.edit`) and edit sheet live in the detail column's `NavigationStack` (the sidebar zero-height caveat does not apply there). **Presentation-host rule:** presentation hosts (`EntryEditorPresentation`, the editor/alert hosts in `GroupListView.swift` and `EntryListView.swift`, `GroupEditView`'s presenters) attach to the body's outer container, never inside an `if let`/empty-state branch: a permanent delete from the editor removes the entry from the index while the editor is the topmost pushed view, and a branch-scoped `navigationDestination` or alert host torn down in that update leaves the editor stuck with no way to pop. Closing goes through `finishClose()`: while an editor is active, the entry-unavailable branch defers the close to the editor's delete completion (on the iPad detail root that branch's `onAppear` fires even under the pushed editor), and the selection-driven shells pass `popsOnClose: false` because the detail root's `dismiss` bubbles out to the split view and pops the *sidebar's* stack. The Tags section draws two strips from `DatabaseViewModel.detailTags(forEntryID:)`: the entry's own tags, then — in an `entry-detail.inherited-tags` container — the tags inherited from its group ancestry as outlined `folder` capsules. Inherited chips navigate like own ones but are not editable here (group tags are edited in `GroupEditView.swift`; the entry editor excludes them from suggestions). Both strips come from the seam the tag index is built from, so browsing to a tag never lands on an entry whose chips fail to explain the match (`InheritedTagsUITests`). Custom fields share one `Section` with each name in its own row; nesting the reusable field-row sections inside it produces mismatched separator insets. Every displayed and copied value (username, password, URLs, notes, custom fields — here and in `EntryHistoryView.swift`) passes through `DatabaseViewModel.resolvingFieldReferences(_:)` so KeePass `{REF:…}` field references show and copy as the value they point at (#90); `PasswordFieldRow` takes the same function as `resolveReferences`. The editor deliberately does not: it seeds from the raw entry so a save keeps the reference. `EntryRow` in `GroupListView.swift` takes the resolved username from its caller for the same reason.
- `AttachmentsSection.swift` (used by `EntryDetailView.swift`) owns the read-only entry-attachment list: paperclip rows resolved lazily via `DatabaseViewModel.attachmentData(for:)`, byte-size formatting, dangling-ref rows disabled and marked unavailable, and QuickLook preview/share backed by `AttachmentPreviewFileStore` temp files. `AttachmentQuickLookPreview.swift` provides one cross-platform `attachmentQuickLookPreview(url:onDismiss:)` modifier: iOS presents the `QLPreviewController` representable in a page-sized sheet wrapped in a `UINavigationController` so Quick Look draws its title, share item, and an added Done item (`EntryAttachmentsSmokeUITests` finds `QLPreviewControllerView`); macOS uses SwiftUI's `.quickLookPreview(_:)`. `onDismiss` runs the temp-file cleanup on both.
- `EntryEditView.swift`, `PasswordGeneratorSheet.swift`, and `SaveConflictAlert.swift` own entry form editing, password generation, discard confirmation, and the save-conflict alert choices surfaced from `DatabaseViewModel`. `basicFieldRow` captions each field itself, so on macOS the row goes through `macLabelsHidden()` (the built-in `TextField` label would otherwise be a second, right-aligned label) and `macFormFieldStyle()` (a grouped form draws fields borderless); the `Form` itself takes `macGroupedForm()`, without which macOS falls back to the edge-to-edge `.columns` style and clips the sheet title. `GroupEditView.swift`'s `fieldRow` is the same shape and carries the same three. `SaveConflictAlert.swift` carries three stacked, mutually exclusive alerts on one modifier: the conflict (`save-conflict.merge`, `save-conflict.reload`, `save-conflict.save-as-copy`, `save-conflict.cancel` — Merge Changes first, the only option that keeps both sides), the merge confirmation (`merge-summary.ok`), and the merge failure (`merge-failure.ok`, whose OK re-presents the conflict alert). A conflicting save leaves `EntryEditView` open; the editor holds its save/delete completion in `../ViewModels/EntryEditCompletionGate.swift` and reports it once `conflictHasSettled` (rationale in that file's doc comment and `../ViewModels/README.md`). Every presenter goes through `onComplete`, so the iOS push, both macOS sheets, and the TOTP enrollment flow inherit this. The Tags row stacks applied tags as removable pills (`entry-edit.tags`, per-pill `entry-edit.tag.<normalized-tag>` via `TagAccessibility`), the single-line entry field (`entry-edit.tags-field`), and a suggestion strip of `plus` chips (`entry-edit.tag-suggestions`, per-chip `entry-edit.tag-suggestion.<normalized-tag>`); both strips use `EntryDetailView.swift`'s `FlowLayout` and `TagCapsule` and render nothing when empty. Return submits (`commitPendingTag()`); typing a separator does **not** commit, because rewriting the field's text mid-edit drops in-flight keystrokes — `a, b` stays literal until Return splits it, and anything left uncommitted still reaches the payload. The strips are the one place a container identifier wraps buttons: `.accessibilityElement(children: .contain)` keeps the chips' own identifiers (see the `AutoFillTipBanner` hazard below). Every site that builds an `EntryEditViewModel` (`GroupListView.swift`, `EntryDetailView.swift`, the macOS ⌘N command in `../App/RegularDatabaseWorkspaceView.swift`) passes the tag pool and the location's inherited tags; the parameters default to empty so a missed site degrades to no suggestions.
- `EntryEditView.swift` also owns the editor's "One-Time Password" section, between Basics and Notes. With no TOTP configured it offers "Scan QR Code" (`entry-edit.totp.scan-qr`, iOS only, presents `TOTPQRScannerSheet.swift`), "Enter Setup Link" (`entry-edit.totp.enter-link`, presents the in-file `TOTPSetupLinkSheet`: `entry-edit.totp.link-field`, `entry-edit.totp.link-error` per `OTPAuthURIError` case, `entry-edit.totp.link-apply` / `entry-edit.totp.link-cancel`), and "Enter Setup Key" (`entry-edit.totp.enter-key`, toggles the manual rows). Entries with a non-empty trimmed `totpSecret` open straight into the configuration rows: the secret in a `PasswordInputRow` with `usesPasswordAutoFill: false` (`entry-edit.totp.secret-field` / `entry-edit.totp.secret-visibility-button`, reveal gated behind the same device-owner auth as the password row; AutoFill off so QuickType does not offer to replace the Base32 key with a generated password), a numeric period field (`entry-edit.totp.period-field`, a String mirror committed only when it parses to a positive integer; focus loss or submit snaps unparsable text back), `entry-edit.totp.digits-picker` (options are `EntryEditViewModel.supportedTOTPDigits` plus the current value, since an enrolled URI may carry any digit count in 1...9; a value the entry's format cannot store shows `entry-edit.totp.digits-error` and blocks Save via `canSave`), `entry-edit.totp.algorithm-picker`, and a confirmed "Remove Verification Code" button (`entry-edit.totp.remove` / `entry-edit.totp.remove-confirm`, calls `EntryEditViewModel.removeTOTP()`). Enrollment paths funnel through `EntryEditViewModel.applyOTPAuthURI(_:)` / `applySetupLink(_:)`.
- `TOTPQRScannerSheet.swift` (whole file `#if os(iOS)`; VisionKit's `DataScannerViewController` does not exist on macOS, where the scan affordance is hidden) is the TOTP enrollment camera sheet: a `DataScannerViewController` representable restricted to QR symbology. Scanning starts from a deferred main-actor task with one retry (`startScanning()` fails before the scanner is on screen), a still-failing start shows the unavailable state, and `dismantleUIViewController` stops the camera. The first payload that parses as a supported `otpauth://` URI completes the sheet; any other QR shows a transient hint, debounced per payload SHA-256 digest (rejected payloads can carry secrets and are never retained). Unsupported hardware and denied permission render `ContentUnavailableView`s (denied offers "Open Settings"; availability is re-checked when the scene becomes active). `NSCameraUsageDescription` lives in `../Info.plist`, localized via `../Resources/InfoPlist.xcstrings`. Cancel is `entry-edit.totp.scan-cancel`. XCUITest cannot drive the camera, so this sheet has no UI-test coverage; keep URI handling in the unit-tested `OTPAuthURI`.
- `TOTPEnrollmentDestinationView.swift` is the destination picker presented at the app root (`../App/KeeForgeApp.swift`) for an incoming `otpauth://` URL. Header summary (`totp-enroll.summary`), a "New Entry" path (`totp-enroll.new-entry`) that pushes a flattened group picker (`totp-enroll.group.<uuid>`, visible root first, recycle bin excluded) and opens the create-mode editor prefilled from the URI, and a searchable existing-entry list (`totp-enroll.entry-list`, rows `totp-enroll.entry.<uuid>`, plain `TextField` search `totp-enroll.search-field` — local filtering in `../ViewModels/TOTPEnrollmentViewModel.swift`, never the session's global `searchText`). Attaching over an entry that already has a code confirms first (`totp-enroll.replace-confirm`). One path-driven `NavigationStack` over a step enum; both paths open the normal `EntryEditView` with `applyOTPAuthURI` pre-applied — pushed on iOS, a sheet on macOS. Saving (or deleting) finishes the flow; cancelling the editor pops back to the destination list so a wrong pick does not destroy the incoming code (why `EntryEditView.Completion` distinguishes `.saved` from `.cancelled`). A read-only session renders an explanatory `ContentUnavailableView`. Cancel is `totp-enroll.cancel`. No UI-test coverage on purpose (XCUITest cannot deliver custom-scheme URLs reliably); the decision logic is unit-tested in `../../KeeForgeTests/TOTPEnrollmentViewModelTests.swift`.
- `PasswordInputRow.swift` owns editable password entry controls shared by master-password creation and entry editing; `usesPasswordAutoFill` (default on) drives both `textContentType` applications — the row's own and `passwordInputStyle(contentType:)`'s — so a row holding a non-password can turn password AutoFill off entirely. `PasswordDisplay.swift` owns read-only password reveal/display rows plus strength indicators. `EntryDetailView.swift`'s `ProtectedFieldRow` masks custom fields whose key is in `KPEntry.protectedStringKeys`, gates reveal and copy behind device-owner authentication, and is shared with the history viewer; identifiers `entry.copy.<normalized-key>` / `entry-history.copy.<normalized-key>` and `entry.protected-field.<normalized-key>.reveal` / `entry-history.protected-field.<normalized-key>.reveal`.
- `SettingsView.swift`, `AcknowledgmentsView.swift`, and `TipJarView.swift` own secondary settings and support surfaces. `SettingsView.swift` contains the in-file sub-screens `SecuritySettingsView`, `AutoFillSettingsView`, `DisplaySettingsView`, `AboutSettingsView`, `AboutSectionContent`, `MacSecuritySettingsTab`, and `MacDisplaySettingsTab`; identifiers: `settings.tab.{security,autofill,display,cloud,about}`, `settings.{security,autofill,display,about}.link`, `settings.cloud.account.label` / `settings.cloud.signout.button`, `settings.send-feedback`, `settings.autofill.copy-totp` (AutoFill section), `settings.display.{clear-favicon-cache,theme-picker,usage-stats-toggle,favicons-toggle}`, `settings.lock-policy.picker`, and `settings.block-screen-capture.toggle`. `AutoFillSettingsView` surfaces the system AutoFill provider status — `settings.autofill.provider-status` (accessibility **value** is the localized On/Off text; `LabeledContent(_:value:)` takes a plain `String`, so those words need `String(localized:)`), the one-tap `settings.autofill.turn-on`, and `settings.autofill.open-ios-settings` — both **iOS-only**, as is the Copy Verification Code row (`settings.autofill.copy-totp`), because the macOS extension cannot advertise `ProvidesOneTimeCodes` on the macOS 14 floor. macOS gets `settings.autofill.open-mac-settings` instead, which routes through `AutoFillStatusService.openAutoFillSettings()` (`ASSettingsHelper` is `macos(14.0)`; only the one-click enable prompt is macOS 15+). The iOS pair is visible in **both** states: iOS can refuse the one-tap prompt and tears this sheet down when the prompt closes, so a declined request is reported as persistent footer text (`DatabaseListViewModel.isAutoFillEnableRequestRejected`), never as an alert, and the manual route stays available. It also lists per-database AutoFill toggles (`settings.autofill.database-toggle.<database-id>`) and the confirmed "Clear AutoFill Entries" action (`settings.autofill.clear-entries` / `settings.autofill.clear-entries.confirm`); every per-database toggle goes through the shared `DatabaseListViewModel.setAutoFillEnabled` (passed into `SettingsView` as `listViewModel`; the open-database App Settings path uses an in-file fallback that installs the same refresh bridge) so disable does targeted identity removal and enable republishes the open session immediately. `TipJarView.swift` is StoreKit-backed and exposes `tip-jar.thank-you`, `tip-jar.tip-again.menu`, and `tip-jar.buy-me-a-coffee` (external link).
- `FeedbackComposerView.swift` is the feedback composer sheet presented from both `SettingsView` (`settings.send-feedback`) and `UnlockView`; it submits through `../Services/AppSupport/FeedbackSubmissionService.swift`.
- `WhatsNewView.swift` is the shared iOS/macOS release-education sheet. It renders the platform-filtered feature catalog supplied by `../Services/AppSupport/WhatsNewPresentationService.swift` and exposes stable `whats-new.*` accessibility identifiers.
- `AutoFillTipBanner.swift` is the dismissible "Turn On AutoFill" card shown by `DatabaseListView` (top safe-area inset) when KeeForge is not the enabled system AutoFill provider. It exposes `autofill-tip.enable` and `autofill-tip.dismiss`; do not add a container-level accessibility identifier — SwiftUI propagates it onto the child buttons and clobbers their ids.
- `GroupIconPickerView.swift` is the group icon chooser sheet presented from `GroupListView`'s group context menu: the standard KDBX icon set (`KPEntry.standardIconNames`, so it never offers an index with no glyph) as an unlabeled grid, current icon marked and scrolled to on appear. Selecting reports the index to the caller, which routes it through `DatabaseViewModel.setGroupIcon`; cancelling writes nothing. Identifiers: `group-icon-picker.cancel` and `group-icon-picker.icon.<iconID>`. Covered by `GroupIconPickerUITests`.
- `MoveToGroupPickerView.swift` is the "Move to Group" destination sheet presented from `GroupListView`'s entry and group context menus (`entry-row.move-context` / `group-row.move-context`): the flattened indented group tree from `DatabaseViewModel.moveDestinationOptions(forEntryID:/forGroupID:)` (recycle bin pruned; for a group, its own subtree too), current parent disabled and checkmarked. It reports the pick through `onSelect`; the caller routes it through `DatabaseViewModel.moveEntry`/`moveGroup` and saves. Identifiers: `move-picker.group.<uuid uppercase uuidString>` and `move-picker.cancel`.
- `GroupEditView.swift` is the group editor: name, icon, tags, notes, and Search & AutoFill visibility in one `Form`, applied as a single `EntryEdit.updateGroup` through `DatabaseViewModel.updateGroup(groupID:draft:)` and then saved. Like `EntryEditView` it carries no `NavigationStack` of its own: `GroupListView`'s `GroupListGroupEditorPresentation` pushes it on iOS (`navigationDestination(item:)`) and sheets it on macOS, while the Mac sidebar's `MacGroupTreeRow` hands the group up to `RegularDatabaseWorkspaceView.beginGroupEdit` so the sheet is hosted on the split view rather than on a row that comes and goes with the tree; both hosts follow the presentation-host rule in the `EntryDetailView` bullet. The Tags row is the entry editor's, copied whole (same identifiers under the `group-edit.` prefix); the one divergence is that `tagSuggestions` has no inherited-tag exclusion, because re-stating an ancestor's tag on a child group is legitimate authoring. The icon row presents the shared `GroupIconPickerView` and never previews a custom icon: the payload only carries a standard `iconID`, and the draft layer leaves a custom icon alone unless the user picks a different standard one. Entry point is "Edit Group", first in the group row context menu on both shells, under `canEditGroup`.
- `EntryIconPickerView.swift` is the entry icon chooser sheet, presented by tapping the icon in `EntryDetailView`'s header. Two grids: the standard KDBX set (`KPEntry.standardIconNames`) and, above it, the database's `Meta/CustomIcons` (`DatabaseViewModel.customIcons`, sorted by UUID because KDBX fixes no order; section omitted when empty, undecodable icons skipped). `<CustomIconUUID>` outranks `<IconID>` in every client, so the sheet marks whichever the entry actually displays and scrolls to it. Selecting reports an `EntryIconSelection` to the caller, which routes it through `DatabaseViewModel.setEntryIcon(_:entryID:)`; cancelling writes nothing; a read-only database renders the header icon as a plain image with no button. "Download Website Icon" (`entry-icon-picker.download-favicon`) fetches the entry's favicon, stores it in the database, and applies it: disabled when the entry's address names no public host, dismisses on success, failures alert on this sheet, and both grids are disabled while a download is in flight (a pick would race the download's own commit) while Cancel stays live. Identifiers: `entry-detail.icon-button`, `entry-icon-picker.cancel`, `entry-icon-picker.standard.<iconID>`, `entry-icon-picker.custom.<uuid uppercase uuidString>`, `entry-icon-picker.download-favicon`.
- `EntryHistoryView.swift` is the entry history sheet presented from `EntryDetailView`'s History row. It lists an entry's stored `<History>` versions newest first (`DatabaseViewModel.history(forEntryID:)` sorts; KDBX fixes no order and KeePass writes oldest-first) and drills into one version's fields, where it can be restored (confirmed; `DatabaseViewModel.restoreKeepsReplacedState` decides whether the confirmation may promise an undo). The version screen mirrors `EntryDetailView`'s field set, with tags as plain `TagCapsule`s since this sheet's `NavigationStack` does not resolve `TagDestination`. Its timestamp is labelled **Last Modified**, not "replaced": `cloneForHistory` copies the entry untouched, so the stamp is when that version was written. Identifiers: `entry-history.done`, `entry-history.version.<display index>`, `entry-history.restore` / `entry-history.restore.confirm`, and on the version screen `entry-history.copy.{title,username,url,totp,password}` (plus one per custom-field key), `entry-history.password.reveal`, `entry-history.totp.code`, and `entry-history.version-detail` on the Last Modified row (a leaf, because a container-level identifier would clobber the child controls'). `EntryDetailView`'s `entry-detail.history` row carries the stored-version count as its accessibility **value**, so tests read the count without parsing the locale-formatted label. Covered by `EntryHistoryUITests`.
- `FaviconView.swift` is a reusable async image wrapper used by list and detail UIs.
- Notes are rendered by `SelectableNotesText` in `EntryDetailView.swift` (also used by `EntryHistoryView.swift`), one type per platform: a `UITextView` `UIViewRepresentable` on iOS, an `NSTextView` `NSViewRepresentable` on macOS. Both are non-editable, selectable, and report a width-aware height through `sizeThatFits`. The macOS one builds its TextKit **1** stack explicitly (`NSTextView(frame:textContainer:)`) because sizing needs a `layoutManager`, which the TextKit 2 stack `NSTextView(frame:)` opts into does not have; its `Coordinator` exists only to keep the `NSTextStorage` alive, since `NSLayoutManager` does not retain it. URLs and email addresses are marked as links with `NSDataDetector` in `attributedNotes(_:)`.
- `AutoFillStoreInspectorView.swift` + `AutoFillStoreInspectorModel.swift` are **DEBUG-only developer tooling** (whole files wrapped in `#if DEBUG`; app target only, excluded from both extension targets) for validating AutoFill store state. `AutoFillStoreInspectorView` renders the real `ASCredentialIdentityStore` contents (enabled state, enumeration availability, total count, per-database sections keyed by parsed `CredentialRecordIdentifier`, legacy/unrecognized buckets) with a Refresh control; enumeration runs off the main actor and no decrypted secrets are read. Shown full-screen at the app root only when launched with `-autofill-store-inspector` (`../App/KeeForgeApp.swift`'s `rootView`). `AutoFillStoreInspectorModel.swift` holds the pure, unit-tested grouping helpers (`AutoFillStoreInspectorGrouping`) and render model types. Display strings use `Text(verbatim:)` and are not localized. Identifiers (all counts/states exposed as element **values**): `autofill-inspector.enabled-state` (`enabled`/`disabled`), `autofill-inspector.enumeration-state` (`available`/`unavailable`), `autofill-inspector.total-count`, `autofill-inspector.refresh`, `autofill-inspector.database.<database-id-uuidString>.count` (uppercase UUID), `autofill-inspector.legacy.count`, `autofill-inspector.unrecognized.count`.
  - **Simulators cannot enumerate the store.** On simulator runtimes (verified iOS 18.5 and 26.5) `ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)` always returns an empty array even though writes succeed and persist, so the inspector's counts — and the app's own enumerate-then-mutate store maintenance — are only meaningful on a physical device (`KeeForgeUITests/AutoFillStoreUITests` runs on a provisioned device for this reason).

## UI Rules

- Keep business logic in view models and services; views should compose state, trigger intents, and manage local presentation state only.
- Keep compact and regular-width layouts behaviorally aligned. If a screen gains iPad-specific presentation, prefer sharing the same core row/detail/editor views instead of forking the feature, and call out any intentional divergence in the local docs.
- Preserve existing accessibility identifiers on major controls, for both suites — `KeeForgeMacUITests` reuses the same identifiers as `KeeForgeUITests`. If a new flow needs automation, add identifiers as part of the feature instead of relying on visible labels. Identifier *stability* is not element-type stability: the macOS vault columns are `List(selection:)` rows, so `group.navlink` / `entry.navlink` land on cells there and on buttons on iOS. Mac tests must query them with `descendants(matching: .any)` (`MacUITestCase.rowQuery`), never `app.buttons`.
- Icon-only controls carry both an `accessibilityLabel` and `.macHelp(...)` (the macOS-only tooltip shim in `../Extensions/PlatformCompat.swift`), passing the same text. Do not reach for plain `.help()`: on iOS it becomes the VoiceOver hint and would change what an already-labelled control reads out.
- Stable identifiers with no current UI-test references — still part of the identifier surface `AGENTS.md` requires preserving, so keep them stable and add coverage when touching their flows: `database-row.pending-uploads-badge` and `database-row.push-pending-action` (database list), `entry-row.expired` (red warning indicator in group and search lists), `entry-detail.expired-warning` and `entry-detail.expiry` (expired entries and enabled expiration timestamps in entry detail), and `autofill.entry.expired` (AutoFill's interactive picker, expired credentials requiring explicit selection). Folder captions (`entry-row.folder`), group exclusion (`group-row.autofill-exclusion-context` / `group-row.autofill-excluded`), and the group icon picker (`group-row.change-icon-context`, `group-icon-picker.cancel`, `group-icon-picker.icon.<iconID>`) have focused UI coverage.
- The group editor's identifier surface, shared by both shells (the iOS/iPad row menu and the macOS sidebar row menu use the same `group-row.edit-context`): `group-row.edit-context` (context-menu entry point), `group-edit.name-field`, `group-edit.icon-button`, `group-edit.tags` / `group-edit.tag.<normalized-tag>` (applied pills, `TagAccessibility` suffixes), `group-edit.tags-field`, `group-edit.tag-suggestions` / `group-edit.tag-suggestion.<normalized-tag>`, `group-edit.notes-field`, `group-edit.keyboard-done`, `group-edit.autofill-toggle`, `group-edit.cancel`, `group-edit.save`, and `group-edit.saving-overlay`. `GroupEditUITests` drives the entry point, name, icon, applied/typed tags, notes, AutoFill toggle, cancel, and save controls; the suggestion strip and transient saving overlay have no direct test references. Keep all identifiers stable.
- Entry detail's header title carries `entry-detail.title` (a leaf `Text`), which is how the macOS keyboard-navigation tests read which entry the detail column is showing. Keep it stable.
- Entry detail exposes `entry.attachment.<index>` (per-row button, e.g. `entry.attachment.0`) and `entry.attachment.share` for the read-only attachments list; keep those stable unless the matching tests are updated with the change. Tests enumerate rows via the `entry.attachment.<index>` prefix rather than a shared row identifier, since SwiftUI collapses each row into one accessibility element.
- Keep entry-form state local to `EntryEditViewModel`, but keep draft/save orchestration, conflict handling, and lock/discard decisions in `../ViewModels/DatabaseViewModel.swift`.
- When changing navigation, split-view behavior, or sheet structure, rerun the smallest affected UI test class from `../../KeeForgeUITests/README.md`.
- If a view starts needing substantial async or state logic, prefer extracting a helper type or moving the logic into `../ViewModels` rather than growing one monolithic view file.
