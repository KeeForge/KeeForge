# Views Folder

This folder contains the SwiftUI screens for all supported app UIs: the compact iPhone-style flow, the regular-width iPad workspace, and the macOS app. Most feature screens are shared across those presentations, so account for every shell rather than assuming a single navigation structure.

## Supported UI Shells

- Compact UI: iPhone-sized layouts push from the database list into one active unlock or database session at a time.
- Regular-width UI: iPad layouts keep the database list visible while the selected unlock or database session renders in a dedicated detail workspace.
- macOS app: the `KeeForgeMac` target compiles this entire folder and always uses the regular (split-view) layout; it has its own `KeeForgeMacTests` and `KeeForgeMacUITests` targets.
- Treat all three shells as first-class product surfaces. If a feature adds navigation, chrome, editing, or status UI, verify how it lands in each presentation.

## Screen Map

- `DatabaseListView.swift`, `DatabaseRowView.swift`, `DatabaseDetailsView.swift`, and `CloudFileBrowserView.swift` own database picking, cloud browsing UI, rename/remove actions, read-only toggles and badges, the per-database AutoFill toggle (`database-details.autofill-toggle`, routed through `DatabaseListViewModel.setAutoFillEnabled`), pending-upload badges/conflict copy, "Push pending changes" actions, and settings entry points. `DatabaseDetailsView` is the one per-database settings screen behind both entry points: the list's "Database Details" context action and the unlocked database's gear button (`settings.button` in `GroupListView.swift`). The list passes its `DatabaseListViewModel` plus an `onSelectKeyFile` closure (it owns the key-file importer); the unlocked database passes `sessionViewModel`, which routes nickname and read-only edits through the open session, adds the App Settings link, and makes the view create its own list view model with the `autoFillEnabledRefreshHandler` bridge. The read-only toggle reads KDBX 3.1 from the session's parsed header or, from the list, from `KDBXFileSummary`. Session context also adds a Master Key section (next to the unlock-convenience Key File section) whose "Change Master Key…" row (`database-details.change-master-key`, disabled while read-only) pushes `MasterKeyChangeView` inside the details sheet's `NavigationStack`. `CloudFileBrowserView.swift` presents `WebDAVConnectView` in place of hosted OAuth for providers that use a manual connection form.
- `WebDAVConnectView.swift` owns the manual WebDAV connect sheet (server address, username, password with `PasswordInputRow`, advanced unencrypted-HTTP opt-in, inline error, Connect/Cancel), backed by `WebDAVConnectViewModel`.
- `DatabaseCreationView.swift` owns local and cloud database creation, including master-key input, key-file selection, destination choice, a collapsed Advanced section for cipher (AES-256/ChaCha20) and Argon2id preset selection (`database-create.cipher-picker`, `database-create.kdf-preset-picker`), and handoff to Files export or provider folder picking.
- `MasterKeyChangeView.swift` owns the Change Master Key screen (#59), pushed from `DatabaseDetailsView`'s Master Key section — never a nested sheet — and backed by `MasterKeyChangeViewModel`. The system back button is hidden (Cancel is the single dismiss affordance, and hiding it also disables the edge-swipe pop that could abort a change mid-edit). Two `PasswordInputRow`s with the creation flow's strength warning, a key-file section (current association, Select via its own `.fileImporter`, Clear), a creation-style error banner, and a busy overlay. Every Save presents a destructive confirmation dialog spelling out the unrecoverable-data stakes, with extra key-file-only wording when the password fields are blank, then runs the `EntryDetailView`-shaped device-owner confirmation (`BiometricService.canAuthenticateDeviceOwner`, no-op fallback under `-ui-testing`) before `performChange()`; an authentication failure other than a user cancel surfaces the error banner instead of returning silently. Success gives success haptics and pops back to the details sheet. Cancel and `onDisappear` call `cancelPendingChange()`, so dismissal mid-authentication aborts the change instead of rekeying with cleared fields. Identifiers: `master-key.new-password-field` / `master-key.new-password-visibility-button`, `master-key.confirm-password-field` / `master-key.confirm-password-visibility-button`, `master-key.keyfile.select`, `master-key.keyfile.clear`, `master-key.save`, `master-key.cancel`, `master-key.confirm-change`, `master-key.error`. Covered by `MasterKeyChangeUITests`.
- `UnlockView.swift` owns password/key-file entry and biometric affordances for one database. Its header padlock is the "database closed" beat: `isSealed` starts shut so opening from the list shows a settled lock, and `sealShutIfArrivingFromLock` replays open-to-shut only when `DatabaseViewModel.didManuallyLock` says the user pressed Lock (that flag is cleared when a database is opened, in `../App/KeeForgeApp.swift`). It rides the arrival transition rather than delaying the lock — the lock has already happened by the time this screen appears. Note this fires on the regular shells only; compact returns to the database list on lock instead of showing this screen, and gets its own transition on the vault/list swap in `../App/KeeForgeApp.swift`. On macOS the master-password field is `MacUnlockPasswordField.swift` (an `NSSecureTextField`/`NSTextField` `NSViewRepresentable`) so Return submits and Escape returns to the database list from within the focused field — a focused `NSSecureTextField` turns on secure event input, which bypasses every app-level key hook (`NSEvent` local monitors, `.keyboardShortcut`, `.onExitCommand`, `.onKeyPress`), so those keys are caught at the field editor's `doCommandBySelector`.
- `GroupListView.swift`, `EntryListView.swift`, `EntryDetailView.swift`, and `SearchView.swift` own post-unlock navigation, entry/group creation and deletion affordances, expired-entry list/detail warnings, enabled expiration timestamps, detail presentation, and the global read-only + unsaved-change surfaces shown while a database is open. macOS caveats: pushed `NavigationStack` levels inside the `NavigationSplitView` sidebar render zero-height on macOS, so the Mac workspace builds its own three-column layout in `../App/RegularDatabaseWorkspaceView.swift` (`macSplitView` + `MacGroupTreeRow`), putting toolbar and search on the split view so nothing collapses into the toolbar overflow chevron. `GroupListView` (with its toolbar and `.searchable`) therefore effectively renders on iOS/iPadOS only — the compact/`DatabaseNavigationView` code paths are unreachable on macOS because `usesRegularLayout` in `../App/KeeForgeApp.swift` is hardcoded `true` there. The entry editor is a sheet on macOS instead of a navigation push. The `group.back` drill-down toolbar button and its `onNavigateBack` parameter still exist in `GroupListView.swift` but are dead on both platforms — no caller passes the closure, no test references the identifier. `GroupListView`'s group context menu also carries the AutoFill exclusion toggle (`group-row.autofill-exclusion-context`) with a `key.slash` badge on excluded rows (`group-row.autofill-excluded`); the badge and menu item share the same eligibility rules — not read-only, not the recycle bin, not inside it — so a row never shows a badge it cannot act on. The same menu carries "Change Icon" (`group-row.change-icon-context`) under those identical eligibility rules, presenting `GroupIconPickerView.swift`; the Recycle Bin is excluded because its row always draws a trash can regardless of the stored `iconID`. Its **first** item is "Edit Group" (`group-row.edit-context`), which opens `GroupEditView.swift` under the same predicate; the two shortcuts below it stay, so a one-field change is still one tap.
- `TagListView.swift` and `TagEntriesView.swift` own the tag browser. `TagListView.swift` also declares `TagDestination` — the `Hashable` navigation value both stack shells register (`UUID` already means "group" and `KPEntry` "entry", so tags need their own type) — and `TagAccessibility`, the shared per-tag identifier-suffix normalizer. Entry points: the root-only "Tags" row in `GroupListView.swift` (`group-list.tags-row`, rendered by the in-file `TagBrowserRow`, visible even at zero tags), the macOS sidebar's Tags section in `../App/RegularDatabaseWorkspaceView.swift` (`MacTagRow`, selection through `DatabaseViewModel.selectedTag`), and the entry-detail tag chips. Those chips are `Button`s in every shell — never `NavigationLink`s, even where they push — because they all share one `List` row: a row holding several `NavigationLink`s lets the row rather than the chip own the link, so a tap opens the wrong tag (the row's last one) or several at once, and the row draws its selection background whenever any chip's value is on the navigation path, greying the whole card. The compact shell pushes by appending to `DatabaseViewModel.navigationPath` directly; `TagBrowserUITests` taps a chip and asserts which tag opens, so a regression to `NavigationLink` fails there. `TagEntriesView` re-derives its entries from the view model on every render — never a snapshot taken at push time — so a tag whose last carrier is edited away shows its own empty state instead of crashing or popping; it wraps `EntryListView`, so its rows keep that view's `search.entry.navlink` identifier. Identifiers: `tag-list`, `tag-list.row.<normalized-tag>` (iOS list and macOS sidebar alike), `tag-entries.list`, `entry-detail.tag.<normalized-tag>`, and `entry-detail.inherited-tag.<normalized-tag>`. macOS renders the tag name as a `navigationSubtitle` (content column) where iOS uses the navigation title.
- `EntryDetailView.swift` is the shared entry-detail screen on all three shells (compact push, iPad workspace detail, and the Mac detail column). On macOS its Edit button (`entry-detail.edit`) and edit sheet stay in the detail column's `NavigationStack`, which is safe (the zero-height bug is specific to sidebar columns). Presentation hosts (`EntryEditorPresentation`, and the deletion alerts in `GroupListView.swift`/`EntryListView.swift`) must stay attached to the body's outer `Group`, **outside** any `if let`/empty-state branch: a permanent delete from the entry editor removes the entry from the index while the editor is the topmost pushed view, and a branch-scoped `navigationDestination` gets torn down in that update, leaving the editor stuck with no way to pop (the v1.10.4 wedge). The same applies to alert hosts on branches that can vanish while the alert is up. Closing goes through `finishClose()` with two shell-dependent rules: while an editor is active, the entry-unavailable branch defers the close to the editor's delete completion (on the iPad detail root that branch's `onAppear` fires even under the pushed editor, and closing there tears the editor down mid-save), and the selection-driven shells pass `popsOnClose: false` because the detail root's `dismiss` has nothing of its own to pop — it bubbles out to the split view and pops the *sidebar's* stack, which is what reset the iPad workspace to the vault root. Its Tags section draws two strips from `DatabaseViewModel.detailTags(forEntryID:)`: the entry's own tags, then — in an `entry-detail.inherited-tags` container — the tags it carries only because of where it sits, drawn as outlined `folder` capsules so the two read apart without a separate caption. Inherited chips navigate like the own ones but are deliberately not editable *here*: a group's tags belong to the group and are edited in `GroupEditView.swift`, and the entry editor still excludes them from its suggestions rather than copying them onto the entry. Both strips come from the one seam the tag index is built from, so browsing to a tag can never land on an entry whose chips fail to explain the match (`InheritedTagsUITests`). Custom fields share one `Section` and keep each name inside its own row; do not nest their reusable field-row sections inside it, because SwiftUI then produces mismatched separator insets.
- `AttachmentsSection.swift` (used by `EntryDetailView.swift`) owns the read-only entry-attachment list: paperclip rows resolved lazily via `DatabaseViewModel.attachmentData(for:)`, byte-size formatting, dangling-ref rows disabled and marked unavailable, and QuickLook preview/share backed by `AttachmentPreviewFileStore` temp files. `AttachmentQuickLookPreview.swift` provides one cross-platform `attachmentQuickLookPreview(url:onDismiss:)` view modifier: **iOS** presents the `QLPreviewController` representable in a sheet (unchanged UX, driven by `EntryAttachmentsSmokeUITests`); **macOS** uses SwiftUI's native `.quickLookPreview(_:)`. `onDismiss` runs the temp-file cleanup on both platforms.
- `EntryEditView.swift`, `PasswordGeneratorSheet.swift`, and `SaveConflictAlert.swift` own entry form editing, password generation, discard confirmation, and the save-conflict alert choices surfaced from `DatabaseViewModel`. `SaveConflictAlert.swift` carries three stacked alerts on one modifier, mutually exclusive by construction: the conflict itself (`save-conflict.merge`, `save-conflict.reload`, `save-conflict.save-as-copy`, `save-conflict.cancel` — Merge Changes first, because it is the only option that keeps both sides), the merge confirmation (`merge-summary.ok`), and the merge failure (`merge-failure.ok`), whose OK re-presents the conflict alert so a declined merge is never a dead end. The Tags row stacks three things: a strip of the entry's applied tags as removable pills (`entry-edit.tags`, per-pill `entry-edit.tag.<normalized-tag>` via `TagAccessibility`, trailing `xmark`, tap to remove), the single-line entry field (`entry-edit.tags-field`), and a suggestion strip of tappable `plus` chips (`entry-edit.tag-suggestions`, per-chip `entry-edit.tag-suggestion.<normalized-tag>`). Both strips are laid out in `EntryDetailView.swift`'s `FlowLayout` and drawn with its `TagCapsule`. The field is deliberately single-line so Return submits (`commitPendingTag()`) instead of inserting a newline, which is also the only visible hint that tags commit one at a time. Typing a separator does **not** commit — the field's text is never rewritten mid-edit, because that drops in-flight keystrokes — so `a, b` stays literal text until Return splits it into two pills. Anything left uncommitted still reaches the payload. The applied strip renders nothing until the entry carries a tag, the same way the suggestion strip renders nothing when it has nothing to offer. The strip is the one place a container identifier wraps buttons: it is declared `.accessibilityElement(children: .contain)` so the chips keep their own identifiers instead of inheriting the container's (the `AutoFillTipBanner` hazard below). The strip renders nothing — no header, no empty container — when `EntryEditViewModel.tagSuggestions` is empty. Every site that builds an `EntryEditViewModel` (`GroupListView.swift`, `EntryDetailView.swift`, and the macOS ⌘N command in `../App/RegularDatabaseWorkspaceView.swift`) passes the pool and the location's inherited tags; the parameters default to empty so a missed site degrades to no suggestions rather than breaking.
- `EntryEditView.swift` also owns the editor's "One-Time Password" section, between Basics and Notes. With no TOTP configured it offers three entry paths — "Scan QR Code" (`entry-edit.totp.scan-qr`, iOS only, presents `TOTPQRScannerSheet.swift`), "Enter Setup Link" (`entry-edit.totp.enter-link`, presents the in-file `TOTPSetupLinkSheet`: paste-friendly `entry-edit.totp.link-field`, inline `entry-edit.totp.link-error` mapped per `OTPAuthURIError` case, `entry-edit.totp.link-apply` / `entry-edit.totp.link-cancel`), and "Enter Setup Key" (`entry-edit.totp.enter-key`, toggles the manual rows via local state). Entries that already carry a TOTP (non-empty trimmed `totpSecret`) open straight into the configuration rows: the secret in a `PasswordInputRow` with `usesPasswordAutoFill: false` (`entry-edit.totp.secret-field` / `entry-edit.totp.secret-visibility-button`, reveal gated behind the same device-owner auth as the password row in edit mode; password AutoFill is off because the QuickType bar would otherwise offer to replace the Base32 setup key with a generated password), a numeric period field (`entry-edit.totp.period-field`, a String mirror committed to the view model only when it parses to a positive integer; focus loss or submit snaps unparsable text back to the committed value so the field never shows a period Save would not write), digits and algorithm pickers (`entry-edit.totp.digits-picker` — options are `EntryEditViewModel.supportedTOTPDigits` plus the current value, since an enrolled URI may carry any digit count in 1...9 and an untagged selection renders blank; a value the entry's format cannot store shows `entry-edit.totp.digits-error` and blocks Save through `canSave` rather than letting the payload silently revert the whole TOTP edit — and `entry-edit.totp.algorithm-picker`), and a confirmed "Remove Verification Code" destructive button (`entry-edit.totp.remove`, confirm `entry-edit.totp.remove-confirm`) that calls `EntryEditViewModel.removeTOTP()`. Enrollment paths funnel through `EntryEditViewModel.applyOTPAuthURI(_:)` / `applySetupLink(_:)`; dirty tracking and save come free from the view model.
- `TOTPQRScannerSheet.swift` (whole file `#if os(iOS)` — VisionKit's `DataScannerViewController` does not exist on macOS, where the scan affordance is hidden) is the TOTP enrollment camera sheet: a `DataScannerViewController` representable restricted to QR symbology with highlighting on (scanning starts from a deferred main-actor task with one retry — `startScanning()` fails before the scanner is on screen — a still-failing start surfaces the unavailable state instead of a frozen preview, and `dismantleUIViewController` stops the camera on dismissal). The first payload that parses as a supported `otpauth://` URI completes the sheet; any other QR shows a transient "Not a verification-code QR code" hint (debounced per payload SHA-256 digest — rejected payloads can carry secrets and are never retained) and scanning continues. Unsupported hardware and denied camera permission render explanatory `ContentUnavailableView`s inside the sheet — the denied state with an "Open Settings" button; availability is re-checked when the scene becomes active again so returning from Settings recovers, and authorized-but-unavailable shows the unsupported message rather than blaming permissions — and `NSCameraUsageDescription` lives in `../Info.plist`, localized via `../Resources/InfoPlist.xcstrings`. Cancel is `entry-edit.totp.scan-cancel`. The camera cannot be driven by XCUITest, so this sheet has no UI-test coverage; keep the URI handling in `OTPAuthURI` where it is unit-tested.
- `TOTPEnrollmentDestinationView.swift` is the destination picker presented at the app root (`../App/KeeForgeApp.swift`) when an incoming `otpauth://` URL arrives (iOS Settings "Set Up Codes In", or any app opening the scheme). Header summary (`totp-enroll.summary`: issuer/account, localized "Verification code" fallback), a "New Entry" path (`totp-enroll.new-entry`) that pushes an indented flattened group picker (`totp-enroll.group.<uuid>`, visible root first, recycle bin excluded) and opens the create-mode editor prefilled from the URI, and a searchable existing-entry list (`totp-enroll.entry-list`, rows `totp-enroll.entry.<uuid>`, plain `TextField` search `totp-enroll.search-field` — local filtering in `../ViewModels/TOTPEnrollmentViewModel.swift`, never the session's global `searchText`; an empty list falls back to `ContentUnavailableView.search` only while a query is active, and to a "No Entries" state otherwise). Attaching over an entry that already has a code confirms first (`totp-enroll.replace-confirm`, destructive). Navigation is one path-driven `NavigationStack` over a step enum (group picker → editor is a normal two-element stack); both paths open the normal `EntryEditView` with `applyOTPAuthURI` pre-applied — pushed on iOS, a sheet on macOS like every other editor site. Saving (or deleting) finishes the whole flow; cancelling the editor pops back to the destination list so a wrong pick does not destroy the incoming code (this is why `EntryEditView.Completion` distinguishes `.saved` from `.cancelled`). A read-only session renders an explanatory `ContentUnavailableView` instead of destinations. Cancel is `totp-enroll.cancel`. No UI-test coverage on purpose — XCUITest cannot deliver custom-scheme URLs reliably; the decision logic is unit-tested in `../../KeeForgeTests/TOTPEnrollmentViewModelTests.swift`.
- `PasswordInputRow.swift` owns editable password entry controls shared by master-password creation and entry editing; `usesPasswordAutoFill` (default on) drives both `textContentType` applications — the row's own and `passwordInputStyle(contentType:)`'s — so a row holding something that is not a password can turn password AutoFill off entirely; `PasswordDisplay.swift` owns read-only password reveal/display rows plus strength indicators. `EntryDetailView.swift`'s `ProtectedFieldRow` masks custom fields whose key is in `KPEntry.protectedStringKeys`, gates reveal and copy behind device-owner authentication, and is shared with the history viewer. It preserves `entry.copy.<normalized-key>` / `entry-history.copy.<normalized-key>` and adds `entry.protected-field.<normalized-key>.reveal` / `entry-history.protected-field.<normalized-key>.reveal`.
- `SettingsView.swift`, `AcknowledgmentsView.swift`, and `TipJarView.swift` own secondary settings and support surfaces. `SettingsView.swift` contains the in-file sub-screens `SecuritySettingsView`, `AutoFillSettingsView`, `DisplaySettingsView`, `AboutSettingsView`, `AboutSectionContent`, `MacSecuritySettingsTab`, and `MacDisplaySettingsTab`; its identifier surface includes `settings.tab.{security,display,cloud,about}`, `settings.{security,autofill,display,about}.link`, `settings.cloud.account.label` / `settings.cloud.signout.button`, `settings.send-feedback`, `settings.autofill.copy-totp` (in the AutoFill section, moved from Security), `settings.display.{clear-favicon-cache,theme-picker,usage-stats-toggle,favicons-toggle}`, `settings.lock-policy.picker`, and `settings.block-screen-capture.toggle`. `AutoFillSettingsView` also surfaces the system AutoFill provider status — `settings.autofill.provider-status` (an accessibility **value** of the localized On/Off text; `LabeledContent(_:value:)` takes a plain `String`, so those two words need `String(localized:)` or they ship English), the one-tap `settings.autofill.turn-on`, and `settings.autofill.open-ios-settings`, which stays visible in **both** states on purpose: iOS can refuse the one-tap prompt and tears this sheet down when the prompt closes, so hiding the manual route while the provider is off leaves those users with no way into iOS Settings. For the same teardown reason a declined request is reported as persistent footer text driven by `DatabaseListViewModel.isAutoFillEnableRequestRejected`, never as an alert — anything modal raised at that moment is dropped before it appears. It further surfaces a per-database AutoFill toggle list (`settings.autofill.database-toggle.<database-id>`), and the confirmed "Clear AutoFill Entries" action (`settings.autofill.clear-entries` / `settings.autofill.clear-entries.confirm`); every per-database toggle must go through the app's shared `DatabaseListViewModel.setAutoFillEnabled` (passed into `SettingsView` as `listViewModel`; the open-database App Settings path uses an in-file fallback that installs the same refresh bridge) so disable does targeted identity removal and enable republishes the open session immediately. `TipJarView.swift` is StoreKit-backed and exposes `tip-jar.thank-you`, `tip-jar.tip-again.menu`, and `tip-jar.buy-me-a-coffee` (an external Buy-Me-a-Coffee link).
- `FeedbackComposerView.swift` is the feedback composer sheet presented from both `SettingsView` (`settings.send-feedback`) and `UnlockView`; it submits through `../Services/AppSupport/FeedbackSubmissionService.swift`.
- `WhatsNewView.swift` is the shared iOS/macOS release-education sheet. It renders the platform-filtered, user-facing feature catalog supplied by `../Services/AppSupport/WhatsNewPresentationService.swift` and exposes stable `whats-new.*` accessibility identifiers.
- `AutoFillTipBanner.swift` is the dismissible "Turn On AutoFill" card shown by `DatabaseListView` (top safe-area inset) when KeeForge is not the enabled system AutoFill provider. It exposes `autofill-tip.enable` and `autofill-tip.dismiss`; do not add a container-level accessibility identifier — SwiftUI propagates it onto the child buttons and clobbers their ids.
- `GroupIconPickerView.swift` is the group icon chooser sheet presented from `GroupListView`'s group context menu. It renders the standard KDBX icon set (driven off `KPEntry.standardIconNames`, so it can never offer an index with no glyph) as an unlabeled grid, the way KeePass's own chooser does, marks the group's current icon, and scrolls to it on appear. Selecting reports the index to the caller, which routes it through `DatabaseViewModel.setGroupIcon`; cancelling writes nothing. Identifiers: `group-icon-picker.cancel` and `group-icon-picker.icon.<iconID>` per cell.
- `GroupEditView.swift` is the group editor: name, icon, tags, notes, and Search & AutoFill visibility in one `Form`, applied as a single `EntryEdit.updateGroup` through `DatabaseViewModel.updateGroup(groupID:draft:)` and then saved. Like `EntryEditView` it carries no `NavigationStack` of its own — presenters supply one, and the presentation splits the same way: `GroupListView`'s `GroupListGroupEditorPresentation` pushes it on iOS (`navigationDestination(item:)`) and sheets it on macOS, while the Mac sidebar's `MacGroupTreeRow` hands the group up to `RegularDatabaseWorkspaceView.beginGroupEdit` so the sheet is hosted on the split view rather than on a row that comes and goes with the tree. Both hosts hang off the body's outer container, never inside an `if let`, for the v1.10.4 teardown reason above. The Tags row is the entry editor's, copied whole (applied pill strip, single-line field where Return commits, suggestion strip, both `.accessibilityElement(children: .contain)`); the only deliberate divergence is that there is no inherited-tag exclusion in `tagSuggestions`, because re-stating an ancestor's tag on a child group is legitimate authoring. The icon row presents the shared `GroupIconPickerView` and never previews a custom icon: the payload only carries a standard `iconID`, and the draft layer leaves a custom icon alone unless the user actually picks a different standard one. Entry point is "Edit Group", the **first** item of the group row context menu on both shells, under the same `canEditGroup` predicate the icon and AutoFill shortcuts use — not read-only, not the Recycle Bin, not inside it — so the Recycle Bin and a read-only database expose no editor at all. The older "Change Icon" and AutoFill-toggle shortcuts stay, identifiers unchanged.
- `EntryIconPickerView.swift` is the entry icon chooser sheet, presented by tapping the icon in `EntryDetailView`'s header. Two grids rather than the group picker's one: the standard KDBX set (same `KPEntry.standardIconNames` source, so it can never offer an index with no glyph) and, above it, the images the database carries in `Meta/CustomIcons` (`DatabaseViewModel.customIcons`, sorted by UUID because KDBX fixes no order for that dictionary). The custom section is omitted entirely when the database defines none, and a single icon whose bytes no image loader accepts is skipped rather than rendered as an empty cell. The two are exclusive because the format makes them exclusive — `<CustomIconUUID>` outranks `<IconID>` in every client — so the sheet marks whichever one the entry actually displays and scrolls to it on appear. Selecting reports an `EntryIconSelection` to the caller, which routes it through `DatabaseViewModel.setEntryIcon(_:entryID:)`; cancelling writes nothing. A read-only database renders the header icon as a plain image with no button at all, rather than offering a chooser that could only report a refusal. Above both grids sits "Download Website Icon" (`entry-icon-picker.download-favicon`), which fetches the entry's favicon, stores it in the database and applies it, the way KeePass's own dialog offers it; it is disabled when the entry's address names no public host, so the action is never offered where its only possible outcome is an error, and it dismisses on success because the icon has been applied to the entry by then and returning to the entry is what shows the result. Failures surface in an alert on this sheet rather than the entry screen behind it. While a download is in flight both grids are disabled — a pick would race the download's own commit, two icon choices for the same entry with the last writer winning — while Cancel stays live, since closing the sheet is still how "never mind" works. Identifiers: `entry-detail.icon-button`, `entry-icon-picker.cancel`, `entry-icon-picker.standard.<iconID>`, `entry-icon-picker.custom.<uuid uppercase uuidString>` per cell, and `entry-icon-picker.download-favicon`.
- `EntryHistoryView.swift` is the entry history sheet presented from `EntryDetailView`'s History row. It lists an entry's stored `<History>` versions, newest first (`DatabaseViewModel.history(forEntryID:)` sorts them, since KDBX fixes no order and KeePass writes oldest-first), and drills into one version's fields, where it can be restored (confirmed; `DatabaseViewModel.restoreKeepsReplacedState` decides whether the confirmation may promise an undo). The version screen mirrors `EntryDetailView`'s field set — title, username, password, URL, TOTP, notes, custom fields, tags, and a Details section — because a stored version can differ in any of them; tags render as plain `TagCapsule`s rather than the detail screen's links, since this sheet's `NavigationStack` does not resolve `TagDestination`. Its timestamp is labelled **Last Modified**, not "replaced": `cloneForHistory` copies the entry untouched, so the stamp is when that version was written, and it stopped being current at the *next* version's. Identifiers: `entry-history.done`, `entry-history.version.<display index>`, `entry-history.restore` / `entry-history.restore.confirm`, and on the version screen `entry-history.copy.{title,username,url,totp,password}` (plus one per custom-field key), `entry-history.password.reveal`, `entry-history.totp.code`, and `entry-history.version-detail` on the Last Modified row — a leaf, because a container-level identifier would clobber the child controls'. `EntryDetailView`'s `entry-detail.history` row carries the stored-version count as its accessibility **value**, so tests read the count without parsing the locale-formatted label. All of these are covered by `EntryHistoryUITests`.
- `FaviconView.swift` is a reusable async image wrapper used by list and detail UIs.
- `AutoFillStoreInspectorView.swift` + `AutoFillStoreInspectorModel.swift` are **DEBUG-only developer tooling** (whole files wrapped in `#if DEBUG`; app target only, excluded from both extension targets) for validating AutoFill store state. `AutoFillStoreInspectorView` renders the real `ASCredentialIdentityStore` contents (enabled state, enumeration availability, total count, per-database sections keyed by parsed `CredentialRecordIdentifier`, plus legacy/unrecognized buckets) with a Refresh control; enumeration runs off the main actor and no decrypted secrets are read. It is shown full-screen at the app root only when launched with `-autofill-store-inspector` (see `../App/KeeForgeApp.swift`'s `rootView`). `AutoFillStoreInspectorModel.swift` holds the pure, unit-tested grouping helpers (`AutoFillStoreInspectorGrouping`) and the render model types. Display strings use `Text(verbatim:)` and are intentionally not localized (dev-only, never shipped). Accessibility identifiers: `autofill-inspector.enabled-state` (value `enabled`/`disabled`), `autofill-inspector.enumeration-state` (value `available`/`unavailable`), `autofill-inspector.total-count`, `autofill-inspector.refresh`, `autofill-inspector.database.<database-id-uuidString>.count` (uppercase UUID), `autofill-inspector.legacy.count`, `autofill-inspector.unrecognized.count` — all counts/states exposed as element **values**.
  - **Simulators cannot enumerate the store.** On simulator runtimes (verified iOS 18.5 and 26.5) `ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)` always returns an *empty array* even though writes succeed and persist, so the inspector's counts — and the app's own enumerate-then-mutate store maintenance — are only meaningful on a physical device (`KeeForgeUITests/AutoFillStoreUITests` runs on a provisioned device for this reason).

## UI Rules

- Keep business logic in view models and services; views should compose state, trigger intents, and manage local presentation state only.
- Keep compact and regular-width layouts behaviorally aligned. If a screen gains iPad-specific presentation, prefer sharing the same core row/detail/editor views instead of forking the feature, and call out any intentional divergence in the local docs.
- Preserve existing accessibility identifiers on major controls, for both suites — `KeeForgeMacUITests` reuses the same identifiers as `KeeForgeUITests`. If a new flow needs automation, add identifiers as part of the feature instead of relying on visible labels.
- Stable identifiers with no current UI-test references — still part of the identifier surface `AGENTS.md` requires preserving, so keep them stable and add coverage when touching their flows: `database-row.pending-uploads-badge` and `database-row.push-pending-action` (database list), `entry-row.expired` (red warning indicator in group and search lists), `entry-detail.expired-warning` and `entry-detail.expiry` (expired entries and enabled expiration timestamps in entry detail), `autofill.entry.expired` (AutoFill's interactive picker, expired credentials requiring explicit selection), `group-row.change-icon-context` (group context menu shortcut) and `group-icon-picker.cancel` (group icon picker sheet). Folder captions (`entry-row.folder`), group exclusion (`group-row.autofill-exclusion-context` / `group-row.autofill-excluded`), and picker selection (`group-icon-picker.icon.<iconID>`) now have focused UI coverage.
- The group editor's identifier surface, shared by both shells (the iOS/iPad row menu and the macOS sidebar row menu use the same `group-row.edit-context`): `group-row.edit-context` (context-menu entry point), `group-edit.name-field`, `group-edit.icon-button`, `group-edit.tags` / `group-edit.tag.<normalized-tag>` (applied pills, `TagAccessibility` suffixes), `group-edit.tags-field`, `group-edit.tag-suggestions` / `group-edit.tag-suggestion.<normalized-tag>`, `group-edit.notes-field`, `group-edit.keyboard-done`, `group-edit.autofill-toggle`, `group-edit.cancel`, `group-edit.save`, and `group-edit.saving-overlay`. `GroupEditUITests` drives the entry point, name, icon, applied/typed tags, notes, AutoFill toggle, cancel, and save controls. The suggestion strip and transient saving overlay remain without direct test references; keep all identifiers stable.
- Entry detail exposes `entry.attachment.<index>` (per-row button, e.g. `entry.attachment.0`) and `entry.attachment.share` for the read-only attachments list; keep those stable unless the matching tests are updated with the change. Tests enumerate rows via the `entry.attachment.<index>` prefix rather than a shared row identifier, since SwiftUI collapses each row into one accessibility element.
- Keep entry-form state local to `EntryEditViewModel`, but keep draft/save orchestration, conflict handling, and lock/discard decisions in `../ViewModels/DatabaseViewModel.swift`.
- When changing navigation, split-view behavior, or sheet structure, rerun the smallest affected UI test class from `../../KeeForgeUITests/README.md`.
- If a view starts needing substantial async or state logic, prefer extracting a helper type or moving the logic into `../ViewModels` rather than growing one monolithic view file.
