# Views Folder

This folder contains the SwiftUI screens for both supported app UIs: the compact iPhone-style flow and the regular-width iPad workspace. Most feature screens are shared across those presentations, so view changes should account for both shells rather than assuming a single navigation structure.

## Supported UI Shells

- Compact UI: iPhone-sized layouts push from the database list into one active unlock or database session at a time.
- Regular-width UI: iPad layouts keep the database list visible while the selected unlock or database session renders in a dedicated detail workspace.
- Treat both shells as first-class product surfaces. If a feature adds navigation, chrome, editing, or status UI, verify how it lands in both presentations.

## Screen Map

- `DatabaseListView.swift`, `DatabaseRowView.swift`, the in-file `DatabaseDetailsView`, and `CloudFileBrowserView.swift` own database picking, cloud browsing UI, rename/remove actions, read-only toggles and badges, the per-database AutoFill toggle (`database-details.autofill-toggle`, routed through `DatabaseListViewModel.setAutoFillEnabled`), pending-upload badges/conflict copy, "Push pending changes" actions, and settings entry points. `CloudFileBrowserView.swift` presents `WebDAVConnectView` in place of hosted OAuth for providers that use a manual connection form.
- `WebDAVConnectView.swift` owns the manual WebDAV connect sheet (server address, username, password with `PasswordInputRow`, advanced unencrypted-HTTP opt-in, inline error, Connect/Cancel), backed by `WebDAVConnectViewModel`.
- `DatabaseCreationView.swift` owns local and cloud database creation, including master-key input, key-file selection, destination choice, and handoff to Files export or provider folder picking.
- `UnlockView.swift` owns password/key-file entry and biometric affordances for one database. On macOS the master-password field is `MacUnlockPasswordField.swift` (an `NSSecureTextField`/`NSTextField` `NSViewRepresentable`) so Return submits and Escape returns to the database list from within the focused field — a focused `NSSecureTextField` turns on secure event input, which bypasses every app-level key hook (`NSEvent` local monitors, `.keyboardShortcut`, `.onExitCommand`, `.onKeyPress`), so those keys are caught at the field editor's `doCommandBySelector`.
- `GroupListView.swift`, `EntryListView.swift`, `EntryDetailView.swift`, and `SearchView.swift` own post-unlock navigation, entry/group creation and deletion affordances, expired-entry list/detail warnings, enabled expiration timestamps, detail presentation, and the global read-only + unsaved-change surfaces shown while a database is open. macOS caveats: pushed `NavigationStack` levels inside the `NavigationSplitView` sidebar render zero-height on macOS. `GroupListView` (with its toolbar and `.searchable`) is now iOS/iPadOS-only for the workspace sidebar; the Mac workspace builds its own three-column layout in `../App/RegularDatabaseWorkspaceView.swift` (`macSplitView` + `MacGroupTreeRow`) so the toolbar and search live on the split view, not on `GroupListView`, and nothing collapses into the toolbar overflow chevron. `GroupListView` is still used on macOS only inside the compact/`DatabaseNavigationView` code paths. The entry editor is presented as a sheet on macOS instead of a navigation push. The Mac `group.back` drill-down toolbar button is retired (no test references it). `GroupListView`'s group context menu also carries the AutoFill exclusion toggle (`group-row.autofill-exclusion-context`) with a `key.slash` badge on excluded rows (`group-row.autofill-excluded`); the badge and the menu item share the same eligibility rules — not read-only, not the recycle bin, not inside it — so a row never shows a badge it cannot act on.
- `EntryDetailView.swift` is the macOS detail column: its Edit button (`entry-detail.edit`) and edit sheet stay in the detail column's `NavigationStack`, which is safe (the zero-height bug is specific to sidebar columns).
- `AttachmentsSection.swift` (used by `EntryDetailView.swift`) owns the read-only entry-attachment list: paperclip rows resolved lazily via `DatabaseViewModel.attachmentData(for:)`, byte-size formatting, dangling-ref rows disabled and marked unavailable, and QuickLook preview/share backed by `AttachmentPreviewFileStore` temp files. `AttachmentQuickLookPreview.swift` provides one cross-platform `attachmentQuickLookPreview(url:onDismiss:)` view modifier: **iOS** presents the `QLPreviewController` representable in a sheet (unchanged UX, driven by `EntryAttachmentsSmokeUITests`); **macOS** uses SwiftUI's native `.quickLookPreview(_:)`. `onDismiss` runs the temp-file cleanup on both platforms.
- `EntryEditView.swift`, `PasswordGeneratorSheet.swift`, and `SaveConflictAlert.swift` own entry form editing, password generation, discard confirmation, and the save-conflict alert choices surfaced from `DatabaseViewModel`.
- `PasswordInputRow.swift` owns editable password entry controls shared by master-password creation and entry editing; `PasswordDisplay.swift` owns read-only password reveal/display rows plus strength indicators.
- `SettingsView.swift`, `AcknowledgmentsView.swift`, and `TipJarView.swift` own secondary settings and support surfaces. `SettingsView.swift`'s in-file `AutoFillSettingsView` also surfaces the system AutoFill provider status (`settings.autofill.turn-on` / `settings.autofill.open-ios-settings`) via `AutoFillStatusService`, a per-database AutoFill toggle list (`settings.autofill.database-toggle.<database-id>`), and the confirmed "Clear AutoFill Entries" action (`settings.autofill.clear-entries` / `settings.autofill.clear-entries.confirm`). Every per-database AutoFill toggle must go through the app's shared `DatabaseListViewModel.setAutoFillEnabled` (passed into `SettingsView` as `listViewModel`; the open-database App Settings path uses an in-file fallback that installs the same refresh bridge) so disable does targeted identity removal and enable republishes the open session immediately.
- `WhatsNewView.swift` is the shared iOS/macOS release-education sheet. It renders the platform-filtered, user-facing feature catalog supplied by `../Services/AppSupport/WhatsNewPresentationService.swift` and exposes stable `whats-new.*` accessibility identifiers.
- `AutoFillTipBanner.swift` is the dismissible "Turn On AutoFill" card shown by `DatabaseListView` (top safe-area inset) when KeeForge is not the enabled system AutoFill provider. It exposes `autofill-tip.enable` and `autofill-tip.dismiss`; do not add a container-level accessibility identifier — SwiftUI propagates it onto the child buttons and clobbers their ids.
- `FaviconView.swift` is a reusable async image wrapper used by list and detail UIs.
- `AutoFillStoreInspectorView.swift` + `AutoFillStoreInspectorModel.swift` are **DEBUG-only developer tooling** (whole files wrapped in `#if DEBUG`; app target only, excluded from both extension targets) for the AutoFill store-validation harness. `AutoFillStoreInspectorView` renders the real `ASCredentialIdentityStore` contents (enabled state, enumeration availability, total count, source, per-database sections keyed by parsed `CredentialRecordIdentifier`, plus legacy/unrecognized buckets) with a Refresh control; enumeration runs off the main actor and no decrypted secrets are read. It is shown full-screen at the app root only when launched with `-autofill-store-inspector` (see `../App/KeeForgeApp.swift`'s `rootView`). `AutoFillStoreInspectorModel.swift` holds the pure, unit-tested grouping helpers (`AutoFillStoreInspectorGrouping`), the render model types, and `AutoFillStoreStatusLog` (the `-autofill-store-status-log` launch-time probe). Display strings use `Text(verbatim:)` and are intentionally not localized (dev-only, never shipped). Accessibility identifiers: `autofill-inspector.enabled-state` (value `enabled`/`disabled`), `autofill-inspector.enumeration-state` (value `available`/`unavailable`), `autofill-inspector.total-count`, `autofill-inspector.source` (value `api`/`fallback-db`), `autofill-inspector.refresh`, `autofill-inspector.database.<database-id-uuidString>.count` (uppercase UUID), `autofill-inspector.legacy.count`, `autofill-inspector.unrecognized.count` — all counts/states exposed as element **values**.
  - **Simulator enumeration fallback lives at the store seam, not here.** On simulator runtimes (verified iOS 18.5 and 26.5) `ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)` always returns an *empty array* even though `saveCredentialIdentities`/`replaceCredentialIdentities`/`removeCredentialIdentities` succeed and the identities persist (QuickType consumes them). Because the app's own store maintenance (`CredentialIdentityStoreManager.populate` / `removeIdentities(forDatabase:)`) enumerates-then-mutates, that empty read breaks per-database maintenance on every simulator. The fix is a **single** fallback at the seam — `SystemCredentialIdentityStore.credentialIdentities()` (`../Services/AutoFill/CredentialIdentityStoreManager.swift`), under `#if DEBUG && targetEnvironment(simulator)` only — which, when the API returns empty, reconstructs real `ASCredentialIdentity` objects from the store's backing SQLite file via `../Services/AutoFill/AutoFillIdentityStoreFallbackReader.swift` (`<NSHomeDirectory>/SystemData/com.apple.AuthenticationServices/Identities/Identities.db`, table `credential_identities`, `identity_type` `1`=password/`2`=passkey/`4`=one-time-code; metadata + public passkey identifiers only, never a private key). Non-simulator / Release builds are byte-for-byte unchanged; the API always wins when non-empty.
  - The inspector consumes that same seam signal: `AutoFillStoreInspectorViewModel.buildSnapshot` calls the DEBUG-only `credentialIdentitiesWithSource()`, which returns `(identities, source)` where `source == .fallbackDB` when the seam read the backing DB and `.api` otherwise (raw values feed `autofill-inspector.source`). There is **one** fallback, not two. **`enabled-state` and `enumeration-state` stay purely API-truth** — the seam only substitutes fallback rows for a non-`nil`, empty API result, so `enumerationAvailable == (identities != nil)` still mirrors the API.
  - **Known remaining simulator limitation (write-side, not enumeration):** the simulator's `saveCredentialIdentities` dedups identities that share `(service_id, user)` across databases, ignoring `recordIdentifier` — so two databases publishing the same domains + usernames collapse to one set on a simulator (verified on the harness). Multi-database *union* of identical-domain databases therefore cannot be observed on a simulator regardless of the enumeration fallback; per-database disable/removal (distinct record identifiers) is unaffected and works via the shim.

## UI Rules

- Keep business logic in view models and services; views should compose state, trigger intents, and manage local presentation state only.
- Keep compact and regular-width layouts behaviorally aligned. If a screen gains iPad-specific presentation, prefer sharing the same core row/detail/editor views instead of forking the feature, and call out any intentional divergence in the local docs.
- Preserve existing accessibility identifiers on major controls. If you add a new flow that needs automation, add identifiers as part of the feature instead of relying on visible labels.
- The database list now exposes `database-row.pending-uploads-badge` and `database-row.push-pending-action`; keep those stable unless the matching tests are updated with the change.
- Expired entry rows expose `entry-row.expired` on the red warning indicator in group and search lists; keep it stable unless matching tests are updated.
- Entry detail exposes `entry-detail.expired-warning` for expired entries and `entry-detail.expiry` for enabled expiration timestamps; keep them stable unless matching tests are updated.
- AutoFill's interactive picker exposes `autofill.entry.expired` for expired credentials that require explicit selection.
- Entry detail exposes `entry.attachment.<index>` (per-row button, e.g. `entry.attachment.0`) and `entry.attachment.share` for the read-only attachments list; keep those stable unless the matching tests are updated with the change. Tests enumerate rows via the `entry.attachment.<index>` prefix rather than a shared row identifier, since SwiftUI collapses each row into one accessibility element.
- Keep entry-form state local to `EntryEditViewModel`, but keep draft/save orchestration, conflict handling, and lock/discard decisions in `../ViewModels/DatabaseViewModel.swift`.
- When changing navigation, split-view behavior, or sheet structure, rerun the smallest affected UI test class from `../../KeeForgeUITests/README.md`.
- If a view starts needing substantial async or state logic, prefer extracting a helper type or moving the logic into `../ViewModels` rather than growing one monolithic view file.
