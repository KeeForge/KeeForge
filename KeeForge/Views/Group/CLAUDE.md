# Group Views

Post-unlock group navigation, the group editor, and the group icon and move-destination pickers.

## Screen Map

- `GroupListView.swift`, `EntryListView.swift`, `EntryDetailView.swift`, and `SearchView.swift` own post-unlock navigation, entry/group creation and deletion affordances, expired-entry list/detail warnings, enabled expiration timestamps, detail presentation, and the global read-only + unsaved-change surfaces shown while a database is open. On macOS the sidebar column cannot host pushed `NavigationStack` levels (zero-height; see `../../App/CLAUDE.md`), so `../../App/RegularDatabaseWorkspaceView.swift` builds its own three-column layout (`macSplitView` + `MacGroupTreeRow`) and `GroupListView` (toolbar, `.searchable`) renders on iOS/iPadOS only; `usesRegularLayout` in `../../App/KeeForgeApp.swift` is hardcoded `true` on macOS, so the compact/`DatabaseNavigationView` paths are unreachable there. The entry editor is a sheet on macOS instead of a push. Because `GroupListView` never renders there, anything wired only into it is invisible on macOS — `macSplitView` therefore carries its own Move to Group items (`entry-row.move-context`, `group-row.move-context`), delete confirmations, and a Database Details toolbar button (`database-details.button`) that passes the live `DatabaseViewModel`; that last one is what makes Change Master Key reachable on macOS, since `DatabaseDetailsView` only shows the master-key section when it has a session. On the iPad split view `GroupListView` hands New Entry and Edit Group to `RegularDatabaseWorkspaceView` through its optional `onCreateEntry` / `onEditGroup` closures so they open in the detail column, and pushes them itself (compact) when the closures are nil. Entry row context menu: the shared `../Entry/EntryRowCopyActions.swift` copy pair first, then "Move to Group" and the delete. Group row context menu: "Edit Group" first (`group-row.edit-context`, opens `GroupEditView.swift`), then "Change Icon" (`group-row.change-icon-context`, presents `GroupIconPickerView.swift`) and the AutoFill exclusion toggle (`group-row.autofill-exclusion-context`; excluded rows show a `key.slash` badge, `group-row.autofill-excluded`). All three share the `canEditGroup` predicate — not read-only, not the recycle bin, not inside it — so a row never shows a badge it cannot act on (the Recycle Bin row always draws a trash can regardless of `iconID`).
- `GroupIconPickerView.swift` is the group icon chooser sheet presented from `GroupListView`'s group context menu: the standard KDBX icon set (`KPEntry.standardIconNames`, so it never offers an index with no glyph) as an unlabeled grid, current icon marked and scrolled to on appear. Selecting reports the index to the caller, which routes it through `DatabaseViewModel.setGroupIcon`; cancelling writes nothing. Identifiers: `group-icon-picker.cancel` and `group-icon-picker.icon.<iconID>`. Covered by `GroupIconPickerUITests`.
- `MoveToGroupPickerView.swift` is the "Move to Group" destination sheet presented from `GroupListView`'s entry and group context menus (`entry-row.move-context` / `group-row.move-context`): the flattened indented group tree from `DatabaseViewModel.moveDestinationOptions(forEntryID:/forGroupID:)` (recycle bin pruned; for a group, its own subtree too), current parent disabled and checkmarked. It reports the pick through `onSelect`; the caller routes it through `DatabaseViewModel.moveEntry`/`moveGroup` and saves. The entry editor raises the same sheet for a New Entry form's destination group, over `DatabaseViewModel.groupDestinationOptions(currentGroupID:)` and with `navigationTitle: "Select Group"` — the pick is the same walk over the same tree, but "Move to Group" is not the sentence for an entry that does not exist yet. Identifiers: `move-picker.group.<uuid uppercase uuidString>` and `move-picker.cancel`.
- `GroupEditView.swift` is the group editor: name, icon, tags, notes, and Search & AutoFill visibility in one `Form`, applied as a single `EntryEdit.updateGroup` through `DatabaseViewModel.updateGroup(groupID:draft:)` and then saved. Like `EntryEditView` it carries no `NavigationStack` of its own: `GroupListView`'s `GroupListGroupEditorPresentation` pushes it on iOS (`navigationDestination(item:)`) and sheets it on macOS, while the Mac sidebar's `MacGroupTreeRow` hands the group up to `RegularDatabaseWorkspaceView.beginGroupEdit` so the sheet is hosted on the split view rather than on a row that comes and goes with the tree; both hosts follow the presentation-host rule in the `EntryDetailView` bullet. The Tags row is the entry editor's, copied whole (same identifiers under the `group-edit.` prefix); the one divergence is that `tagSuggestions` has no inherited-tag exclusion, because re-stating an ancestor's tag on a child group is legitimate authoring. The icon row presents the shared `GroupIconPickerView` and never previews a custom icon: the payload only carries a standard `iconID`, and the draft layer leaves a custom icon alone unless the user picks a different standard one. Entry point is "Edit Group", first in the group row context menu on both shells, under `canEditGroup`.

Shared UI shells and the folder-wide UI rules live in `../README.md`.
