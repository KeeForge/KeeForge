# Group Views

Post-unlock group navigation, the group editor, and the group icon and move-destination pickers.

## Screen Map

- `GroupListView.swift`, `EntryListView.swift`, `EntryDetailView.swift`, and `SearchView.swift` own post-unlock navigation, entry/group creation and deletion affordances, expired-entry list/detail warnings, enabled expiration timestamps, detail presentation, and the global read-only + unsaved-change surfaces shown while a database is open. On macOS the sidebar column cannot host pushed `NavigationStack` levels (zero-height; see `../../App/AGENTS.md`), so `../../App/RegularDatabaseWorkspaceView.swift` builds its own three-column layout (`macSplitView` + `MacGroupTreeRow`) and `GroupListView` (toolbar, `.searchable`) renders on iOS/iPadOS only; `usesRegularLayout` in `../../App/KeeForgeApp.swift` is hardcoded `true` on macOS, so the compact/`DatabaseNavigationView` paths are unreachable there. The entry editor is a sheet on macOS instead of a push. Because `GroupListView` never renders there, anything wired only into it is invisible on macOS — `macSplitView` therefore carries its own Move to Group sheet host and group-row item (`group-row.move-context`; entry rows get theirs from the shared `../Entry/EntryRowMoveAction.swift`), delete confirmations, and a Database Details toolbar button (`database-details.button`) that passes the live `DatabaseViewModel`; that last one is what makes Change Master Key reachable on macOS, since `DatabaseDetailsView` only shows the master-key section when it has a session. On the iPad split view `GroupListView` hands New Entry and Edit Group to `RegularDatabaseWorkspaceView` through its optional `onCreateEntry` / `onEditGroup` closures so they open in the detail column, and pushes them itself (compact) when the closures are nil. Entry row context menu: the shared `../Entry/EntryRowCopyActions.swift` copy pair first, then the shared `../Entry/EntryRowDuplicateAction.swift` and `../Entry/EntryRowMoveAction.swift`, then the delete. Group row context menu: "Edit Group" first (`group-row.edit-context`, opens `GroupEditView.swift`), then "Change Icon" (`group-row.change-icon-context`, presents `GroupIconPickerView.swift`) and the AutoFill exclusion toggle (`group-row.autofill-exclusion-context`; excluded rows show a `key.slash` badge, `group-row.autofill-excluded`). All three share the `canEditGroup` predicate — not read-only, not the recycle bin, not inside it — so a row never shows a badge it cannot act on (the macOS sidebar's Recycle Bin row always draws a trash can regardless of `iconID`).
- The database root's title is its view menu (`view.menu`): All Entries, Groups, Verification Codes, and Tags, then the Recycle Bin in a section of its own. The pick is `DatabaseViewModel.viewMode` and swaps the rows of the root `List`; pushed levels have no menu, always list their group, and keep the bar's large title with their group's name. A database opens on All Entries, and the pick is not kept across a lock. From iOS 26 the root draws its title itself, as the list's first section header (`titleViewMenu`: the view's name in the large-title font with a chevron), because the navigation bar's large title takes no taps — not as a system title, and not as a custom `.largeTitle` toolbar item either, which also collapses to inline as soon as a search drawer is pinned open under it. `GroupListTitleStyle` keeps the bar's own title removed while that header is on screen (`isTitleHeaderVisible`, fed by `onScrollVisibilityChange`) and shows it inline with the same items as a `.toolbarTitleMenu` once the header has scrolled away, the way a large title collapses. While the header is on screen the bar's leading corner shows the app's name instead (`RootBarAppName`, hidden from accessibility): the database list has the same name centered in its bar, so on unlock the text starts at that center and slides into the corner, or simply appears there under Reduce Motion. The item leaves the bar while the inline title is in it — hidden in place it would still push that title off the leading edge — so whether it has slid in is kept on `GroupListView`, not in the item. That layout needs the search field out of the bar, so from iOS 26 `GroupListSearchModifier` uses the system's default placement on every level (the bottom of the screen on iPhone). iOS 18 to 25 keep the bar's large title over the pinned search drawer and get the menu as a toolbar button between + and Sort instead (`hasTitleViewMenu` is the switch). All Entries is a flat section of the same entry rows with the folder caption (`entry-row.folder`) and a count footer (`group-list.summary`); Verification Codes draws `VerificationCodeRow.swift` instead — the entry's title, its current code from a per-row `TOTPViewModel` (grouped "284 019", read digit by digit by VoiceOver), username and group, the countdown, and a copy button (`verification-code-row.copy`). The row's opening part and the copy button are sibling buttons, since a button nested in a `NavigationLink` label gets no taps of its own; the opening part keeps `entry.navlink` and does what the link would (select in the regular-width workspace, append to `DatabaseViewModel.navigationPath` in the compact stack); Tags draws `TagListRows` (`../SearchAndTags/TagListView.swift`); Recycle Bin lists the bin group's contents and hides the + menu. The bin is never drawn as a group row at any level, so opening it goes through the menu only. Menu items are `Toggle`s, not one `Picker`, because a picker's options cannot be split into menu sections. Identifiers: `view-menu.<groups|allEntries|verificationCodes|tags|recycleBin>` (dropped by iOS 27 like every sectioned menu item; `KeeForgeUITestCase.selectDatabaseView` matches by label too). The database actions use `.topBarPinnedTrailing` where the SDK has it (`databaseActionsPlacement`, behind `#if compiler(>=6.4)`): an app built with the iOS 27 SDK otherwise folds them into an overflow menu once a long inline title needs their room. macOS never renders `GroupListView`, so its sidebar is unchanged: the whole tree with the bin pinned last, and its own Tags section. Covered by `ViewMenuUITests`, `DefaultViewUITests`, and `TagBrowserUITests`.
- `GroupIconPickerView.swift` is the group icon chooser sheet presented from `GroupListView`'s group context menu: the standard KDBX icon set (`KPEntry.standardIconNames`, so it never offers an index with no glyph) as an unlabeled grid, rendered through `../Components/StandardIconView.swift` with the same semantic colors as group rows; the current icon is marked and scrolled to on appear. Selecting reports the index to the caller, which routes it through `DatabaseViewModel.setGroupIcon`; cancelling writes nothing. Identifiers: `group-icon-picker.cancel` and `group-icon-picker.icon.<iconID>`. Covered by `GroupIconPickerUITests`.
- `MoveToGroupPickerView.swift` is the "Move to Group" destination sheet presented from `GroupListView`'s entry and group context menus (`entry-row.move-context` / `group-row.move-context`): the flattened indented group tree from `DatabaseViewModel.moveDestinationOptions(forEntryID:/forGroupID:)` (recycle bin pruned; for a group, its own subtree too), current parent disabled and checkmarked. It reports the pick through `onSelect`; the caller routes it through `DatabaseViewModel.moveEntry`/`moveGroup` and saves. The entry editor raises the same sheet for a New Entry form's destination group, over `DatabaseViewModel.groupDestinationOptions(currentGroupID:)` and with `navigationTitle: "Select Group"` — the pick is the same walk over the same tree, but "Move to Group" is not the sentence for an entry that does not exist yet. Identifiers: `move-picker.group.<uuid uppercase uuidString>` and `move-picker.cancel`.
- `GroupEditView.swift` is the group editor: name, icon, tags, notes, and Search & AutoFill visibility in one `Form`, applied as a single `EntryEdit.updateGroup` through `DatabaseViewModel.updateGroup(groupID:draft:)` and then saved. Like `EntryEditView` it carries no `NavigationStack` of its own: `GroupListView`'s `GroupListGroupEditorPresentation` pushes it on iOS (`navigationDestination(item:)`) and sheets it on macOS, while the Mac sidebar's `MacGroupTreeRow` hands the group up to `RegularDatabaseWorkspaceView.beginGroupEdit` so the sheet is hosted on the split view rather than on a row that comes and goes with the tree; both hosts follow the presentation-host rule in the `EntryDetailView` bullet. The Tags row is the entry editor's, copied whole (same identifiers under the `group-edit.` prefix); the one divergence is that `tagSuggestions` has no inherited-tag exclusion, because re-stating an ancestor's tag on a child group is legitimate authoring. The icon row presents the shared `GroupIconPickerView` and never previews a custom icon: the payload only carries a standard `iconID`, and the draft layer leaves a custom icon alone unless the user picks a different standard one. Entry point is "Edit Group", first in the group row context menu on both shells, under `canEditGroup`.

Shared UI shells and the folder-wide UI rules live in `../README.md`.
