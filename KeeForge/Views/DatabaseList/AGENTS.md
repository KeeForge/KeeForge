# DatabaseList Views

Database picking, creation, per-database settings, master-key changes, and export to Files.

## Screen Map

- `DatabaseListView.swift` takes `isSidebarColumn` from its host — the split view's sidebar column passes `true`, the compact full-screen root leaves it `false` — and styles its list from it: `.sidebar` in a column, `.insetGrouped` full screen. It is passed in rather than read from `horizontalSizeClass`, which a sidebar column reports as compact however wide the window is. The grouped card is drawn for a plain grouped page, so over a sidebar's background it comes out *darker* than the column on iPadOS and opaque over the material on macOS. macOS also drops the view's `NavigationStack` (the split view supplies navigation there, and a stack would paint over the sidebar material).
- `DatabaseListView.swift`, `DatabaseRowView.swift`, `DatabaseDetailsView.swift`, and `CloudFileBrowserView.swift` own database picking, cloud browsing UI, rename/remove actions, read-only toggles and badges, the per-database AutoFill toggle (`database-details.autofill-toggle`, routed through `DatabaseListViewModel.setAutoFillEnabled`), pending-upload badges/conflict copy, "Push pending changes" actions, and settings entry points. `DatabaseDetailsView` is the one per-database settings screen behind two entry points: the list's "Database Details" context action (passes the `DatabaseListViewModel` plus an `onSelectKeyFile` closure; the list owns the key-file importer) and the unlocked database's gear button (`settings.button` in `GroupListView.swift`; passes `sessionViewModel`, which routes nickname/read-only edits through the open session, adds the App Settings link, and creates its own list view model with the `autoFillEnabledRefreshHandler` bridge). The read-only toggle reads KDBX 3.1 from the session's parsed header or, from the list, from `KDBXFileSummary`. Session context adds a Master Key section whose "Change Master Key…" row (`database-details.change-master-key`, disabled while read-only) pushes `MasterKeyChangeView` inside the details sheet's `NavigationStack`. `CloudFileBrowserView.swift` presents `WebDAVConnectView` for providers that use a manual connection form instead of hosted OAuth. `DatabaseDetailsView`'s eleven sections are far taller than the 540x560 sheet its presenters give it, so its `Form` takes `macGroupedForm()`; without it macOS clipped everything from Cloud Sync down where no click could reach it. The Custom Name field sits in a `LabeledContent`, so it also takes `macLabelsHidden()` and `macFormFieldStyle()`.
- `DatabaseCreationView.swift` owns local and cloud database creation, including master-key input, key-file selection, destination choice, a collapsed Advanced section for cipher (AES-256/ChaCha20) and Argon2id preset selection (`database-create.cipher-picker`, `database-create.kdf-preset-picker`), and handoff to Files export or provider folder picking.
- `MasterKeyChangeView.swift` owns the Change Master Key screen, pushed from `DatabaseDetailsView`'s Master Key section — never a nested sheet — and backed by `MasterKeyChangeViewModel`. The system back button is hidden: Cancel is the single dismiss affordance, which also disables the edge-swipe pop that could abort a change mid-edit. Two `PasswordInputRow`s with the creation flow's strength warning, a key-file section (Select via its own `.fileImporter`, Clear), an error banner, and a busy overlay. Save presents a destructive confirmation dialog (extra key-file-only wording when the password fields are blank), then device-owner confirmation (`BiometricService.canAuthenticateDeviceOwner`, no-op under `-ui-testing`) before `performChange()`; an authentication failure other than a user cancel surfaces the error banner. Cancel and `onDisappear` call `cancelPendingChange()`, so dismissal mid-authentication aborts the change instead of rekeying with cleared fields. Identifiers: `master-key.new-password-field` / `master-key.new-password-visibility-button`, `master-key.confirm-password-field` / `master-key.confirm-password-visibility-button`, `master-key.keyfile.select`, `master-key.keyfile.clear`, `master-key.save`, `master-key.cancel`, `master-key.confirm-change`, `master-key.error`. Covered by `MasterKeyChangeUITests`. The `Form` takes `macGroupedForm()` and both password rows `macFormFieldStyle()`; in the default `.columns` style the key-file section fell off the bottom of the details sheet it is pushed into.
- `KDBXExportDocument.swift` is the `FileDocument` wrapper around raw KDBX bytes for `.fileExporter`, shared by database creation and the export-copy / export-backup flows.
- `DatabaseExportPresenter.swift` owns the export-to-Files flow: `.databaseExporter(request:)` takes a `DatabaseExportRequest` (`.currentCopy` or `.backup`), loads the bytes through `DatabaseExportService`, presents `.fileExporter`, and shows a "Couldn’t Export Database" alert (`database-export.error.ok`) on failure. Entry points: the list row's "Export Copy…" context action (`database-row.export-copy-action`), the pending-upload conflict alert's Export / Discard / Cancel buttons (`pending-upload-conflict.export|discard|cancel`; Discard hands off to the row's "Discard Pending Upload?" dialog after a short delay so the alert has dismissed), and `DatabaseDetailsView`'s Export section (`database-details.export-copy`) plus its Backups section, which lists `DatabaseExportService.backups(for:)` as `database-details.backup-row` buttons (or `database-details.backups-empty`). The details view attaches its own presenter because it is presented from two places.

Shared UI shells and the folder-wide UI rules live in `../README.md`.
