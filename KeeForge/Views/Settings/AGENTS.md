# Settings Views

App settings, release education, support surfaces, and DEBUG-only developer tooling.

## Screen Map

- `SettingsView.swift`, `AcknowledgmentsView.swift`, and `TipJarView.swift` own secondary settings and support surfaces. `SettingsView.swift` contains the in-file sub-screens `SecuritySettingsView`, `AutoFillSettingsView`, `DisplaySettingsView`, `CloudAccountsSettingsView`, `AboutSettingsView`, `AboutSectionContent`, `MacSecuritySettingsTab`, and `MacDisplaySettingsTab`; identifiers: `settings.tab.{security,autofill,menu-bar,display,cloud,about}`, `settings.{security,autofill,display,cloud,about}.link`, `settings.cloud.account.label` / `settings.cloud.signout.button`, `settings.send-feedback`, `settings.autofill.copy-totp` (AutoFill section), `settings.display.{clear-favicon-cache,theme-picker,usage-stats-toggle,favicons-toggle,accent-color-picker,accent-color-reset}`, `settings.lock-policy.picker`, and `settings.block-screen-capture.toggle`. The accent-color picker is cross-platform, stores an opaque sRGB color, and the reset action restores the asset-catalog default. `AutoFillSettingsView` surfaces the system AutoFill provider status through `settings.autofill.provider-status` (accessibility **value** is the localized On/Off text; `LabeledContent(_:value:)` takes a plain `String`, so those words need `String(localized:)`) and offers the one-tap `settings.autofill.turn-on` action on both platforms. The manual settings route stays available through `settings.autofill.open-ios-settings` or `settings.autofill.open-mac-settings`; a declined enable request is reported as persistent footer text (`DatabaseListViewModel.isAutoFillEnableRequestRejected`), never as an alert. The Copy Verification Code row (`settings.autofill.copy-totp`) is iOS-only: macOS supplies verification codes directly through the credential provider, and its timer-based clipboard clearing cannot outlive the extension process. On macOS its Databases footer also states that suggestions come from one database at a time — the most recently unlocked one — whenever more than one database is selected; macOS credential identity stores report no incremental-update support, so they cannot aggregate (`../../Services/AutoFill/CredentialIdentityStoreManager.swift`, `../../../KeeForgeMac/README.md`). It also lists per-database AutoFill toggles (`settings.autofill.database-toggle.<database-id>`) and the confirmed "Clear AutoFill Entries" action (`settings.autofill.clear-entries` / `settings.autofill.clear-entries.confirm`); every per-database toggle goes through the shared `DatabaseListViewModel.setAutoFillEnabled` (passed into `SettingsView` as `listViewModel`; the open-database App Settings path uses an in-file fallback that installs the same refresh bridge) so disable does targeted identity removal and enable republishes the open session immediately. `TipJarView.swift` is StoreKit-backed and exposes `tip-jar.thank-you`, `tip-jar.tip-again.menu`, and `tip-jar.buy-me-a-coffee` (external link); its tip rows take `macPlainRowButton()`, because a `Button` whose label fills a row draws as a bordered control inside a grouped `Form` on macOS — a gray slab inside the section's own gray card. The tip descriptions and prices, and the titles of the About links (`AboutLinkLabel`), take `Color.primary` rather than `.primary`/`.secondary`: inside a button or link label the hierarchical styles resolve against the tint, which left that text a dim shade of the accent color. On macOS every settings tab is pinned to `MacSettingsPane`'s fixed size rather than a minimum: a settings window sizes itself to its widest tab, and each `Form` footer paragraph wants a full line, so a free-sizing window opened far wider than any Mac settings window and left every label an arm's length from its control.
- The iOS root is a list of summary rows: Security, AutoFill, Display, and Cloud Accounts each push their screen and say what is currently set underneath (`../Components/SettingsSummaryRow.swift`), followed by Send Feedback, the support section, and an About row carrying the version. The wording comes from `AppSettingsSummary.swift`, which is pure and covered by `AppSettingsSummaryTests`: the Security row names a biometric only when auto-unlock is on and available, and the AutoFill row says nothing about the system provider until `DatabaseListViewModel.isAutoFillProviderEnabled` is known, so the root refreshes that state itself. The support section stays inline on the root — a tip jar behind a row is not seen. Cloud Accounts is a pushed screen on iOS and the same view is the Cloud tab on macOS; the macOS window keeps its tabs and has no summary rows.
- `MacMenuBarSettingsTab.swift` (`#if os(macOS)`) is Settings ▸ Menu Bar, shown only when the app put its `MacQuickAccessController` in the environment: the Show KeeForge in the Menu Bar toggle and `MacShortcutRecorder`, which records one key combination through a local key monitor (Escape cancels, a combination without ⌘/⌥/⌃ beeps) and sets the controller's `isRecordingShortcut` so the live shortcut is released while recording. A combination another app holds is reported in the footer. Identifiers: `settings.menu-bar.{toggle,shortcut-recorder,shortcut-clear}`.
- `SupportKeeForgeSection.swift` picks the build's support surface so neither `SettingsView` call site has to: an App Store build gets the StoreKit tip jar (`TipJarView`), while a notarized direct-download build has no receipt to purchase against and instead links to GitHub Sponsors (`support.sponsors`).
- `FeedbackComposerView.swift` is the feedback composer sheet presented from both `SettingsView` (`settings.send-feedback`) and `UnlockView`; it submits through `../../Services/AppSupport/FeedbackSubmissionService.swift`. The message editor alone is 150pt tall, so the `Form` takes `macGroupedForm()` and the follow-up email field `macFormFieldStyle()`.
- `WhatsNewView.swift` is the shared iOS/macOS release-education sheet. It renders the platform-filtered feature catalog supplied by `../../Services/AppSupport/WhatsNewPresentationService.swift` and exposes stable `whats-new.*` accessibility identifiers.
- `MacTransitionNoticeView.swift` (macOS only) is the one-time sheet shown to people arriving from the "Designed for iPad" build, presented by `AppRootView` when `MacTransitionNoticeService` claims it. Its copy is deliberately static — it must read correctly whether the database list behind it is intact, stale, or empty — so it never names a database or reports a count. Identifiers are `mac-transition-notice.*`.
- `AutoFillTipBanner.swift` is the dismissible "Turn On AutoFill" card shown by `DatabaseListView` (top safe-area inset) when KeeForge is not the enabled system AutoFill provider. It exposes `autofill-tip.enable` and `autofill-tip.dismiss`; do not add a container-level accessibility identifier — SwiftUI propagates it onto the child buttons and clobbers their ids.
- `AutoFillStoreInspectorView.swift` + `AutoFillStoreInspectorModel.swift` are **DEBUG-only developer tooling** (whole files wrapped in `#if DEBUG`; app target only, excluded from both extension targets) for validating AutoFill store state. `AutoFillStoreInspectorView` renders the real `ASCredentialIdentityStore` contents (enabled state, incremental-update support, total count, per-database sections keyed by parsed `CredentialRecordIdentifier`, legacy/unrecognized buckets) with a Refresh control; enumeration runs off the main actor and no decrypted secrets are read. Unreadable OS results render `autofill-inspector.enumeration-error` instead of a zero-count snapshot; each database exposes exact kind/service/label/record-identifier metadata through `autofill-inspector.database.<uuid>.identities`. Shown full-screen at the app root only when launched with `-autofill-store-inspector` (`../../App/KeeForgeApp.swift`'s `rootView`). `AutoFillStoreInspectorModel.swift` holds the pure, unit-tested grouping helpers (`AutoFillStoreInspectorGrouping`) and render model types. Display strings use `Text(verbatim:)` and are not localized. Identifiers (all counts/states exposed as element **values**): `autofill-inspector.enabled-state` (`enabled`/`disabled`), `autofill-inspector.incremental-updates` (`supported`/`unsupported`), `autofill-inspector.total-count`, `autofill-inspector.refresh`, `autofill-inspector.database.<database-id-uuidString>.count` (uppercase UUID), `autofill-inspector.legacy.count`, `autofill-inspector.unrecognized.count`.
  - **Simulators cannot enumerate the store.** On simulator runtimes (verified iOS 18.5 and 26.5) `ASCredentialIdentityStore.credentialIdentities(forService:credentialIdentityTypes:)` always returns an empty array even though writes succeed and persist, so the inspector's counts — and the app's own enumerate-then-mutate store maintenance — are only meaningful on a physical device (`KeeForgeUITests/AutoFillStoreUITests` runs on a provisioned device for this reason).
  - **macOS cannot enumerate the store either, and reports no incremental updates.** A real enabled provider on macOS 26.5 returns `supportsIncrementalUpdates == false` and an empty (or unattributable) enumeration, so the inspector's per-database sections stay empty there and every store write is a whole-store replace. That is why suggestions cannot aggregate across databases on macOS — reasoning in `../../../KeeForgeMac/README.md`.

Shared UI shells and the folder-wide UI rules live in `../README.md`.
