# Cloud Services

This folder owns provider abstractions plus the cloud-backed open/save pipeline.

## Main Files

- `CloudSyncModels.swift` describes cloud provider files and sync metadata used by the database list and sync coordinator. Optimistic concurrency uses a single opaque `rev` field; the provider-specific mapping (Dropbox rev, OneDrive cTag/eTag, WebDAV ETag → `rev`) happens in the this folder providers.
- `CloudProvider.swift` and `CloudProviderRegistry.swift` define the provider boundary the rest of the app talks to.
- `CloudAccountStore.swift` and `CloudTokenStore.swift` persist provider account state and auth material.
- `CloudSyncCoordinator.swift` decides when to reuse cache, download before open, or refresh metadata after cloud saves. If a pending AutoFill upload marker is still queued, a sync-down first writes a best-effort timestamped backup of the shared cache into the savers' backup directory (the cache is that save's only copy until the upload drains).
- `CloudDatabaseSaver.swift` performs the cloud-backed save pipeline with provider revision verification, upload, cache refresh, and backup rotation (timestamped backups, pruned to keep the 5 newest — same retention as `LocalDatabaseSaver`). Every byte comparison here — the cache gate, the stale-tag rebase, and the 412 retry — runs through `SaveBaseline` (see `../Persistence/README.md`), so a merge save proceeds while the cache still holds the open-time bytes: the recorded rev is deliberately left stale and rebases onto whichever head hashes to the reconciled remote.
- `CloudProvider.swift` also exposes create-only cloud uploads used by database creation; providers must use no-overwrite semantics for new files.
- `PendingUploadQueue.swift` and `PendingUploadDrainer.swift` handle deferred cloud uploads from the AutoFill save path. The drainer refuses to push a marker created before the reference's `lastMasterKeyChangeAt` — its payload is ciphertext under the pre-rekey key and would revert the master-key change on the remote — surfacing it as a conflict instead.
- `DropboxCloudProvider.swift`, `OneDriveCloudProvider.swift`, and `UITestDropboxCloudProvider.swift` implement the real and test cloud integrations.
- `UITestWebDAVCloudProvider.swift` is the WebDAV UI-test double (mirrors `UITestDropboxCloudProvider`): gated by `-ui-testing` + `UI_TEST_WEBDAV_PAYLOAD_JSON`, conforms to `CloudProvider` + `WebDAVConnecting`, and is swapped in by `provider(for:)` when enabled.
- `WebDAVModels.swift` holds the WebDAV config/credential value types, HTTPS-by-default URL normalization with explicit HTTP opt-in, accountId derivation, and the `WebDAVConnecting` connect seam.
- `WebDAVPropfindParser.swift` is a pure `XMLParser`-based multistatus parser (DAV: namespace only) that yields `[WebDAVResource]`.
- `WebDAVClient.swift` is a `Sendable` transport (injectable closure; live ephemeral `URLSession` with same-origin redirect handling and preemptive Basic auth) plus the HTTP/URLError→`CloudProviderError` mapping. The URLError mapping distinguishes TLS handshake failures (server's TLS configuration — often a cipher-suite mismatch, since many WebDAV servers lack the forward-secrecy suites Apple implements) from genuine certificate problems; keep those messages separate. App-side, `NSAllowsArbitraryLoads` is enabled in both app Info.plists because ATS has no per-domain exception for user-entered hosts — HTTPS-only enforcement for WebDAV lives in `WebDAVConnectViewModel`/`WebDAVModels` instead.
- `WebDAVCloudProvider.swift` implements `CloudProvider` + `WebDAVConnecting` for WebDAV: stateless, credential-per-call from `CloudTokenStore`, ETag-based `rev`, depth-zero `PROPFIND` metadata checks, and folder/.kdbx listing. Wired via `provider(for:)` and included in `CloudProviderRegistry.availableProviders`; the `isAvailableOnCurrentPlatform` gate below passes WebDAV on every platform.

## Change Carefully

- Keep provider-specific behavior behind `CloudProvider` so view models and tests stay decoupled.
- macOS UI gate: Dropbox and OneDrive are temporarily hidden from the macOS UI (add/import menus and the New Database destination picker) via the single `CloudProviderKind.isAvailableOnCurrentPlatform` choke point, which filters `availableProviders` and `DatabaseCreationDestinationChoice.availableChoices`. The OAuth/sync code paths stay compiled and tested; `provider(for:)` is intentionally left unfiltered so already-connected cloud databases still resolve and open on macOS. WebDAV stays user-visible on every platform. This is the shipped scope for the first macOS release, not a temporary state: the OAuth flows have never been validated end-to-end on a Mac, and unhiding them is a decision for a later release.
- Pending-upload markers must remain durable, secret-free, and App-Group-relative because AutoFill may return before the main app is foregrounded to upload the cloud cache copy.
- AutoFill cloud saves use a two-phase marker (`AutoFillSaveCoordinator.saveNewEntry`): a provisional marker recording the base bytes' SHA is made durable *before* the cache write (Darwin notification suppressed), then finalized to the payload's SHA and notified. Invariant: unuploaded cache bytes always have a durable covering marker, and every cache-replacing path (`downloadLatestCopy`, `applyUploadedBytesAfterSave`) must honor the marker-gated pre-overwrite backup. Do not reorder these steps without re-deriving the crash-at-every-step analysis written at the call site.
- The drainer auto-rebases a conflicted marker only when `marker.baseRev` equals the reported remote head (a provable fast-forward) on top of the pre-existing payload-SHA and store-rev checks; legacy markers decode with `baseRev == nil` and never rebase. Marker supersession is SHA-equality-based: an app save (or a newer AutoFill enqueue) drops markers whose recorded payload SHA equals its own base SHA. A drain request that coalesces onto an in-flight same-scope drain forces one extra pass, so a mid-drain enqueue is never swallowed.
- `CloudDatabaseSaver.remoteHasDiverged(recorded:remote:expectedRev:)` is the single conflict gate for both the app save and the pending-upload push. A missing `expectedRev` must never skip that gate — the upload itself still goes out rev-less (Dropbox `WriteMode.overwrite`, OneDrive `conflictBehavior=replace`), so the metadata check is the only protection on that path. Only a provider exposing neither rev nor content hash keeps the unverified path.
- The app-save path additionally guards against stale tags (OneDrive mutates cTag/eTag on its own): a divergence or provider-reported 412 whose remote bytes are SHA-512-identical to the open-time copy rebases onto the fresh rev instead of conflicting — with exactly one retry on the 412 path. Bytes that actually differ must still conflict for every provider; the pending-upload push keeps the plain gate.
- Conflict copies are create-only on every provider (`createFile`, never `upload`), with seconds in the filename and numbered retries on collision. This is a data-preservation feature; it must never replace an existing file.
- `CloudSyncCoordinator.syncIfNeededForOpen` races the metadata probe (`getMetadata`) against `openProbeDeadline` (10 s, injectable per call) whenever a cached copy could stand in (`allowCachedFallback` and the cache exists). A probe that misses the deadline is cancelled and treated as an unreachable server: the open falls back to the cache as `.offlineCached` (same banner as airplane mode) with `lastSyncError` set to the network-unavailable message. Only the probe is bounded — once it answers, the download runs on normal transport timeouts — and with no cache the probe waits out the transport, since there is nothing to fall back to. `CloudProviderError.isLikelyOffline` also counts `.serviceUnavailable` (WebDAV 502/503/504, Dropbox/OneDrive 5xx after retries) as offline, so a half-up server takes the same calm path.
- `CloudSyncCoordinator.downloadLatestCopy` pins the superseded cache with a hard link before listing markers, and publishes the new bytes with `replaceItemAt` under a coordinated `.forReplacing` write conditioned on the pinned inode. Do not reintroduce a rename-aside: it leaves the cache path empty for the duration of the backup write.
- `CloudProvider.download` returns the metadata of the bytes it wrote (nil where the transport cannot know). Record that in preference to the pre-download `getMetadata` reading.
- New code learning cloud state across an `await` must write it back via `DatabaseListStore.updateCloudSyncMetadata(for:ifUnchangedFrom:mutate:)`, not `update(_:)` — a whole-reference write rolls back a save or drain that completed inside the window. Two pre-existing `update(_:)` call sites remain (`applyUploadedBytesAfterSave`, the unlock read path); both self-heal with at worst one spurious conflict.
- Platform auth seams: `DropboxCloudProvider` uses SwiftyDropbox's desktop OAuth on macOS (system browser via `NSWorkspace`; completion returns through the `db-<appkey>` URL scheme into `handleRedirectURL`, same as iOS), while `OneDriveCloudProvider` presents MSAL from the anchor window's `contentViewController` and never handles redirect URLs on macOS (MSAL's web session intercepts them internally; `handleMSALResponse` is iOS-only and there is no macOS broker). Only the presentation layer is platform-gated; token storage, listing, download, and upload code stays shared.
- OneDrive rev/hash values only ever originate from the `$select`ed metadata shape (`metadataSelectList`): `upload(...)` and `createFile(...)` re-read the committed item by id and fall back to the upload response's metadata only if the re-read fails (the upload has committed by then, so the save must not fail). `contentHash` prefers `quickXorHash` (the only hash Graph guarantees on Personal and Business) and is algorithm-tagged (`quickXor:`/`sha1:`) so hashes of different algorithms never compare equal.
- OneDrive upload paths are split by size and by semantics. `upload(...)` (overwrite) sends a single `PUT .../content` with `If-Match` when the payload is at or below `simpleUploadByteLimit` (4 MiB); larger payloads, and every `createFile(...)` call, go through `uploadUsingSession`. `createFile` must never take the simple PUT — create-only semantics come from `@microsoft.graph.conflictBehavior: "fail"` in the session body, and `PUT /content` has no equivalent.
- Transient-failure retry is uniform across the OneDrive provider: reads, the simple content `PUT`, the `createUploadSession` POST, and the chunk `PUT` loop each allow up to 3 total attempts with ~0.5s/~1.5s backoff honoring a clamped `Retry-After`. 401/403/404/409/412 always fail immediately. `createUploadSession` additionally retries HTTP 400 `invalidRequest`, which OneDrive returns spuriously for well-formed requests (OneDrive/onedrive-api-docs#1064); the decision reads the Graph error `code`, never the message. A chunk PUT never blindly resends — it re-anchors on `GET uploadUrl` → `nextExpectedRanges` (`resumeOffset(fromNextExpectedRanges:totalBytes:)`) and treats 416 as a resync, and a give-up cancels the session with `DELETE uploadUrl`.
- `If-Match` on a OneDrive session upload is validated at session creation, not at commit, leaving an unguarded window for >4 MiB overwrites. Graph's `deferCommit` remedy is blocked on personal drives by OneDrive/onedrive-api-docs#1616; see the `createUploadSession` doc comment before attempting a fix.
- OneDrive Graph failures are mapped by error `code` first, HTTP status second (`mapGraphError(statusCode:errorCode:message:)`). Do not reintroduce status-only or English-message-substring mapping; `.invalidName` is the sole message-shaped heuristic and is scoped to code `invalidRequest`.
- All mutable state on the `OneDriveCloudProvider` singleton lives behind one `OSAllocatedUnfairLock`: the MSAL application instance (first-wins publish), one in-flight silent token acquisition per account, and the single interactive-auth slot. Never add a bare `var` to this type, and never hold the lock across an `await`.
- `DropboxCloudProvider` keeps `didConfigure` and one `DropboxClient` per accountId behind a single `OSAllocatedUnfairLock`. SwiftyDropbox's `setupWithAppKey*` asserts it runs exactly once, and its clients own URLSessions that only `shutdown()` invalidates — never call setup outside `configure(_:)`, and never build a client per operation.
- Only the Dropbox refresh token is persisted (`accessToken: ""`, expiry 0), so every request refreshes first and an offline call fails at the OAuth stage. SwiftyDropbox flattens the transport cause into a string, leaving `ClientError.oauthError(OAuth2Error.unknown)` — that is why `.unknown` maps to `.networkUnavailable` in `mapOAuthRefreshError`. Do not "fix" it to `.unknown(...)`.
- SwiftyDropbox does not retry 429, 5xx, or `too_many_write_operations`; `DropboxCloudProvider.withRetry` does, using the pure `retryDelay(for:attempt:)`. Retries are safe only because both write routes use `strictConflict`; keep that invariant if new routes are added.
- `OneDriveCloudProvider.graphURL(path:queryItems:)` takes an **already percent-encoded** path from `encodedGraphPath(_:)` and must not re-encode it. Do not reintroduce `URL.appendingPathComponent` here; it double-encodes (`%20` → `%2520`) and breaks every request for a path with a space, `&`, `#`, or non-ASCII character. `OneDriveCloudProviderTests` pins this.
- MSAL's macOS token cache lives in the `com.microsoft.identity.universalstorage` keychain group (iOS uses `com.microsoft.adalcache`, declared in `KeeForge/KeeForge.entitlements`). The macOS group is **not** declared in `KeeForgeMac/KeeForgeMac.entitlements`, because macOS ships WebDAV only and nothing there authenticates through MSAL. Whoever unhides OneDrive on macOS has to add it back — MSAL checks for it by suffix match before enabling the cache, and silent token refresh across relaunch breaks without it — and regenerate the Developer ID profiles, which embed the entitlements.
