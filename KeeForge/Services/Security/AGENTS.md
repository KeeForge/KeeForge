# Security Services

This folder holds device-security integrations and secret-handling helpers outside the core models.

## Main Files

- `BiometricService.swift` wraps LocalAuthentication flows used by the app and AutoFill. Database unlock stays biometric-only except in the native Mac app, where an explicit companion-only policy enables Apple Watch without allowing the Mac login password.
- `KeychainService.swift` stores composite keys with biometric access control, shared with the extension via the keychain access group (see the invariant below). On a Mac with a paired Apple Watch it also stores a separate device-only companion-gated item; keeping it separate preserves existing biometric items and makes the authorized mechanism explicit. A master-key change rewrites every item that exists, whether or not its mechanism can authenticate at that moment.
- `PasskeyCrypto.swift` handles passkey-related crypto helpers used by the extension flow: PEM key handling and assertion signing, plus registration support — ES256 key/credential-ID generation, attested authenticator data (COSE key, `aaguid` = KeeForge's stable product AAGUID `FF55D8C0-F4FB-4016-9FDD-56DBBD251802`), and the "none"-format WebAuthn attestation object via a minimal private CBOR encoder.
- `HardwareKeyService.swift` answers a YubiKey HMAC-SHA1 challenge through YubiKit (`YubiKitManager` NFC or Lightning accessory connection, `YKFChallengeResponseSession`) and maps YubiKit and Core NFC failures to `HardwareKeyError`. YubiKit is linked into the iOS `KeeForge` target only, so on the Mac app `availableTransports` is empty and a request throws `unavailable`. The file is not on the AutoFill allow-lists. Cancellation is Swift task cancellation, which stops the NFC session or accessory connection; the answer and the cancellation reach `finish` separately, so the request re-checks cancellation after it resumes and a cancelled request never returns a response. NFC needs the `com.apple.developer.nfc.readersession.formats` entitlement plus the YubiKey OTP AIDs and `NFCReaderUsageDescription` in `../../Info.plist`; Lightning needs `com.yubico.ylp` under `UISupportedExternalAccessoryProtocols`. Lightning is offered only where `LightningPort` says the model shipped with the port: YubiKit's own check treats every model newer than its table as a Lightning device, so on its own it would offer Lightning on USB-C iPhones (`../../../KeeForgeTests/LightningPortTests.swift`). USB-C YubiKeys are unreachable: YubiKit's smart-card connection does not carry OTP.
- `ScreenProtectionService.swift` holds both platform implementations behind `#if os(iOS)`/`#else`: iOS shields the app switcher and reacts to screen capture; macOS layers a resign-active cover with best-effort `NSWindow.sharingType` capture blocking through a single choke point (see `../../../KeeForgeMac/SECURITY.md`).
- `SecureRandom.swift` wraps `SecRandomCopyBytes` for throwing secure-random `Data` generation; on both AutoFill allow-lists in `../../../project.yml` (dual-list rule in `../README.md`).

## Change Carefully

- Keychain account naming, access-group behavior, biometric prompts, and screen-protection defaults all have user-visible security consequences.
- For a database with `DatabaseReference.hardwareKey` set, the item `KeychainService` stores is the pre-key (`KDBXCrypto.preKey`), never the composite key, so Quick Launch still has to ask the YubiKey and no response is ever persisted. `DatabaseListStore.setHardwareKey` deletes both the biometric and the Apple Watch item whenever the hardware key is turned on or off, because the item's meaning changes; the AutoFill coordinator never offers biometrics for such a database.
- Access-group ordering invariant: `KeychainService` never sets `kSecAttrAccessGroup`, so its items land in the FIRST keychain access group listed in the calling target's entitlements. App/extension sharing therefore depends on `com.keevault.sharedkeychain` staying first in every entitlements file — ahead of `com.microsoft.adalcache` in the iOS app, the only target that currently lists a second group. Reordering any `keychain-access-groups` array strands the shared composite keys, so the invariant holds for the Mac entitlements too even though they list one group today. Also noted in comments in `../../../AutoFillExtension/AutoFillExtensionMac.entitlements` and `../../../KeeForgeMac/KeeForgeMac.entitlements`.
