# App

**Scope:** app startup, scene phase, the iOS adaptive root shell that connects the database list to one active session, the SwiftUI pieces the Mac database windows host, and shared SwiftUI presentation. Compiled into `KeeForge` and `KeeForgeMac`, not the AutoFill targets.

## Ownership

Keep scene and platform adapters here and lifecycle decisions in the owning view model or service. Do not hide an app-wide state transition inside a view.

- `KeeForgeApp` owns the iOS lifecycle and its `DatabaseSessionStore`, `DatabaseListViewModel`, and `AppRoutingCoordinator`; `AppRootView` is the iOS shell only. On Mac, `../../KeeForgeMac/App/AppDelegate` owns the session store, list and app services, and `MacWindowCoordinator` owns the Databases window and one `DatabaseWindowController` per open database, keyed by database UUID (`../../KeeForgeMac/README.md`). Each database window holds its session directly; no Mac code reads or writes `activeSession`/`activeSessionID`.
- The app owner (`KeeForgeApp` on iOS, `AppDelegate` on Mac) installs database-list reconciliation, forced retirement, and AutoFill enablement refresh hooks when it constructs the shared models; these hooks never depend on a mounted root.
- On iOS, launch order, incoming-URL classification, and Open/Close Database transitions are decided by `AppRoutingCoordinator`, which owns a `TOTPEnrollmentCoordinator` for link parsing, destination binding, expiry, and enrollment presentation (see `../ViewModels/AGENTS.md`). `AppRootView` only adapts the result to SwiftUI presentation. On Mac, `MacWindowCoordinator` applies `MacApplicationRouting` (launch presentations before any open, queued URL and Quick Launch opens, duplicate fronting, Dock reopen) and owns one app-level `TOTPEnrollmentCoordinator`, bound to the database window targeted when a link arrives or to the database chosen in the Databases window.
- Auto-unlock is attempted in one place per platform: `.biometricAutoUnlock(_:)` on the iOS scene shells, and `MacBiometricAutoUnlockObserver` hosted once per database window by `MacDatabaseRootView` on macOS. Eligibility is `DatabaseViewModel.isEligibleForBiometricAutoUnlock`.
- Compact navigation and the group list compile only on iOS; the shared saving overlay and group/entry sheet content remain available on both platforms.
- `RegularDatabaseWorkspaceView` and `RegularDatabaseScene` own the iPad workspace and compile only on iOS. On Mac, `MacDatabaseRootView` (`../../KeeForgeMac/App/`) switches one session's states and embeds `MacDatabaseWorkspaceView`, which embeds the window-owned `MacWorkspaceSplitViewController` through a representable. Its sidebar and entries items are the AppKit `MacSidebarViewController` and `MacEntryListViewController` (`../../KeeForgeMac/App/`); the detail item hosts one SwiftUI column. While the split is shown the window's toolbar is the native `MacWorkspaceToolbar` (`../../KeeForgeMac/App/`), and the root host stops bridging SwiftUI toolbars; the unlock screen keeps the root's bridged toolbar. Column hosts never bridge. The toolbar's Edit goes through the shared presentation object.
- `MacWorkspacePresentationHost` wraps the native split representable once and owns the workspace sheets, confirmation, alerts, saving overlay, and command request observers. Its identity must stay outside column revision keys and selection branches. The detail column takes only the database and presentation object and shows the banners at its top. The split representable ignores the top safe area so the columns run under the titlebar and inset from their own safe areas; the host must add no top inset of its own.
- The Mac `MainMenu` builds the AppKit menu. Nil-target actions reach `AppDelegate` for app actions and a `DatabaseWindowController` for database actions. `MacDatabaseCommandTargetResolver` picks that controller for validation and again at dispatch: the key database window or a key sheet's parent, else the main database window while Settings or a panel is key, and none while the Databases window is key; `AppDelegate.supplementalTarget` and each controller's `isCommandTarget` gate both use it. New Database, Open Database and Connect to Server are launcher operations that ignore session state. `DatabaseCommands` owns enablement and actions; presentation commands only raise workspace request counters. Find is a window concern: the controller focuses its toolbar's search field directly.
- `MacLockMonitor` owns app-wide lock triggers on macOS; `MacWindowCloseGuard` settles each registered window's unsaved work and locks only its session on committed close (`../Services/AppSupport/`). `AppDelegate` owns `MacDatabaseWindowRegistry`; the coordinator registers each database window once before showing it and unregisters it on committed close, which also retires that session and releases the controller.

## Invariants

### Scene phase and locking

- Backgrounding always shows the capture shield. On iOS it locks only when `SettingsService.lockOnBackground` is on; otherwise the `autoLockTimeout` check runs on the next activation.
- The scene-phase `.background` lock path is iOS-only; `MacLockMonitor` applies the Mac policy, where minimize and hide do not lock.
- Scene activation, iOS backgrounding, Mac system lock callbacks, and iOS foreground activity forward through `DatabaseSessionStore` to every stored session. Mac window activity resets only the registered database session; Mac activation evaluates existing deadlines without renewal. The app supplies that store to all Settings entry points through the environment; per-database AutoFill refresh looks up the toggled database's session by ID.
- iOS observes touches across the main window (including sheets) and text-field/text-view edits through `IOSUserActivityObserver`. Only foreground activity resets the inactivity timer; its passive recognizer must never delay, cancel, or prevent normal controls and scrolling.
- On the compact shell only a manual lock calls `VaultCloseTransition.coverCurrentFrame()`, immediately before the closing state change. An automatic lock can coincide with backgrounding, and a snapshot added then is what iOS would capture for the app switcher.
- Pending AutoFill uploads drain on foreground activation (iOS scene phase, and `MacLockMonitor.onDidBecomeActive` on macOS) and on the extension's Darwin notification. Both go through `DatabaseListViewModel.drainPendingUploadsOnAppActive()`.
- A change to background/foreground behaviour needs checking in both shells together with AutoFill cache refresh and pending-upload drain timing.

### Launch and presentation

- Open cloud databases keep Sync Now below the iPad sidebar title and in the Mac database toolbar. On iPhone only a status badge sits beside the root title and scrolls away with it (a spinner while syncing, a warning whose popover offers Sync Now), and pulling a cloud list down syncs on every iOS layout. Skipped-check, last-sync, pending-upload, and result text lives in its status popover; choosing a future sync policy never claims the current open skipped a check. Sync enablement comes from `DatabaseViewModel.canSyncCloudNow`.
- Unlock, unlocking, and unlocked are one selected-database flow. Compact presents unlock as a sheet over the list and swaps to the session once unlocked; regular renders all three states inline in the detail column.
- Incoming Mac URLs queue in `MacWindowCoordinator` until startup, and database opens queue in `MacApplicationRouting` until the launch presentations are dismissed. The transition notice and What's New are presented once per launch from the Databases window; the notice suppresses What's New and Quick Launch for that launch.
- Quick Launch waits until the What's New sheet (and the Mac transition notice) is dismissed, so two launch presentations never compete.
- Mac window restoration runs once, after the launch presentations and before queued or Quick Launch opens (`MacApplicationRouting.Effect.restoreWindows`). It recreates windows only with new locked sessions, registered as restoring so `admitsAutomaticUnlock` refuses until the user clicks or types in the window (`MacLockMonitor.onUserActivity`) or opens that database explicitly; becoming key during launch does not count. Restoration takes precedence over Quick Launch, and a launch URL for a restored database fronts its window. `MacWindowCoordinator` is the only writer of the topology and of top-level frames, and records nothing until restoration has run.
- Mac quit settles each database window's unsaved write before termination (`MacWindowCoordinator.requestTermination`): every answer is collected before anything is written, and any cancel, failed save or editor holding fields cancels the quit with every session untouched. Only a quit that proceeds records the pre-quit topology and freezes the record.
- SwiftUI drops a presentation raised while another sheet is dismissing. That is why deferred presentations wait 450 ms and why the conflicted-upload notice is a banner, not an alert: it is due at unlock, while the compact unlock sheet is dismissing.
- The iOS Settings sheet is attached above the root so it survives the lock/unlock root swap. It exists for the iPad app running on a Mac, where the sidebar gear is hidden and the system Settings item opens a compatibility window.
- On iOS, session-provider closures capture the reference-type session store and read `activeSession` when invoked. The iOS app keeps at most one session: replacement retires the locked source before opening the destination; creation, returning to the list, and list removal force retirement at the point the session is dropped. On Mac, list removal force-retires the session and the coordinator closes its window.
- The database window's minimum height (620) and the Databases window's content size (600 x 620) must stay clear of `MacSheetMetrics.maxHeight` (560, `../Extensions/PlatformCompat.swift`): a sheet is anchored under the toolbar. Raise them together.

### Auto-unlock

- On iOS, one attempt per `lockCycleID`, and only while `scenePhase == .active`: LocalAuthentication fails with `LAError.notInteractive` for a caller that is not foreground-active, which would burn the cycle's attempt on an error screen.
- An attempt that returns `.promptUnavailable` showed no UI and gives its lock cycle back.
- The attempt is claimed on `DatabaseViewModel` (`claimBiometricAutoUnlockAttempt`), not in view state. The scenes show the opening screen for a locked database only while `isAwaitingBiometricAutoUnlock`, so a cancelled or failed prompt hands the screen to the unlock form instead of leaving a spinner up.
- On Mac, attempt only when the session mounts in a foreground key window or that window/app returns to the foreground, including a screen unlock or session switch back while KeeForge stays active (`MacBiometricAutoUnlockController.startObserving`). Never trigger from a lock-cycle change. Defer past activation observers and recheck eligibility, window visibility, attached sheets, and the captured lock cycle before prompting. Cancellation or fallback consumes the cycle; the password form stays available. Automatic attempts share one app-wide gate and require the registered window to resolve to the observer's session, with restoration suppressed. Pending work is invalidated on unmount.
- The Mac observer lives above the locked/unlocked view switch, keyed by session. Mounting it counts as opening, so placing it inside a view that a lock replaces would prompt on every automatic lock while the window is frontmost.
- `BiometricAutoUnlockPolicy` disables auto-unlock for the iOS build running on Mac or Vision Pro, because `active` does not prove the compatibility window is frontmost. Those keep the explicit biometric action in `UnlockView`.

### Layout changes (iPhone Duo, iPad resizing)

- Opening or closing an iPhone Duo, and resizing an iPad window, flips the size class and rebuilds every view under the root. `AppRootView` applies the new layout one update behind the size class, after `DatabaseWorkspaceState.adaptNavigation(toRegularLayout:)` has carried the place across, and passes its applied size class down so no view sees the next layout early.
- Anything that must survive the switch lives on `DatabaseWorkspaceState`, never in a shell's `@State`: the navigation path (compact stack or regular sidebar), the selected entry, search, selection mode, and the open editor (`openEditor`). Both shells present `openEditor`: compact pushes it as the path's `.editor` route, regular hosts it in the detail column and keeps `.editor` and entries out of its sidebar path. Never present the compact editor with `navigationDestination(item:)` at the stack's root: popping it replaces the path, dropping the user back to the vault root.
- A layout switch is not a scene-phase change. It never locks or shows the capture shield unless iOS also backgrounds the app.
- `-ui-testing-layout-switch` shows a control that switches layouts in-app; no simulator can open or close a Duo from a test (`../../KeeForgeUITests/AGENTS.md`).

### macOS workspace lists

- Native split items own widths and collapse state through `NSSplitView` autosave, one name per database (`MacWindowRestorationStore.splitViewAutosaveName(for:)`). Never retain database contents to preserve layout; release the controller on lock or replacement.
- `DatabaseWindowController` observes its session's unlocked state, database title, and group/tag/collection/search subtitle using `MacObservation`. `MacWindowWorkspace` owns the native controller and toolbar for that unlocked lifetime; the window controller swaps the toolbar in and turns root toolbar bridging off together, and reverses both on lock, so one source owns the bar in each state. The root hosting controller remains mounted across swaps to preserve enrollment sheets and the biometric observer; only its unlocked content embeds the split. Never make the window key or change first responder during a content update.
- `MacObservation` tracks reads separately from effects, re-arms on the main actor after mutation, and invalidates queued callbacks on cancellation/replacement. Capture owners weakly in its read/effect closures. The SwiftUI detail host observes saving disablement and appearance itself because SwiftUI environments do not cross a representable into independent hosting roots. The AppKit sidebar and entry list disable their views while saving and inherit the window's appearance, which the root host's `preferredColorScheme` sets.
- The sidebar is a source-list `NSOutlineView` and the entries column a view-based inset `NSTableView`, so arrow keys, type-select, extended selection, and the focus ring come from AppKit. Each row's identifier sits on its title text, because XCUITest drops a table cell's own identifier; Mac UI tests match rows with `descendants(matching: .any)` (`../Views/AGENTS.md`, `../../KeeForgeMacUITests/AGENTS.md`).
- The entry list renders `MacEntryListSnapshot` (`../ViewModels/MacEntryListModel.swift`) through one `MacObservation`. Edits, renames, creation, deletion and resorting remove, move and insert rows in place and reconfigure existing cells, so row views, selection and scroll survive; only switching to another list (a group, tag or collection, or into or out of search) reloads the table. Usernames are resolved when a cell is configured, so rows never drawn never resolve field references.
- Entry selection maps both ways through `MacEntryListSelection`: one row is `selectedEntryID`; two or more are `entrySelection` (movable rows only, one row in a read-only database), and a Command or Shift extension keeps picks the current list does not show. Escape and the selection bar's Cancel end it. Return, Enter and double-click open the entry through `requestEntryEdit()`; bare Delete, Space and ⌘C do nothing.
- Verification Codes rows show the live code from `MacVerificationCodeClock`. The table owns one timer, running only while that list is showing, the view has appeared and the session is unlocked; a tick redraws visible rows only, and every stop resets the clock's cache. The copy button goes through `DatabaseCommands.copyVerificationCode(entryID:)` only.
- The entry row menu comes from `EntryRowActions` (bulk: Move to Group only). Its Copy Password goes through `DatabaseCommands.copyPassword(entryID:currentSession:)` with the window controller's `isCurrent` recheck; username copies through `DatabaseCommands.copyUsername(entryID:currentSession:)`, which takes the same gate when the username's references reach a protected value. Row-menu selectors must not reuse a main-menu command's selector, or the table's controller intercepts the menu-bar command. A duplicate made from search or a tag selects the copy in place (`MacWorkspacePresentation.selectsCreatedEntryInPlace`); elsewhere the host reveals it.
- Mac sidebar navigation is selection on `DatabaseViewModel.workspace`, never a pushed stack. `GroupListView` never renders on macOS.
- Sheets, the Move picker, and the delete confirmation raised by a row belong to the stable outer `MacWorkspacePresentationHost`, never a row or column. The presentation object belongs to its `DatabaseWindowController` and resets when the workspace disappears (sidebar expansion excepted), releasing forms and invalidating old cloud-reconnect completions across lock or session replacement.
- The delete confirmation is a `confirmationDialog`, not a second `.alert(item:)`: two sibling `.alert(item:)` on one view chain collide and SwiftUI silently drops one. The sidebar and entry list menus raise their deletion to this host.
- Database-scoped toolbar items are navigational `NSToolbarItem`s, ahead of the title. At the trailing edge they would sit beside the entry's Edit button, where they read as actions on the selected entry.
- `MacWorkspaceToolbar` item identifiers are the accessibility identifiers the UI tests query; each item's view carries the same identifier. The search item and `DatabaseViewModel.searchText` are bound both ways; enablement comes from `DatabaseCommands` where a rule exists, and every item is disabled while saving.

### iPad workspace

- Successful New Entry completion selects the saved entry through `revealEntry` in both regular shells, including a changed destination group. Cancel, edit, and Save and Lock keep their existing selection behavior.
- Editors (New Entry, Duplicate, Edit Group, Edit Entry) are hosted in the detail column, not pushed into the narrow sidebar. An open editor keeps its unsaved work: later requests are ignored while one is up.
- iPad mini in portrait starts with the sidebar collapsed behind the system "Show Sidebar" button. That is the platform's default visibility for a 744 pt regular window. An explicit `columnVisibility: .all` does open it side by side (iOS 18.6 and 27.0); the workspace passes no column visibility and keeps the platform default.

### Menu bar

- `SettingsWindowController` retains the Settings window (`settings`). It cannot become main, so database commands keep targeting the database window behind it, and it reads no window's session; the SSH Agent tab picks its database explicitly. Settings buttons send `showSettings:` through the responder chain. Mac activation notifications replace scene-phase reads for enrollment expiry and AutoFill status.

- The AppKit File menu includes Close Window (Cmd-W). The macOS lock guarantee and `MacWindowCloseGuard` assume that shortcut exists.
- Every item is disabled when it cannot apply (locked, read-only, no selection). Enablement for Edit and Delete comes from the same view-model properties the action uses.
- Copy Password goes through `EntrySecretAction` and revalidates after authentication that the originating window still owns the same session (the active session on iOS).

## Tests

- Persistent cloud sync controls, repeated syncs, policy changes, and warning state: `DatabaseViewModelCloudSyncTests`. The status popover workflow is covered by `CloudUnlockSmokeUITests` and `MacWebDAVSmokeUITests`.
- Mac automatic prompts, their trigger notifications, and queued-event invalidation: `MacBiometricAutoUnlockTests`.
- Single-session routing and launch integration: `AppRoutingCoordinatorTests`. Enrollment lifetime, destination validation and deferred presentation: `TOTPEnrollmentCoordinatorTests`. Mac application policy: `MacApplicationRoutingTests`; its window effects, opening, duplicate fronting, committed and cancelled close, session-retirement closes, command targeting, enrollment binding, restoration (locked, restoring until focused, precedence, launch URLs, missing databases), topology recording, list-removal cleanup and quit settling: `MacWindowCoordinatorTests`; one controller per session, independence through unlock/lock/error/edit/title, guarded close, no frame autosave or AppKit restoration, the initial size, and the unlock screen's layout and bridged toolbar across an unlock: `DatabaseWindowControllerTests`; target resolution: `MacDatabaseCommandTargetResolverTests`; Databases window decisions and provider filtering: `MacDatabasesLauncherViewModelTests`. AppKit menu titles, shortcuts, selectors, owners, and launcher-command validation: `MacMainMenuTests`. Database menu rules and requests: `DatabaseCommandsTests`; password copy: `EntrySecretActionTests`. Lock triggers: `MacLockMonitorTests`, `MacWindowCloseGuardTests`, `AutoLockTests`. Multi-session event delivery, reference reconciliation, view-independent list retirement and targeted activity: `DatabaseSessionStoreTests`; list mutations and AutoFill refresh wiring: `DatabaseListViewModelTests`; Settings effects: `AppSettingsViewModelTests`. iOS window activity forwarding: `IOSUserActivityTests`; real editor typing, scrolling, button taps, and subsequent idle locking: `AutoLockActivityUITests`.
- The entry table (rows, in-place row updates, selection both ways, Return and double-click, Escape, menus and their gates, password copy, cells, offscreen resolution, empty states, saving, code rows and their timer): `MacEntryListViewControllerTests`. Real arrow keys and clicks need the UI suite: `MacSmokeUITests` (the `testDownArrow…` and double-click cases) and `MacListKeyboardNavigationUITests`.
- Sidebar rows, custom-icon data and recycle-bin icon projection: `MacSidebarSnapshotTests`; the outline itself: `MacSidebarViewControllerTests`. The window appearance the sidebar inherits: `DatabaseWindowControllerTests`.
- Presentation targets, open-editor preservation, where a created duplicate lands, deletion snapshots, new-group form resets, window isolation, and cloud-reconnect lifetime: `MacWorkspacePresentationTests`.
- Observation delivery, re-arming, cancellation, replacement and owner lifetime: `MacObservationTests`. Native item constraints, the AppKit sidebar item and its status card, the AppKit entry list item, sidebar collapse, the split running under the titlebar with column safe-area insets, and controller replacement/release: `MacWorkspaceSplitViewControllerTests`. Divider restoration across repeated lock/unlock cycles: `MacSmokeUITests.testSidebarWidthSurvivesRepeatedLockUnlockCycles`; native split-view layout requires the UI test.
- Root navigation changes ripple into `DatabaseListView`, `UnlockView`, and both UI suites; rerun the smallest affected class from `../../KeeForgeUITests/AGENTS.md`.
