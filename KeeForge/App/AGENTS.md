# App Folder

This folder owns app startup, scene transitions, and the adaptive root shell that connects the database list to one active database session.

## Main Files

- `KeeForgeApp.swift` creates the shared `DatabaseListViewModel` and `AppRoutingCoordinator`, owns the optional active `DatabaseViewModel`, chooses the compact vs regular-width root layout, and wires global scene-phase behavior. It reads the persisted appearance mode and optional app accent color with `@AppStorage`, applying both to the main window and the macOS Settings scene so changes take effect immediately. One `#if DEBUG` launch-argument hook (developer tooling, no Release effect): in `rootView`, `-autofill-store-inspector` replaces the normal root with `../Views/Settings/AutoFillStoreInspectorView.swift`. It presents the cross-platform What's New sheet before any Quick Launch unlock sheet and resumes the pending database route after dismissal. On iOS it owns the app-level Settings sheet (`appSettingsPresentation`, presenting `SettingsView` above the root so it survives the lock/unlock root swap) and attaches `AppSettingsCommands`. On macOS it additionally declares the `Settings { }` scene (⌘,), sets the window `defaultSize`/min frame, publishes the active session via `.focusedSceneValue(\.databaseViewModel, ...)`, attaches `KeeForgeCommands`, and starts `MacLockMonitor` — the sole lock driver on macOS (the scene-phase `.background` lock path is iOS-only because macOS backgrounds scenes on window minimize/app hide) — alongside `MacWindowCloseGuard`, which settles unsaved work before a window close commits and is handed the active session the same way, and `MacQuickAccessController` (menu bar quick search), which gets the same live session binding and is put in the environment of the main window and the Settings scene. On macOS the `WindowGroup` has the id `KeeForgeApp.mainWindowID` so the file-private `MacQuickAccessMainWindowHookup` can hand the controller `openWindow` for reopening the window after ⌘W, plus a `MacWindowReader` for fronting the existing one. Besides the `App` type, the file declares the cross-file views `DatabaseNavigationView`, `DatabaseSavingOverlay`, `UnsavedChangesBanner`, `CloudReauthBanner`, `CloudSyncStatusBanner`, `PendingUploadConflictBanner` (the "Merge Changes" notice for a conflicted AutoFill upload, #149; a banner because an alert due at unlock collides with the dismissing compact unlock sheet), and `CloudSyncWarningButton` (used by `RegularDatabaseWorkspaceView.swift`). `CloudSyncStatusBanner` (`database.cloud-sync-status`, `database.cloud-sync-now`, `database.cloud-sync-status.dismiss`) sits in both shells' top inset beside `UnsavedChangesBanner`: it reports a refresh the manual sync policy skipped on open, a Sync Now in progress, or what the last one found, and is deliberately separate from the yellow `CloudSyncWarningButton`, which stays reserved for failures, plus the file-private scene shells `AppRootView`, `CompactDatabaseHost`, `CompactUnlockScene`, `RegularDatabaseScene`, and `LaunchRoutingView`. Targets: KeeForge and KeeForgeMac, not the AutoFill targets.
- `VaultCloseTransition.swift` (iOS only) snapshots the window so the compact vault→list swap can fade; call `coverCurrentFrame()` immediately before the closing state change — see the file header for why.
- `AppSettingsCommands.swift` (iOS only, `#if os(iOS)`) is the Settings entry point that stays reachable when the iPad app runs on a Mac (#69), where the sidebar gear is hidden and the system "Settings…" item opens a compatibility window. It declares the observable `AppSettingsPresentation` (installed by `KeeForgeApp` in the environment and used to present the app-owned sheet), `AppSettingsCommands` (replaces `.appSettings` with a "Settings…" ⌘, item), and `.appSettingsToolbarButton()`, a gear (`app.settings.button`) that renders only when `ProcessInfo.processInfo.isiOSAppOnMac`; the regular layout applies it to the detail column both locked (`AppRootView.rootContent`) and unlocked (`RegularDatabaseWorkspaceView.selectionDetail`). iPhone and iPad behavior is unchanged apart from ⌘, on a hardware keyboard.
- `KeeForgeCommands.swift` (KeeForgeMac target only; excluded from the iOS target in `project.yml`) owns the macOS menu bar: About KeeForge (`CommandGroup(replacing: .appInfo)`, the standard AppKit About panel — the `#if KEEFORGE_DIRECT_DOWNLOAD` Check for Updates group in `KeeForgeApp.swift` still installs after it), New Entry ⌘N, New Group ⇧⌘N, Open Database… ⌘O, Close Window ⌘W, Save ⌘S, Close Database ⇧⌘W, Copy Username ⇧⌘B / Password ⇧⌘C (device-owner auth gated) / URL ⇧⌘U / Verification Code ⇧⌘T, Edit Entry ⌘E, Delete ⌘⌫, Find ⌘F, Lock ⌘L, and a Help menu (`CommandGroup(replacing: .help)`; without it macOS ships a dead "KeeForge Help" item). Every item is disabled when it cannot apply — locked, read-only, no selection. Password copy uses `EntrySecretAction` and revalidates the active session, selection/navigation, lock cycle, and draft revision after authentication; headless command coverage lives in `EntrySecretActionTests`. Commands reach the active `DatabaseViewModel` through `FocusedValues` — the one FocusedValues plumbing pattern in the codebase. Four of them need a presentation only the workspace can host, so they go through counter signals on `DatabaseViewModel.workspace` (`newEntryRequestID`, `newGroupRequestID`, `editEntryRequestID`, `deleteSelectionRequestID`) rather than reaching into views; Delete therefore raises the *shared* `PendingDeletion` confirmation from `../Views/Entry/PendingRowActions.swift` and never deletes directly. Which item Delete and Edit Entry act on comes from `DatabaseViewModel.deletableSelection` / `canEditSelectedEntry`, so the menu's enablement and the workspace's action can't drift. ⌘O runs its own `NSOpenPanel` and reports failures with an `NSAlert`: the `.fileImporter` that adds a database lives in `../Views/DatabaseList/DatabaseListView.swift`, which is off screen while a vault is open, and a menu command has no SwiftUI host to raise an alert on. Close Window is there because `CommandGroup(replacing: .saveItem)` replaces the group the standard File ▸ Close sits in, which silently removed ⌘W — the shortcut the macOS lock guarantee assumes exists (`../Services/AppSupport/MacWindowCloseGuard.swift`).
- `RegularDatabaseWorkspaceView.swift` owns the regular-width unlocked workspace. iOS/iPadOS keeps the two-column split view (`sidebarColumn` is a `NavigationStack` pushing `GroupListView`; entry detail in the detail column). Editors raised from the sidebar — New Entry from the + menu, Edit Group from a row's context menu — are handed up through `GroupListView`'s `onCreateEntry` / `onEditGroup` closures and hosted in the detail column (`detailEditor`, `hostedEditor`) rather than pushed into the 320–440pt sidebar; a hosted editor keeps its unsaved work until it completes (later + / Edit Group requests are ignored while one is up, and lock/close clears it with the rest of the workspace state). Note that iPad mini in portrait (744pt) collapses both split views' sidebars behind the system "Show Sidebar" button — the platform's automatic display mode for a sub-768pt regular window (Files, Notes, and Mail do the same there); neither column widths nor `columnVisibility: .all` tile it, so the shells leave the system default alone. macOS uses a dedicated three-column `macSplitView` (`#if os(macOS)`): a sidebar group tree (`MacGroupTreeRow`, a recursive `DisclosureGroup`/`.listStyle(.sidebar)` view whose rows carry `group.navlink`), a content column of entry rows (`entry.navlink`) or `SearchView` when searching, and the entry-detail column. Selection is driven by `DatabaseViewModel.workspace.selectedGroupID`/`selectedEntryID` — no pushed sidebar stacks; those render zero-height on macOS. Both columns are native `List(selection:)`, so arrow keys, type-select, and the focus ring come from AppKit instead of being hand-rolled; rows are therefore plain content, **not** buttons (a `Button` swallows the click the list needs). The sidebar's one selection value is `MacSidebarSelection` (`.group(UUID)` / `.tag(String)`), bridged onto the view model's two mutually exclusive selections by a computed `Binding` that ignores a `nil` write — clicking the list's empty area must not leave the workspace with nothing selected. The entries column binds straight to `selectedEntryID`.

  **Any tap gesture on a row consumes the click the list would have used**, `simultaneousGesture` included (verified against the live app: a `.tag`-carrying sidebar row with a double-click handler stopped selecting at all). So: sidebar rows carry no tap gesture — their disclosure triangle is the way to fold a group, and a double-click-to-toggle affordance was dropped rather than break navigation. The sidebar selection binding still drives a `@FocusState` bound to the list because macOS 27 can update selection from an accessibility click without making the list first responder. The entries column does want double-click-to-open, so it pays the full price: the row handles `count: 2` (open the editor) *and* `count: 1` (set `selectedEntryID`), and the single-click handler also drives a `@FocusState` bound to the list because a consumed click never makes the list first responder and the arrow keys would otherwise go nowhere. Return opens the editor too, via `.onKeyPress(.return)` on the list. `MacSmokeUITests`' two `testDownArrow…` cases are what keep this wiring honest.

  Because the rows are no longer buttons, `KeeForgeMacUITests` matches them with `descendants(matching: .any)` rather than `app.buttons`, and on text that lands in the AppKit `value` attribute rather than `label` (`MacUITestCase.clickRow` / `rowQuery` / `displayText` / `waitForDisplayText`). `SearchView` and `TagEntriesView` render `MacEntriesList` (`../Views/Entry/MacEntriesList.swift`) on macOS instead of the shared iOS `EntryListView`, whose button rows swallow the click the list needs, so keyboard navigation now covers search results and tag results as well as a group's entries. All three columns share `MacEntryRow`. Window title is the database name (`.navigationTitle`) with the group name as `.navigationSubtitle`. The Mac toolbar uses explicit `ToolbarItem` placements plus `.searchable`, sized so nothing overflows at the 900pt minimum width. Everything database-scoped (lock, add-menu, sort, database details, settings) is placed `.navigation`, so it sits over the group and entry columns; `.primaryAction` would park it at the trailing edge beside `EntryDetailView`'s own Edit button, reading as actions on the selected entry. It services the menu-bar/toolbar New Entry request (`DatabaseViewModel.workspace.newEntryRequestID` / `requestNewEntry()`) via a single shared entry-editor sheet targeting `selectedGroupID ?? visibleRootGroupID`, and presents `NewGroupSheet` (from `../Views/Group/GroupListView.swift`) for group creation. On macOS the sidebar and `MacEntriesColumn` are keyed with `.id(viewModel.contentRevision)` to force rebuilds — the three-column `NavigationSplitView` caches those columns on macOS and would otherwise keep stale rows after draft edits; sidebar expansion state (`macCollapsedGroupIDs`, view-local `@State`) and selection live outside the rebuilt subtree and survive it. Targets: KeeForge and KeeForgeMac, not the AutoFill targets.

## What Lives Here

- App launch routing: auto-open on launch only when the list holds exactly one database and it is marked Quick Launch (`DatabaseListViewModel.databaseToAutoOpenOnLaunch`).
- Launch and incoming URL decisions live in `../ViewModels/AppRoutingCoordinator.swift`; `AppRootView` adapts them to SwiftUI. Mac Open/Close Database commands and incoming database URLs share its pending database transition. A destination stays tied to the source session identity and lock cycle until the ordinary lock request finishes: dirty editors show their existing Save/Discard/Keep Editing prompt, failed writes defer to the draft prompt, and Keep Editing cancels the destination. The root observes lock completion and cancellation and applies the destination only after the source locks; opening the already active database leaves its editor intact. Menu Open chooses the file first so resolving unsaved work can resume the selected destination. Cloud OAuth callbacks go to `CloudProviderRegistry.handleOpenURL` first, then the coordinator classifies `otpauth://` and database URLs. The app supplies initial launch inputs (transition notice, What's New, Quick Launch), opens the returned database, and resumes parked enrollment after launch presentation ends. The coordinator parks a link while locked or while launch education is showing, preserves its original five-minute expiry through lock/unlock, and revalidates the session when promoting it. The app executes the coordinator's deferred presentation token in a cancellable `.task(id:)` with a 450ms dismissal delay; the coordinator rejects superseded requests. Enrollment appearance, completion, and cancellation carry the enrollment ID plus session identity and lock cycle, so callbacks from a replaced sheet cannot clear a newer link. Scene changes ask the coordinator to expire pending links. Keep presentation mechanics here and routing/expiry policy in the coordinator; test the latter in `AppRoutingCoordinatorTests`.

- Scene protection: backgrounding always shows the capture shield but locks the active database only when `SettingsService.lockOnBackground` is on; otherwise the lock decision defers to the `autoLockTimeout` check on the next activation (`DatabaseViewModel.handleSceneDidEnterBackground` / `handleSceneDidBecomeActive`).
- Root/session presentation: unlock, unlocking, and unlocked states are one selected-database flow, not a modal lifecycle. Compact presents unlock/unlocking as a sheet (`CompactUnlockScene`) over the list, then swaps to a full-screen session once unlocked; regular-width keeps the list visible in a split view and renders all three states inline without a sheet, handing the whole window to `RegularDatabaseWorkspaceView` once unlocked.
- Auto-unlock orchestration: `BiometricAutoUnlockModifier` (`.biometricAutoUnlock(_:)`) is the single owner for both scene shells. Eligibility lives on `DatabaseViewModel.isEligibleForBiometricAutoUnlock`, which folds in `BiometricAutoUnlockPolicy` (same file): iOS builds in compatibility mode on Mac or Vision Pro never auto-unlock, because `active` does not prove the compatibility window is frontmost — those platforms keep the explicit biometric action in `UnlockView`. `lockCycleID` prevents repeated biometric retries for the same lock cycle, and the attempt additionally requires `scenePhase == .active`, because LocalAuthentication fails with `LAError.notInteractive` when the caller is not foreground-active. An attempt that reports `.promptUnavailable` never showed UI and so gives its lock cycle back.
- Pending upload draining: foreground activation and the AutoFill Darwin notification both trigger `PendingUploadDrainer` so queued cloud saves from the extension are pushed as soon as the app can do it.
- Version education: `WhatsNewPresentationService` claims each marketing version once, while `WhatsNewView` presents only curated feature content supported by the current platform. Quick Launch waits until that sheet closes so the two presentations never compete.

## Change Carefully

- Root navigation changes here usually ripple into `../Views/DatabaseList/DatabaseListView.swift`, `../Views/Unlock/UnlockView.swift`, `RegularDatabaseWorkspaceView.swift`, `../../KeeForgeUITests/README.md`, and `../../KeeForgeMacUITests/` (its tests drive `macSplitView` via the `group.navlink` / `entry.navlink` identifiers).
- Keep scene and platform adapters here, with lifecycle decisions in the relevant services/view models; do not hide app-wide state transitions inside individual views.
- If the app should behave differently on background/foreground, verify both compact and regular-width unlocked flows, AutoFill cache refresh behavior, and pending-upload drain timing together.
