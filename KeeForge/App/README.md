# App Folder

This folder owns app startup, scene transitions, and the adaptive root shell that connects the database list to one active database session.

## Main Files

- `KeeForgeApp.swift` creates the shared `DatabaseListViewModel`, owns the optional active `DatabaseViewModel`, chooses the compact vs regular-width root layout, and wires global scene-phase behavior. One `#if DEBUG` launch-argument hook (developer tooling, no Release effect): in `rootView`, `-autofill-store-inspector` replaces the normal root with `../Views/AutoFillStoreInspectorView.swift`. It presents the cross-platform What's New sheet before any Quick Launch unlock sheet and resumes the pending database route after dismissal. On iOS it owns the app-level Settings sheet (`isShowingAppSettings`, presenting `SettingsView` above the root so it survives the lock/unlock root swap) and attaches `AppSettingsCommands`. On macOS it additionally declares the `Settings { }` scene (⌘,), sets the window `defaultSize`/min frame, publishes the active session via `.focusedSceneValue(\.databaseViewModel, ...)`, attaches `KeeForgeCommands`, and starts `MacLockMonitor` — the sole lock driver on macOS (the scene-phase `.background` lock path is iOS-only because macOS backgrounds scenes on window minimize/app hide). Besides the `App` type, the file declares the cross-file views `DatabaseNavigationView`, `DatabaseSavingOverlay`, `UnsavedChangesBanner`, `CloudReauthBanner`, and `CloudSyncWarningButton` (used by `RegularDatabaseWorkspaceView.swift`), plus the file-private scene shells `AppRootView`, `CompactDatabaseHost`, `CompactUnlockScene`, `RegularDatabaseScene`, and `LaunchRoutingView`. Targets: KeeForge and KeeForgeMac, not the AutoFill targets.
- `VaultCloseTransition.swift` (iOS only) snapshots the window so the compact vault→list swap can fade; call `coverCurrentFrame()` immediately before the closing state change — see the file header for why.
- `AppSettingsCommands.swift` (iOS only, `#if os(iOS)`) is the Settings entry point that stays reachable when the iPad app runs on a Mac (#69), where the sidebar gear is hidden and the system "Settings…" item opens a compatibility window. It declares the `\.presentAppSettings` environment action (installed by `KeeForgeApp`, flips `isShowingAppSettings`), `AppSettingsCommands` (replaces `.appSettings` with a "Settings…" ⌘, item), and `.appSettingsToolbarButton()`, a gear (`app.settings.button`) that renders only when `ProcessInfo.processInfo.isiOSAppOnMac`; the regular layout applies it to the detail column both locked (`AppRootView.rootContent`) and unlocked (`RegularDatabaseWorkspaceView.selectionDetail`). iPhone and iPad behavior is unchanged apart from ⌘, on a hardware keyboard.
- `KeeForgeCommands.swift` (KeeForgeMac target only; excluded from the iOS target in `project.yml`) owns the macOS menu bar: New Entry ⌘N, Save ⌘S, Close Database ⇧⌘W, Copy Username ⇧⌘B, Copy Password ⇧⌘C (device-owner auth gated), Find ⌘F, Lock ⌘L. Commands reach the active `DatabaseViewModel` through `FocusedValues` — the one FocusedValues plumbing pattern in the codebase.
- `RegularDatabaseWorkspaceView.swift` owns the regular-width unlocked workspace. iOS/iPadOS keeps the two-column split view (`sidebarColumn` is a `NavigationStack` pushing `GroupListView`; entry detail in the detail column). Editors raised from the sidebar — New Entry from the + menu, Edit Group from a row's context menu — are handed up through `GroupListView`'s `onCreateEntry` / `onEditGroup` closures and hosted in the detail column (`detailEditor`, `hostedEditor`) rather than pushed into the 320–440pt sidebar; a hosted editor keeps its unsaved work until it completes (later + / Edit Group requests are ignored while one is up, and lock/close clears it with the rest of the workspace state). Note that iPad mini in portrait (744pt) collapses both split views' sidebars behind the system "Show Sidebar" button — the platform's automatic display mode for a sub-768pt regular window (Files, Notes, and Mail do the same there); neither column widths nor `columnVisibility: .all` tile it, so the shells leave the system default alone. macOS uses a dedicated three-column `macSplitView` (`#if os(macOS)`): a sidebar group tree (`MacGroupTreeRow`, a recursive `DisclosureGroup`/`.listStyle(.sidebar)` view whose rows are plain buttons carrying `group.navlink` with a manual selection highlight), a content column of entry rows (`entry.navlink`) or `SearchView` when searching, and the entry-detail column. Selection is driven by `DatabaseViewModel.selectedGroupID`/`selectedEntryID` — no pushed sidebar stacks; those render zero-height on macOS. Window title is the database name (`.navigationTitle`) with the group name as `.navigationSubtitle`. The Mac toolbar uses explicit `ToolbarItem` placements (lock, add-menu, sort, settings) plus `.searchable`, sized so nothing overflows at the 900pt minimum width. It services the menu-bar/toolbar New Entry request (`DatabaseViewModel.newEntryRequestID` / `requestNewEntry()`) via a single shared entry-editor sheet targeting `selectedGroupID ?? visibleRootGroupID`, and presents `NewGroupSheet` (from `../Views/GroupListView.swift`) for group creation. On macOS the sidebar and `MacEntriesColumn` are keyed with `.id(viewModel.contentRevision)` to force rebuilds — the three-column `NavigationSplitView` caches those columns on macOS and would otherwise keep stale rows after draft edits; sidebar expansion state (`macCollapsedGroupIDs`, view-local `@State`) and selection live outside the rebuilt subtree and survive it. Targets: KeeForge and KeeForgeMac, not the AutoFill targets.

## What Lives Here

- App launch routing: auto-open on launch only when the list holds exactly one database and it is marked Quick Launch (`DatabaseListViewModel.databaseToAutoOpenOnLaunch`).
- Incoming URL routing (`AppRootView.handleOpenURL`): cloud OAuth callbacks first (`CloudProviderRegistry.handleOpenURL`), then `otpauth://` links (`OTPAuthURI.isOTPAuthURL`; the scheme is declared in `../Info.plist`'s `CFBundleURLTypes` as "OTP Authentication", which is what makes iOS Settings offer KeeForge under "Set Up Codes In" — iOS app only, the Mac plist deliberately does not declare it), and finally kdbx file URLs to add/open. A parsed otpauth link presents `../Views/TOTPEnrollmentDestinationView.swift` as a root-level sheet immediately when the active session is unlocked; otherwise it parks in `pendingTOTPEnrollment` behind an "unlock a database" alert and is promoted to the sheet by the root `onChange` the moment a session reaches `.unlocked` (same deferred-deep-link pattern as `pendingAutoOpenReference`). Promotion goes through `promoteParkedTOTPEnrollment()`, which waits `enrollmentPresentationDelay` before presenting and leaves the parked copy in place until the sheet's own `onAppear` releases it: the same `.unlocked` transition dismisses `CompactDatabaseHost`'s unlock sheet, and a sheet raised into that dismissal is dropped by SwiftUI. Every enrollment alert raised from a dismissal (`finishWhatsNewPresentation`, expiry) goes through `requestTOTPEnrollmentAlert(_:)` for the same reason; `handleOpenURL`'s parse-failure alerts are raised directly because nothing is dismissing there. While the What's New sheet is up the enrollment always parks silently — `finishWhatsNewPresentation` promotes it (sheet if a session is unlocked, unlock-needed alert otherwise) so the two presentations never compete. A parked enrollment expires after 5 minutes (`PendingTOTPEnrollment.lifetime`); `discardExpiredTOTPEnrollment()` is the one place that drops an expired one — from the unlock promotion, the What's New hand-off, and scene-phase changes — and it always raises the link-expired alert, because after telling the user to unlock a database, silently having nothing happen reads as the app losing their code. If the session locks or closes mid-flow, the root `onChange` re-parks the presented enrollment (original creation date intact) instead of discarding it, so re-unlocking within the window resumes the flow; cancelling or completing the sheet clears everything. The sheet content is keyed (`.id`) on the enrollment id plus the active session's database-reference id, so a second otpauth link or a session swap rebuilds it rather than leaving a stale snapshot. Parse failures alert, distinguishing unsupported code types from invalid links.
- Scene protection: backgrounding always shows the capture shield but locks the active database only when `SettingsService.lockOnBackground` is on; otherwise the lock decision defers to the `autoLockTimeout` check on the next activation (`DatabaseViewModel.handleSceneDidEnterBackground` / `handleSceneDidBecomeActive`).
- Root/session presentation: unlock, unlocking, and unlocked states are one selected-database flow, not a modal lifecycle. Compact presents unlock/unlocking as a sheet (`CompactUnlockScene`) over the list, then swaps to a full-screen session once unlocked; regular-width keeps the list visible in a split view and renders all three states inline without a sheet, handing the whole window to `RegularDatabaseWorkspaceView` once unlocked.
- Auto-unlock orchestration: `BiometricAutoUnlockModifier` (`.biometricAutoUnlock(_:)`) is the single owner for both scene shells. Eligibility lives on `DatabaseViewModel.isEligibleForBiometricAutoUnlock`, which folds in `BiometricAutoUnlockPolicy` (same file): iOS builds in compatibility mode on Mac or Vision Pro never auto-unlock, because `active` does not prove the compatibility window is frontmost — those platforms keep the explicit biometric action in `UnlockView`. `lockCycleID` prevents repeated biometric retries for the same lock cycle, and the attempt additionally requires `scenePhase == .active`, because LocalAuthentication fails with `LAError.notInteractive` when the caller is not foreground-active. An attempt that reports `.promptUnavailable` never showed UI and so gives its lock cycle back.
- Pending upload draining: foreground activation and the AutoFill Darwin notification both trigger `PendingUploadDrainer` so queued cloud saves from the extension are pushed as soon as the app can do it.
- Version education: `WhatsNewPresentationService` claims each marketing version once, while `WhatsNewView` presents only curated feature content supported by the current platform. Quick Launch waits until that sheet closes so the two presentations never compete.

## Change Carefully

- Root navigation changes here usually ripple into `../Views/DatabaseListView.swift`, `../Views/UnlockView.swift`, `RegularDatabaseWorkspaceView.swift`, `../../KeeForgeUITests/README.md`, and `../../KeeForgeMacUITests/` (its tests drive `macSplitView` via the `group.navlink` / `entry.navlink` identifiers).
- Keep lifecycle policy here or in services/view models; do not hide app-wide state transitions inside individual views.
- If the app should behave differently on background/foreground, verify both compact and regular-width unlocked flows, AutoFill cache refresh behavior, and pending-upload drain timing together.
