# KeeForge Unit Tests

Use this folder to find the smallest test slice that proves a change. Prefer unit tests over UI tests unless the behavior is truly UI-driven.

## Running Tests

```bash
xcodebuild test -project KeeForge.xcodeproj -scheme KeeForge \
  -destination 'platform=iOS Simulator,name=iPhone 17 Pro' \
  -only-testing:KeeForgeTests/DatabaseViewModelTests -quiet
```

- Run only the classes touched by the change.
- `-only-testing:` takes test **class** names; the map below lists files, and the two sometimes differ: `PasskeyTests.swift` declares `PasskeyCredentialTests` and `PasskeyCryptoTests` (no `PasskeyTests` class).
- If source files move between targets, regenerate the project with `xcodegen generate`.

## KDBX Compatibility Story

- `KDBXRoundTripTests.swift` is for parser/XML serializer regressions only.
- `KDBXWriterTests.swift` is for encrypted container, header, HMAC, cipher, KDF, and protected-value regressions only.
- `DatabaseDraftTests.swift` is for in-memory edit semantics only, including history trimming by both `HistoryMaxItems` and `HistoryMaxSize` and the legacy `otp` URI preserve/invalidate contract.
- `CustomIconXMLTests.swift` covers the splice that adds an icon to the preserved `Meta/CustomIcons` fragment: an existing element keeps every byte ahead of its closing tag, the empty `<CustomIcons/>` form is opened without losing its start tag, and the element is created when the database has none. That the spliced result is *valid in a real file* is not provable here — the `add-entry-custom-icon` scenario in `KDBXCompatibilitySupport.swift` writes and re-parses an actual KDBX for that.
- `LocalDatabaseSaverTests.swift`, `CloudDatabaseSaverTests.swift`, and `CredentialProviderSaveTests.swift` are save-path safety tests with representative smoke edits. `LocalDatabaseSaverTests.swift` also re-opens the timestamped backup a save wrote and parses it with the original credentials, so backups are proven restorable rather than merely present. Both saver suites cover the rekey path (`newCompositeKey`): the saved/uploaded file must open with the new key and reject the old one, the pre-rekey backup keeps the old credentials, and a conflict or verification failure leaves the file untouched; the `changeMasterKey` guards, keychain-refresh seams, and conflict abort live in `DatabaseViewModelTests.swift`.
- `PendingUploadQueueTests.swift` owns the pending-upload marker schema decode-compatibility gate (legacy marker JSON without newer fields must keep decoding); `CloudSyncCoordinatorTests.swift` also covers pending-marker pre-overwrite backups and conflicted-marker discard resolution.
- `KDBXCompatibilityTests.swift` is the authoritative end-to-end compatibility matrix for every supported edit type and rich KDBX fixture shape.
- `KDBXMergerTests.swift` and `KDBXMergerOracleTests.swift` own merge *semantics*; the merge's write path is one compatibility scenario, `merge-remote-divergence`, which runs the engine over a divergent pair, writes the merged tree through a pristine draft (`Scenario.makeMergedTree`, the merge/rekey path — not an `EntryEdit`), reparses it, and emits the artifact so the external gate opens it with real KeePassXC.
- The compatibility matrix runs the full edit set for both AES and synthetic Twofish databases, and the artifact gate asks `keepassxc-cli` to open KeeForge-produced Twofish output.
- That proves KeeForge's ChaCha20/Twofish outer-cipher WRITE paths (KeeForge-authored input, external opener on the output). The `foreign-chacha20`/`foreign-twofish` smoke fixtures (see `../TestFixtures/README.md`) are what cover the READ side: a pykeepass-authored (not KeeForge-authored) ChaCha20/Twofish database, parsed by KeeForge itself, in `KDBXParserTests.swift` and as two more entries in `KDBXCompatibilitySupport.smokeFixtures`.

### One Run Per Scenario

Every scenario in `KDBXCompatibilitySupport.artifactDescriptors` is executed by **exactly one** `KDBXCompatibilityTests` method, and that method emits the bytes it just wrote as XCTAttachments for `../ci_scripts/run_kdbx_compatibility_gate.sh`. Artifact emission piggybacks on the assertion-bearing run; nothing is re-executed to produce a file (the retired `KDBXCompatibilityArtifactTests.swift` used to re-run the whole set, doubling the Argon2 work on every CI run).

Each emitting method builds a `KDBXCompatibilitySupport.ArtifactCollector`, drives its scenarios through `collector.run(_:on:)` instead of `scenario.apply(to:)`, and finishes with `try collector.emit()`. `emit()` attaches one manifest **fragment** — `kdbx-compatibility-manifest-<test name>.json` — covering only that method's artifacts; the gate merges every fragment it finds. Each fragment also repeats the full `expectedArtifactIDs` list, so a method that stops contributing fails the gate instead of quietly shrinking coverage.

Adding a scenario means: add it to `artifactDescriptors`, run it through a collector in exactly one test method, and list its external expectations (or explicitly list it in the matching `scenarioIDsWithout…Expectations` allowlist). The lookups are fail-closed — an unlisted scenario id throws — and `test_externalExpectationTables_areExhaustiveOverEveryArtifactScenario` fails on stale or missing ids, so a rename cannot silently drop a check.

### What The Snapshot Covers

`CompatibilitySnapshot` diffs entries, groups, and meta across the save. Two things beyond per-field equality:

- `Entry.attachmentHashes` — SHA-256 of each *referenced* binary's resolved pool bytes.
- `binaryPoolDigest` — an ordered digest over the *whole* inner-header binary pool (index, protection flag, content hash of every slot, referenced or not). `Scenario.apply` compares it on every scenario, so a dropped orphan, a reordered or renumbered pool, or a flipped protection flag on an unreferenced binary fails even though no entry changed. `test_binaryPoolDigest_detectsOrphanedReorderedAndReflaggedPoolEntries` pins its sensitivity. This complements — never replaces — the per-attachment hashes.

### Single Smoke Fixture List

`KDBXCompatibilitySupport.smokeFixtures` is the one source of truth for the representative-fixture sweep, consumed by both `test_representativeCompatibilityFixtures_…` and `artifactDescriptors`. `unknown-inner-header` is skipped by the sweep because a dedicated deeper method runs (and emits) its smoke scenario; that skip list lives in `KDBXCompatibilityTests.smokeFixtureIDsWithDedicatedTests`. `kitchen-sink` is not in `smokeFixtures` at all — `test_kitchenSinkFixture_…` owns its smoke scenario plus the four `attachments-*`/`group-tags-*` edit scenarios. Its group-tag, opaque-XML and `PublicCustomData` proofs are deliberately split off from the gate: `keepassxc-cli` has no verb for any of the three, so the external gate checks the rewritten database opens with structure (`Projects/Client Work` and friends via `ls`), attachments and protected values intact, while the byte-faithful preservation itself is asserted in-process (`GroupScalars` carries `tags`/`hasTagsElement`, so `assertSurvivingGroupsPreserveScalars` covers every scenario on every fixture, and the `Round Trip` fragments plus the unknown outer-header field are compared before/after on the smoke snapshots). The `unknown-inner-header` proof is split the same way: `keepassxc-cli` cannot print an inner-header field, so the gate proves the rewritten database still opens, its protected password reads back, and both attachments export byte-identically, while the byte-exact survival and before-the-pool ordering of the unknown fields themselves are asserted in-process (`KDBXCompatibilityTests.test_unknownInnerHeaderFixture_…` and `KDBXWriterTests`).
