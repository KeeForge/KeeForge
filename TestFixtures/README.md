# Test Fixtures

This folder contains the sample databases and key files used by unit tests, UI tests, and screenshot flows.

## Main Databases

- `test.kdbx` — default fixture for most tests. Password: `testpassword123`.
- `demo.kdbx` — richer demo fixture used by `KeeForgeUITests/AppStoreScreenshots.swift`. Password: `demo`.
- `demo-keyfile.kdbx` — key-file-protected fixture. Credentials: password `demo` plus `demo-keyfile.key`, hardcoded by the UI tests and by `KeeForgeTests/KDBXWriterTests.swift` and `KeeForgeTests/KDBXRoundTripTests.swift`.
- `autofill-union.kdbx` — distinct-domain second database for `KeeForgeUITests/AutoFillStoreUITests`' multi-database union scenario. Password: `testpassword123`. One `Union` group with three entries — `Union Bank` (`unionbank-fixture.net`), `Union News` (`union-news-fixture.org`, TOTP via the KeePassXC `otp` field), `Union Shop` (`union-shop-fixture.io`) — publishing exactly 3 password + 1 one-time-code AutoFill identities. Every service domain and username is deliberately disjoint from `test.kdbx`'s: the simulator's credential-identity store dedups identities sharing the same (service, user) pair across databases, so the union scenario needs fixtures that cannot collapse into each other. Generated with `pykeepass` (`create_database` → KDBX 4.0 / AES-256, same rationale as `compatibility/attachments.kdbx` — `keepassxc-cli db-create` only produces KDBX 3.1); regenerate by recreating the three entries above with the same password.
- `tag-browser.kdbx` — the only bundled fixture that carries entry tags; neither `test.kdbx` nor `demo.kdbx` has a single one. Password: `testpassword123`. Drives `KeeForgeUITests/TagBrowserUITests`. Two root groups: `Tagged` with `Router Admin` (tags `shared`, `Work`, `Personal Notes`), `Mail Account` (tags `shared`, `work`) and `Untagged Entry` (no tags), plus `Archive` with `Old Backup` (tag `archive`). Five distinct tags, deliberately covering the cases the browser has to get right: `shared` spans two entries in two groups (a count above one), `Work`/`work` are a case-variant pair (exact-string identity keeps them apart, the Finder-style display sort keeps them adjacent), `archive` has exactly one carrier (the "1 entry" plural branch), and `Personal Notes` contains a space (identifier suffix `tag-list.row.personal-notes`). pykeepass writes the tags `;`-separated, KeePass's canonical form, so the fixture also exercises the parser's semicolon split. Regenerate with `TestFixtures/generate_tag_browser_fixture.py` (`pip3 install --user pykeepass`, run from the repo root; `--check` verifies the file on disk instead) — KDBX 4.0 / AES-256, same rationale as `autofill-union.kdbx` and `compatibility/attachments.kdbx`. Content is deterministic, bytes are not (fresh crypto salts on every save).
- `protected-custom-field.kdbx` — drives `ProtectedCustomFieldUITests`. Password: `testpassword123`. Its `Secrets/Protected Custom` entry and single stored history version both carry `API Token = custom-secret` with `Protected="True"`, covering masked display and authenticated reveal/copy on both screens. Regenerate or verify it with `TestFixtures/generate_protected_custom_field_fixture.py`.
- `round-trip/unknown-elements.kdbx` — controlled KDBX4 round-trip fixture with meta and entry `CustomData`, `AutoType`, `History`, and an attachment reference. Password: `test-round-trip`.
- `test-v3-backup.kdbx` — legacy KDBX 3.1 fixture. Password: `testpassword123`. Bundled into `KeeForgeTests`/`KeeForgeMacTests`; used by `KDBXParserTests` (legacy-format coverage), `KDBXFileSummaryTests`, `LocalDatabaseSaverTests`, `CloudDatabaseSaverTests`, and `DatabaseViewModelTests`.
- `compatibility/` — sanitized fixtures for the KDBX compatibility matrix and external opener gate. Database passwords mirror their source fixtures: `aes-baseline.kdbx` uses `testpassword123`, `password-keyfile.kdbx` uses `demo` plus `password-keyfile.key`, `unknown-rich.kdbx` uses `test-round-trip`, `kdbx41-public-custom-data.kdbx` uses `testpassword123`, `legacy-kdbx31.kdbx` uses `testpassword123`, `attachments.kdbx` uses `testpassword123`, `foreign-chacha20.kdbx` uses `foreign-chacha20`, `foreign-twofish.kdbx` uses `foreign-twofish`, `group-tags.kdbx` uses `testpassword123`, and `unknown-inner-header.kdbx` uses `unknown-inner-header`.

These pairs are mirrored in `KDBXCompatibilitySupport.fixtureEntryPasswords`; changing an entry's password in a fixture means updating that table.
    - `aes-baseline.kdbx` — `Social/Twitter` → `twitterpass123`
    - `kdbx41-public-custom-data.kdbx` — `Social/Twitter` → `twitterpass123`
    - `password-keyfile.kdbx` — `KeyFile Test Entry` → `keyfilepass123`
    - `unknown-rich.kdbx` — `Controlled Unknowns` → `roundtrip-pass`
    - `attachments.kdbx` — `Attachments/Multi Attachment Entry` → `entry-password-1`
    - `foreign-chacha20.kdbx` — `Foreign/Foreign Entry Alpha` → `ForeignAlphaSecret1`
    - `foreign-twofish.kdbx` — `Foreign/Foreign Entry Alpha` → `ForeignAlphaSecret1`

- `compatibility/attachments.kdbx` — KDBX4 (AES cipher) fixture built with `pykeepass` for attachment coverage. Also bundled into both UI-test targets (`KeeForgeUITests`, `KeeForgeMacUITests`) and driven by `KeeForgeUITests/EntryAttachmentsSmokeUITests.swift` — retargeting or removing it breaks UI tests, not just the compatibility gate. One `Attachments` group with four entries: `Multi Attachment Entry` (two attachments: `note-ü.txt` and `pixel.png`, exercising a non-ASCII filename and binary content), `Dedup Entry A` and `Dedup Entry B` (both attach a file named `shared.bin` with byte-for-byte identical content, for pool-dedup coverage), and `No Attachment Entry` (no attachments). Deterministic content and SHA-256 hashes (also recorded in `KeeForgeTests/KDBXCompatibilitySupport.swift`):
  - `note-ü.txt`: `bcc1c6cd101bd5b27356a7004361fd1e1ff74ed2ef416e3252997d328efd3727`
  - `pixel.png`: `3ec322a42990a3067cc6c73f3856a86e55bdd8baf19d2166954a8fb319329a72`
  - `shared.bin` (identical on both Dedup Entry A and Dedup Entry B): `fd184a4f05cf3d4f39ab726bda3d3a923da30e9ab2d6697b69c2d39d7ea1ab18`
  - Regenerate with `pykeepass` (see `KDBXCompatibilitySupport` / gate history) rather than `keepassxc-cli db-create`, since that CLI's `db-create` only produces KDBX 3.1 databases and exposes no cipher/KDF override flags.
- `compatibility/foreign-chacha20.kdbx` and `compatibility/foreign-twofish.kdbx` — KDBX4 fixtures built with `pykeepass`, an independent (non-KeeForge) implementation, specifically to test KeeForge's ChaCha20 and Twofish outer-cipher **read** paths against a database KeeForge did not write itself. Every other fixture in this repo is AES-256-CBC (authored by pykeepass or KeeForge), so without these two, a read failure on a user's foreign-authored ChaCha20/Twofish vault had zero test coverage. Both carry identical content: a root-level `Foreign` group with two entries — `Foreign Entry Alpha` (username `foreign-alpha-user`, password `ForeignAlphaSecret1`, one custom field `ForeignField` = `ForeignFieldValue`) and `Foreign Entry Beta` (username `foreign-beta-user`, password `ForeignBetaSecret2`, no custom field). Only the database password and the declared outer cipher differ between the two files. Regenerate with `TestFixtures/compatibility/generate_foreign_cipher_fixtures.py` (`pip3 install --user pykeepass`, then run the script from the repo root); it documents pykeepass's undocumented header-mutation path (there is no public `encryption_algorithm` setter) and re-verifies the written cipher UUID by parsing the outer header independently, since the content is deterministic but the crypto salts (master seed, encryption IV, KDF salt) are freshly randomized on every run.
- `compatibility/group-tags.kdbx` — genuine KDBX **4.1** fixture (AES-256-CBC, Argon2d) built with `pykeepass`, an independent implementation, for KeeForge's group-`<Tags>` support (group tags exist only in KDBX ≥ 4.1; authoring one raises a database's header to 4.1). Password: `testpassword123`. Driven by `KDBXParserTests.testGroupTagsFixtureParsesGroupTagsThroughFullDecryptPath`, the compatibility smoke sweep, and `KDBXCompatibilityTests.test_groupTagsFixture_preservesGroupTagsAcrossSaves`. Also bundled into `KeeForgeUITests` and driven by `KeeForgeUITests/InheritedTagsUITests.swift` (the entry detail screen's inherited tag chips) — retargeting or removing it breaks UI tests, not just the compatibility gate. Deterministic content, covering every `<Tags>` state the parser models:
  - `Projects` — group tags `team;shared` (pykeepass writes the KeePass-canonical `;` join, exercising the semicolon split) **plus** a group `<Notes>` ("Group notes ride along as unknown XML next to the structured Tags element."), an element KeeForge preserves as unknown XML, so unknown-sibling positioning next to the structured `<Tags>` is exercised in a real file. Contains `Alpha Login` (username `alpha-user`, password `GroupTagAlpha1`, URL `https://alpha.example.com`).
  - `Projects/Client Work` — nested group with tag `billable`; contains `Beta Login` (username `beta-user`, password `GroupTagBeta2`, URL `https://beta.example.com`, own **entry** tag `own-tag`) so inheritance accumulation (root-level tag + subgroup tag + own tag) has a real carrier.
  - `Empty Tags Group` — an EMPTY `<Tags/>` element (present but contentless, the state `hasTagsElement` preserves); contains `Gamma Login` (username `gamma-user`, password `GroupTagGamma3`).
  - `Plain Group` — no `<Tags>` element at all (KeeForge must never add one); contains `Delta Login` (username `delta-user`, password `GroupTagDelta4`).
  - `Recycle Bin` — created by trashing `Trashed Login` (username `trashed-user`, password `GroupTagTrashed5`), so the fixture also carries `Meta/RecycleBinUUID`. The bin itself deliberately carries no tags; recycle-bin tag exclusion is unit-tested in-memory in `DatabaseViewModelTests`.
  - Regenerate with `TestFixtures/compatibility/generate_group_tags_fixture.py` (`pip3 install --user pykeepass`, run from the repo root; `--check` verifies the file on disk). The script documents the pykeepass header-mutation recipe needed to write 4.1 (pykeepass writes 4.0 by default and Construct's `RawCopy` re-emits cached header bytes unless dropped) and re-reads the raw version bytes independently after saving. Content is deterministic, bytes are not (fresh crypto salts on every save). Changing any password here means updating `KDBXCompatibilitySupport.fixtureEntryPasswords`/`passwordExpectations`, and changing group names or tags means updating that file's `group-tags-update-entry` scenario plus `KDBXParserTests` and `KDBXCompatibilityTests`.
- `compatibility/unknown-inner-header.kdbx` — KDBX4 (AES-256-CBC, Argon2d) fixture with unrecognized KDBX4 inner-header fields spliced in, for KeeForge's unknown-inner-header-field preservation (see `docs/specs/2026-07-26-kdbx-format-hardening/02-unknown-inner-header-preservation.md`). Password: `unknown-inner-header`. One `Unknown Header` group with one entry, `Inner Header Entry` (username `unknown-header-user`, password `UnknownHeaderSecret1`), carrying two attachments — `alpha-attachment.txt` (`2e1e53db7251ba3852ea965523b8ff3ab8b7426adf50277d0d8d41d40630bdfd`) and `beta-attachment.txt` (`ee48b95cd61f6f910959979dc94199de8012611f0050e85c5d7cd15e3d95d4b0`) — so the inner-header binary pool has two entries to splice between. Three unknown inner-header fields are spliced into the on-disk item sequence: id `0x21` with a non-empty payload positioned BETWEEN the two binary-pool entries (KeeForge's writer is expected to normalize this to before-the-pool on save — this fixture is what lets a test observe that), id `0x7F` with a recognizable non-trivial payload, and id `0x10` with a zero-length payload, both positioned after the protected-stream ID/key fields. The inner header (unlike the outer header the other fixtures mutate) lives inside the encrypted payload, so pykeepass's usual header-mutation trick doesn't reach it — pykeepass's own inner-header type field also has no default mapping and raises `MappingError` on any byte outside `0x00`-`0x03`, so it cannot even round-trip an unknown field back out. Regenerate with `TestFixtures/compatibility/generate_unknown_inner_header_fixture.py` (`pip3 install --user pykeepass`, run from the repo root; `--check` verifies the file on disk; pass `--keepassxc-cli /path/to/keepassxc-cli` to also verify externally), which documents the from-scratch decrypt/re-encrypt fallback this required: pykeepass builds and saves a normal database first (verified by reopening it with pykeepass, before the splice), then the script decrypts the payload independently (Argon2d transform, HMAC-SHA256 block verification, AES-256-CBC, zlib inflate), splices the three fields into the parsed item list, and re-encrypts under the same master seed/IV/KDF params. Deliberately, reopening the FINAL spliced file with pykeepass fails with `MappingError` — that failure is the verified, expected behavior demonstrating the gap this fixture exists to probe, not a defect; KeePassXC's reader has no such default-less switch and opens the file normally (its own `readInnerHeaderField` silently skips unrecognized IDs). Content is deterministic, bytes are not (fresh crypto salts on every save). Changing the entry password means updating `KDBXCompatibilitySupport.fixtureEntryPasswords`.

## Key Files

- `test-binary.key`, `test-hex.key`, `test-v1.key`, `test-v2.keyx`, and `test-arbitrary.key` cover the supported key-file parsing formats.
- `demo-keyfile.key` is the end-to-end fixture paired with `demo-keyfile.kdbx`.

## Notes

- `test.kdbx` has groups under the root, so many flows need to enter a subgroup before opening an entry.
- `test.kdbx` is the stable fixture-backed source for common entries like Twitter, GitHub, and Email.
- Compatibility fixtures are intentionally copied into `compatibility/` so future agents can add, remove, or retarget release-gate coverage without changing unrelated unit-test fixture names.
- If you add a new fixture that tests depend on, wire it into the correct target in `../project.yml`. Four targets bundle fixtures: `KeeForgeTests`, `KeeForgeUITests`, `KeeForgeMacTests`, and `KeeForgeMacUITests` (which also consumes `test.kdbx` and `demo.kdbx`).
