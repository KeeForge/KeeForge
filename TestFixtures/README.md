This folder contains the sample databases and key files used by unit tests, UI tests, and screenshot flows.

- `compatibility/foreign-chacha20.kdbx` and `compatibility/foreign-twofish.kdbx` — KDBX4 fixtures built with `pykeepass`, an independent (non-KeeForge) implementation, specifically to test KeeForge's ChaCha20 and Twofish outer-cipher **read** paths against a database KeeForge did not write itself. Every other fixture in this repo is AES-256-CBC (authored by pykeepass or KeeForge), so without these two, a read failure on a user's foreign-authored ChaCha20/Twofish vault had zero test coverage. Both carry identical content: a root-level `Foreign` group with two entries — `Foreign Entry Alpha` (username `foreign-alpha-user`, password `ForeignAlphaSecret1`, one custom field `ForeignField` = `ForeignFieldValue`) and `Foreign Entry Beta` (username `foreign-beta-user`, password `ForeignBetaSecret2`, no custom field). - `compatibility/unknown-inner-header.kdbx` — KDBX4 (AES-256-CBC, Argon2d) fixture with unrecognized KDBX4 inner-header fields spliced in, for KeeForge's unknown-inner-header-field preservation (see `docs/specs/2026-07-26-kdbx-format-hardening/02-unknown-inner-header-preservation.md`). Password: `unknown-inner-header`. One `Unknown Header` group with one entry, `Inner Header Entry` (username `unknown-header-user`, password `UnknownHeaderSecret1`), carrying two attachments — `alpha-attachment.txt` (`2e1e53db7251ba3852ea965523b8ff3ab8b7426adf50277d0d8d41d40630bdfd`) and `beta-attachment.txt` (`ee48b95cd61f6f910959979dc94199de8012611f0050e85c5d7cd15e3d95d4b0`) — so the inner-header binary pool has two entries to splice between. Three unknown inner-header fields are spliced into the on-disk item sequence: id `0x21` with a non-empty payload positioned BETWEEN the two binary-pool entries (KeeForge's writer is expected to normalize this to before-the-pool on save — this fixture is what lets a test observe that), id `0x7F` with a recognizable non-trivial payload, and id `0x10` with a zero-length payload, both positioned after the protected-stream ID/key fields. The inner header (unlike the outer header the other fixtures mutate) lives inside the encrypted payload, so pykeepass's usual header-mutation trick doesn't reach it — pykeepass's own inner-header type field also has no default mapping and raises `MappingError` on any byte outside `0x00`-`0x03`, so it cannot even round-trip an unknown field back out. Regenerate with `python3 TestFixtures/generate_fixtures.py unknown-inner-header` (see [Regenerating fixtures](#regenerating-fixtures)); `TestFixtures/generators/unknown_inner_header.py` documents the from-scratch decrypt/re-encrypt fallback this required: pykeepass builds and saves a normal database first (verified by reopening it with pykeepass, before the splice), then the script decrypts the payload independently (Argon2d transform, HMAC-SHA256 block verification, AES-256-CBC, zlib inflate), splices the three fields into the parsed item list, and re-encrypts under the same master seed/IV/KDF params. Deliberately, reopening the FINAL spliced file with pykeepass fails with `MappingError` — that failure is the verified, expected behavior demonstrating the gap this fixture exists to probe, not a defect; KeePassXC's reader has no such default-less switch and opens the file normally (its own `readInnerHeaderField` silently skips unrecognized IDs). Content is deterministic, bytes are not (fresh crypto salts on every save). Changing the entry password means updating `KDBXCompatibilitySupport.fixtureEntryPasswords`.
- `compatibility/argon2-high-iterations.kdbx` — KDBX4 (AES-256-CBC, Argon2d) fixture built with `pykeepass` whose Argon2 KDF uses a HIGH iteration count with LOW memory: iterations 1500, memory 1 MiB, parallelism 1 (1.5 GiB of total work). Password: `argon2-high-iterations`. This is the acceptance case for the `KDFExecutionPolicy` work-budget model (issue #74): KeeForge used to reject any Argon2 configuration with iterations > 1000 regardless of memory, so a foreign-authored database with these settings could never open. One `High Iterations` group with one entry, `High Iteration Entry` (username `high-iteration-user`, password `HighIterationSecret1`). The low memory keeps the repeated derivations in the compatibility matrix and gate cheap. Regenerate with `python3 TestFixtures/generate_fixtures.py argon2-high-iterations` (see [Regenerating fixtures](#regenerating-fixtures)). `TestFixtures/generators/argon2_high_iterations.py` documents the pykeepass header-mutation recipe for KDF parameters (pykeepass exposes no KDF API; the values are set on the parsed variant dictionary and RawCopy's cached header bytes are dropped) and re-reads the written KDF values by parsing the outer header independently. Content is deterministic, bytes are not (fresh crypto salts on every save). Changing the entry password means updating `KDBXCompatibilitySupport.fixtureEntryPasswords`.

## Merge Fixtures

`Merge/` holds the oracle fixtures for the KeePass Synchronize merge feature. Every scenario is a directory containing a trio of KDBX 4 databases plus a recorded expectation dump; all of them share one password, `testpassword123`.

- `Merge/<scenario-id>/local.kdbx` — the side KeeForge holds in memory (the merge **target**).
- `Merge/<scenario-id>/remote.kdbx` — the side that landed on disk or in the cloud (the merge **source**).
- `Merge/<scenario-id>/merged-reference.kdbx` — `cp local.kdbx merged-reference.kdbx` followed by `keepassxc-cli merge -s merged-reference.kdbx remote.kdbx`. Real KeePassXC 2.7.12 is the behavioural oracle.
- `Merge/<scenario-id>/expectations.txt` — the merge's own change list, the idempotence re-merge output, `keepassxc-cli ls -R` for all three files, and a decoded structural dump (tree, UUIDs, `LastModificationTime`, `LocationChanged`, history items, attachments, `DeletedObjects`).
- `Merge/manifest.json` — machine-readable index: password, base-tree UUIDs, per-scenario description, edit order, assertions, and every place the oracle's behaviour diverges from the algorithm spec.

The base tree behind every scenario is deterministic — root `00000000-0000-4000-8000-000000000000`, groups `Work` / `Personal` / `Archive` (`1111…`, `2222…`, `3333…`), entries `Alpha` / `Beta` / `Gamma` (`aaaa…`, `bbbb…`, `cccc…`) — so tests can key on UUIDs. Timestamps are real wall-clock values from generation time and change on every regeneration.

Scenarios: `both-add-entries`, `remote-newer-wins`, `local-newer-wins`, `history-union`, `same-timestamp-diverged`, `move-vs-edit`, `move-into-remote-only-group`, `delete-local-then-edit-remote`, `edit-remote-then-delete-local`, `delete-remote-then-edit-local`, `edit-local-then-delete-remote`, `recycle-vs-edit`, `group-rename-vs-entry-add`, `group-deleted-vs-entry-added`, `attachment-divergence`, `identical-no-changes`.

**The reference is not authoritative everywhere.** `keepassxc-cli merge` runs KeePassXC's `Merger` in *KeepNewer* mode (the root group's merge mode falls back to `KeepNewer`, and `Merger::mergeDeletions` returns early for every mode except `Synchronize`), and there is no CLI flag to force `Synchronize`. Consequences, all recorded per scenario in `manifest.json`:

- **Deletions never propagate.** In the four delete scenarios the reference resurrects the entry regardless of timestamps, and target-side tombstones survive next to the live entry they refer to. KeeForge implements the `Synchronize` rule (a tombstone kills an object whose `LastModificationTime` precedes the `DeletionTime`; an object edited afterwards survives and its tombstone is dropped), so the reference and KeeForge deliberately disagree in `edit-remote-then-delete-local` and `edit-local-then-delete-remote`, and disagree on tombstone retention in `delete-local-then-edit-remote`.
- **`Meta/RecycleBinUUID` is never adopted** (there is an explicit TODO in `Merger::mergeMetadata`), so `recycle-vs-edit`'s reference carries the bin group with an all-zero `RecycleBinUUID`.
- **A merge-moved entry keeps its stale `LocationChanged`** — `Merger` adopts the source value for groups but not for entries. Compare placement, not that timestamp.
- **Sibling order is an artefact.** When the source entry wins a conflict, `Merger` erases the target entry and appends a clone, so the winner ends up last in its group. Compare merged trees order-insensitively.

Everything else — entry conflict resolution, history union, history dedupe by `LastModificationTime`, moves, group renames, idempotence — is mode-independent in KeePassXC (`Merger::mergeHistory` ignores the merge mode outright) and is a faithful oracle.

Regenerate the whole set with `scripts/generate-merge-fixtures.sh` (see `scripts/README.md`); `--scenario <id>` rebuilds a single one.

`KeeForgeTests/KDBXMergerOracleTests.swift` consumes them, enumerating scenarios from `manifest.json`. Unlike every other fixture, they are bundled into `KeeForgeTests`/`KeeForgeMacTests` as a **folder reference** (`type: folder` in `../project.yml`), because the sixteen scenario directories all contain files named `local.kdbx`, `remote.kdbx`, and `merged-reference.kdbx` — a flat resource copy would collide. The bundle therefore keeps the `Merge/<scenario-id>/…` structure, and adding a scenario directory needs no project change (the oracle suite fails if a directory and the manifest disagree).

## Regenerating fixtures

Five fixtures are authored by one tool, `TestFixtures/generate_fixtures.py` (`pip3 install --user pykeepass`; runs from any working directory). Each fixture's recipe, and the prose explaining why it exists, lives in its own module under `TestFixtures/generators/`; shared plumbing (outer-header and variant-dictionary parsing, the Construct `RawCopy` cache drop, the `keepassxc-cli` wrapper) lives in `generators/_common.py`.

```bash
python3 TestFixtures/generate_fixtures.py --list          # names and output paths
python3 TestFixtures/generate_fixtures.py --all --check   # verify every generated fixture on disk
python3 TestFixtures/generate_fixtures.py kitchen-sink    # rebuild one, then verify it
```

Registered names: `kitchen-sink`, `argon2-high-iterations`, `foreign-chacha20`, `foreign-twofish`, `unknown-inner-header`.

- `--check` verifies only and never writes. Without it, each selected fixture is rebuilt and then verified with the same assertions.
- `--keepassxc-cli /Applications/KeePassXC.app/Contents/MacOS/keepassxc-cli` adds an external-reader check (KeePassXC opens the file and lists its group; `kitchen-sink` and `unknown-inner-header` also read back entry passwords and export every attachment for a SHA-256 comparison). Optional.
- `--output-dir DIR` builds and verifies in `DIR` instead of the committed locations, to rehearse a regeneration without touching the repo.
- Regenerating always changes the file's **bytes**: pykeepass randomizes the master seed, encryption IV, and KDF salt on every save. Only the decoded **content** is deterministic, and that is all the tests and the tool's own verification assert.

The remaining fixtures have no generator: the `Merge/` set is rebuilt by `scripts/generate-merge-fixtures.sh` (see `scripts/README.md`); `test.kdbx`, `demo.kdbx`, `demo-keyfile.kdbx`, `autofill-union.kdbx`, `round-trip/unknown-elements.kdbx`, `compatibility/kdbx41-public-custom-data.kdbx`, `compatibility/legacy-kdbx31.kdbx`, and every key file are one-off artifacts described in place above.

## Notes

- `test.kdbx` has groups under the root, so many flows need to enter a subgroup before opening an entry.
- `test.kdbx` is the stable fixture-backed source for common entries like Twitter, GitHub, and Email.
- One file per content: no fixture is a byte-identical copy of another. The compatibility harness reaches shared fixtures by name and subdirectory (`KDBXCompatibilitySupport.Fixture.Source.bundled`) instead of keeping a private copy under `compatibility/`, and its fixture IDs stay stable when the file it reads moves.
- If you add a new fixture that tests depend on, wire it into `../project.yml`. Fixtures shared by more than one target live in the `UnitTestFixtures` and `UITestFixtures` `targetTemplates`; a target lists only its own extras (`KeeForgeUITests` does, `KeeForgeMacUITests` does not).
