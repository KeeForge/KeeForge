# KeeForge threat model

## Overview

This is the maintained threat model for KeeForge on iPhone, iPad, and macOS, including its AutoFill extensions and distribution channels. Start with the assets and boundary invariants below when changing the product; the resource inventory records implementation details. The scenarios are review hypotheses, not confirmed vulnerabilities or evidence of a completed security audit. Vulnerability reporting is governed by [SECURITY.md](../SECURITY.md); detailed Mac constraints live in [KeeForgeMac/SECURITY.md](../KeeForgeMac/SECURITY.md).

KeeForge opens user-selected or cloud-hosted KeePass databases, decrypts them locally, and returns encrypted KDBX bytes to storage. KDBX 4.x supports editing; KDBX 3.1 is read-only. Users can unlock with a password and/or key file, use an authenticated saved unlock key, and, on supported iOS hardware, require a YubiKey challenge response. AutoFill runs in a separate process with access to shared encrypted caches and Keychain items. It can also save credentials, including passkey registrations, so it is part of the write boundary.

Arrows mark data or authority crossings, not blanket trust. Cloud storage, imported files, and requesting clients are untrusted. The OS mediates authentication, entitlements, and requesting-client identity; KeeForge owns credential selection, session handling, and encrypted writes. The Mac extension cannot use the app's external-file or network entitlements, so its file arrow is iOS-only. Web pages are untrusted as well: the browser extension's content script runs inside them, but the logins it lists stay in an extension frame the page cannot read.

The per-database AutoFill toggle commits its registry change before scheduling identity removal. The system suggestion index is an asynchronous best-effort derivative, not authority to authenticate or fill; its existing non-incremental fallback may clear suggestions belonging to other databases. Registry publication and the system index are not an atomic cross-process transaction.

Database removal revokes the pending-local owner before publishing the registry change. If registry publication fails or is unconfirmed, KeeForge retains the cache, keys, pending sources and suggestion identities; an observed revocation is not proof that removal completed or that an unresolved owner is usable. An idle owner can be retried with the same captured database identity.

Cloud metadata learned across an await is published only if the captured cloud identity, revision, local head, epoch and reference preferences still match inside coordinated registry access. A visible but unconfirmed registry publication is not a durable receipt for the caller.

On Mac, [AppDelegate](../KeeForgeMac/App/AppDelegate.swift) owns the session store, lifecycle and lock services, and AppKit menus. [MacWindowCoordinator](../KeeForgeMac/App/MacWindowCoordinator.swift) keeps a Databases window and one window per open database, keyed by the database UUID that also keys the session. Each [DatabaseWindowController](../KeeForgeMac/App/DatabaseWindowController.swift) holds its session directly; content, title, commands, close, enrollment sheets and automatic unlock act only on it, and opening one database never locks or retires another. Menu commands resolve through [MacDatabaseCommandTargetResolver](../KeeForgeMac/App/MacDatabaseCommandTargetResolver.swift) at validation and again at dispatch: the key database window or a key sheet's parent; the main database window when Settings or a panel is key; nothing when the Databases window is key. An authenticated password copy re-checks that the originating controller still owns the session. The Databases window lists and manages references and never shows database contents. Each database window keeps its root host mounted; its unlocked workspace puts a native sidebar outline, a native entry table and a SwiftUI detail host under a native split controller and a native toolbar. A completed lock drops the split controller and toolbar, and the window-owned native sheet/alert presenters end presentations top-down on lock, close and invalidation, reject old lock-cycle callbacks (including deferred Keep Editing authentication and Save and Lock completion), and clear editors and pending actions. Hosted authentication/import cancellation runs synchronously when the shell ends; an in-flight write continues; split autosave retains only geometry and collapse state, per database UUID. The separate retained Settings window reads no window's session and receives the same blur cover and best-effort capture policy; the coordinator applies the capture policy to each window before first showing it. Closing a database window settles its unsaved work through the close guard, then locks and retires only that session, supersedes any opening still in flight, and releases the window; cancel or a failed save keeps both. A locked database window shows only the database's name, file name, storage provider, last-opened time, associated key file's name, the failure and its code, and why it locked, never a path or server address; its Remove from List asks in that window and applies the Databases window's unsaved-work refusal and cleanup ([MacLockedDatabaseSummary](../KeeForge/ViewModels/MacLockedDatabaseSummary.swift), [MacWindowCoordinator](../KeeForgeMac/App/MacWindowCoordinator.swift)). A verification-code link binds to the database window targeted when it arrives, or to a database the user picks in the Databases window; focus changes never retarget it. Hide and minimize do not introduce lock triggers.

Mac per-database settings use an [attached native sheet](../KeeForgeMac/App/MacDatabaseSettingsSheet.swift), owned by the originating workspace's lock cycle, or a reference-only launcher presenter. The launcher omits decrypted destination groups and key-changing actions. [The settings model](../KeeForge/ViewModels/MacDatabaseSettingsModel.swift) reads plaintext header facts and scoped encrypted backups; AutoFill participation retains the list model's refresh bridge. Password/key-file presence flags are session-only display metadata from typed unlock or rekey, cleared on lock; composite-key-only and hardware-key unlocks, and a rekey that reached only the remote, leave composition unknown. A rekey replaces the session's key-file bytes, so a removed key file never returns in the next change. The sheet drops key-file association controls; existing unlock, launcher-row and rekey paths keep their bookmark/storage boundaries. Export still delegates to the existing encrypted-copy exporter. No new plaintext output, key-file writer or authentication path is introduced.


App-global activation, background/system-lock requests, and live Settings effects reach every session retained by [DatabaseSessionStore](../KeeForge/ViewModels/DatabaseSessionStore.swift), regardless of active selection. Each session applies its existing lock policy and unsaved-work deferral. Mac activity resolves the event window, sheet or child parent through the app-owned MacDatabaseWindowRegistry and resets only that database's timer, throttled per database. Settings, panels and unregistered windows extend no deadline. Mac activation evaluates existing deadlines without renewing idle sessions; cache refresh and upload draining remain global. iOS activity retains its all-session fan-out. Unregistering a database window clears pending close callbacks, preventing stale grants after replacement. A Mac database window's committed close retires its session; reopening creates a new, locked window. The application installs list-reconciliation hooks when it creates the shared models, so removing a database from the list force-retires its session and clears its secrets even without a mounted root view. The Mac Databases window refuses that removal while the session has unsaved work or a write in flight, checks again after the confirmation, and shows a refusal raised as the confirmation ends from a per-window native alert queue rather than dropping it ([MacAlertQueue](../KeeForgeMac/App/MacAlertQueue.swift)); a close waits out a write in flight on its session, and a failed master-key or encryption-settings write keeps the window. Reference reconciliation updates only existing sessions, reads the latest persisted reference to avoid rolling back session-written sync metadata, and never reloads decrypted content. An unlocked local session or in-flight write retains its authenticated target and master-key epoch across these callbacks; list metadata cannot authorize a new key epoch.

## Threat model, trust boundaries, and assumptions

### Assets and objectives

- **Vault confidentiality:** passwords, TOTP seeds, passkey private keys, attachments, history, notes, and custom fields should remain inaccessible without the required unlock factors. Stolen encrypted copies still permit offline password guessing; password strength and key-file custody matter.
- **Key and authentication integrity:** saved unlock keys must retain OS authentication controls. Hardware-key quick unlock must retain the hardware factor; it stores the pre-key, not the final composite key, and never an express-unlock key. The express-unlock key caches one file version's KDF output so quick unlock can skip the KDF; it must open nothing that the saved composite key could not, and only the version it was derived for ([ExpressUnlockKey.swift:12](../KeeForge/Models/ExpressUnlockKey.swift#L12)). Hardware-key transport is currently available only in the iOS app, not Mac or either extension ([HardwareKeyService.swift:8](../KeeForge/Services/Security/HardwareKeyService.swift#L9)).
- **Correct disclosure:** AutoFill should release the intended credential to the OS-mediated request, respect per-database selection, and bind passkey assertions to the relying party and allowed credential. A password fill resolves `{REF:…}` field references against the whole database ([completeRequest(with:)](../AutoFillExtension/CredentialProviderCoordinator.swift)), so values a website or relying party supplies are never saved with a reference: save-password and passkey registration refuse them ([save check: saveNewEntry](../AutoFillExtension/CredentialProviderCoordinator.swift), [registration check: prepareInterface(forPasskeyRegistration:)](../AutoFillExtension/CredentialProviderCoordinator.swift)). The same holds for files and links the user brings in: a password-import row with a reference in any column is skipped and listed as such, and an `otpauth://` link's issuer or account name holding one is not used to fill an entry's empty title or user name ([import check](../KeeForge/Models/PasswordImport.swift), [enrollment prefill](../KeeForge/ViewModels/EntryEditViewModel.swift)). A new entry's URL keeps only the site's scheme, host, and port, and a supplied title holding a reference is dropped ([initial draft:116](../KeeForge/Services/AutoFill/AutoFillSaveCoordinator.swift#L116)). A tapped or silent suggestion fills the entry its record identifier names only while that entry still lists the suggestion's host itself, not just a subdomain of it, so an identity left published after a URL change opens the picker instead ([suggestedEntry](../AutoFillExtension/CredentialProviderCoordinator.swift)). From the password picker, the user can also add the requesting website to any entry they chose; the host comes only from the OS-supplied service identifier, is shown in full beside the entry's saved URLs with a caution when it shares no registrable domain with them, and is written only on confirmation as a new `KP2A_URL_<n>` field. A user who confirms a lookalike domain makes that entry a suggestion on the phishing site, so the confirmation is the control ([URL addition: AutoFillURLAddition](../AutoFillExtension/CredentialProviderCoordinator.swift)). Publishing suggestion metadata must not publish passwords or private keys. Where the OS store cannot be enumerated (iOS and macOS 27.0.1), KeeForge cannot remove one database's identities selectively: disabling or removing a database clears the whole store, and with several AutoFill databases enabled the metadata of a deleted or changed entry can stay published until the store is next cleared ([refresh without enumeration:749](../KeeForge/Services/AutoFill/CredentialIdentityStoreManager.swift#L749)). Password identities do expose domains, usernames or fallback titles, and record identifiers to the OS ([CredentialIdentityStoreManager.swift:852](../KeeForge/Services/AutoFill/CredentialIdentityStoreManager.swift#L852)).
- **SSH signing authority (Mac):** the private-key attachments of the entries chosen for the SSH agent, and the ability to sign with them, belong to the unlocked sessions that offer them; no key is exported or stored by the agent. The agent does give its clients public key blobs and key comments or entry titles, and Settings shows the entry titles and key fingerprints of one unlocked vault: the one picked in the tab's menu, or the first unlocked session until the user picks. The socket path is fixed and not a secret. Whether the agent is on and which entry UUIDs each database serves are kept in the app's own preferences, outside the vault: they cannot add a key the unlocked vault does not hold, but they decide which of its keys are served ([MacSSHAgentController.swift:166](../KeeForge/Services/SSHAgent/MacSSHAgentController.swift#L166), [SettingsService.swift:579](../KeeForge/Services/AppSupport/SettingsService.swift#L579), [SettingsService.swift:588](../KeeForge/Services/AppSupport/SettingsService.swift#L588)).
- **Browser fill authority (Mac):** while the bridge is on, a paired browser learns, without a prompt, the title, resolved user name, database name and whether a verification code exists for each login the app's site matcher offers for any origin it names, from every open, unlocked database that takes part in AutoFill, and the counts of unlocked and locked databases. A password with its user name, or for a code-only request the current verification code alone, is released for one offered entry per request, behind that session's device-owner gate, which for the bridge fails closed: inside the grace period or after a passed prompt, never because the Mac cannot authenticate its owner. The bridge never lists a whole database or exports one, and a `matches` reply never carries a password, code or other field ([BrowserBridgeRequestHandler](../KeeForge/Services/BrowserBridge/BrowserBridgeRequestHandler.swift)). A paired browser can also get a password made with the user's generator settings while an unlocked database can take a new login, and propose a new login (site, user name, password): the app adds it as a new entry only after the user picks Save in the app's own alert and passes the same device-owner gate, through the session's normal save. It never changes or deletes an entry from the browser. Without a prompt, the browser learns whether a login with that user name is already saved for the site (`exists`), which `matches` already tells it. Outside the vault it keeps the installation's X25519 private key in the Keychain, each paired browser's public key and name in the app's own preferences, and a bookmark of each set-up browser's `NativeMessagingHosts` folder ([BrowserPairingStore](../KeeForge/Services/BrowserBridge/BrowserPairingStore.swift), [BrowserHostInstaller](../KeeForge/Services/BrowserBridge/BrowserHostInstaller.swift)). None of these can read a vault, but a public key in the pairing list is what lets a browser ask. In the browser, the extension's in-field menu is part of this authority: what it lists (titles, user names, how many logins match) and its per-tab menu token must stay out of the page, and a page must not be able to make it fill without the user's own click ([background.js](../BrowserExtension/src/background.js), [inline.js](../BrowserExtension/src/inline.js)).
- **Integrity and recoverability:** saves should preserve the vault, detect conflicting changes, retain encrypted backups, and avoid losing extension-created credentials during later sync. KDBX 4.x authenticates its header and payload, but even a valid copy can be stale. KDBX 3.1 has no authenticated outer header and checks its decrypted block stream with unkeyed SHA-256 hashes ([KDBXContainer+KDBX3.swift:87](../Packages/KDBXKit/Sources/KDBXKit/KDBXContainer+KDBX3.swift#L87), [hashed blocks:103](../Packages/KDBXKit/Sources/KDBXKit/KDBXContainer+KDBX3.swift#L103)).
- **Mac restoration metadata:** [MacWindowRestorationStore](../KeeForge/Services/AppSupport/MacWindowRestorationStore.swift) stores only ordered database UUIDs and frames, Databases-window visibility and frame, and an optional frontmost database UUID in the app's own defaults; [MacWindowCoordinator](../KeeForgeMac/App/MacWindowCoordinator.swift) records it as windows open, close, move, resize and change order. This plaintext topology can reveal database usage; it carries no unlock authority. Its record has no fields for sessions, unlocked state, keys, authentication grants, passwords, search text, selected entries/groups/tags, editor drafts, enrollment URIs, database titles, paths, or bookmarks. Plans resolve UUIDs against the current supported database list. Relaunch recreates each window with a new locked session, never authenticates, and keeps automatic Touch ID off for it until the user clicks or types in that window or opens that database explicitly. A quit waits out writes in flight, then settles each window's unsaved write; a session asked about offers no SSH keys until the quit ends, Don't Save covers only the draft it answered for, any cancel or failed write cancels the quit with every session untouched, and only a quit that proceeds freezes the pre-quit topology. Removing a database drops its record entry and split geometry.
- **Availability and privacy:** hostile files, KDF parameters, server responses, and imported content should not cause uncontrolled resource use or unintended disclosure. Logs, optional network features, and plaintext metadata must be considered separately from encrypted vault bytes.

### Actors and boundaries

The legitimate user selects databases, authorizes unlocks, chooses recipients, and configures storage. Relevant attackers may possess an encrypted vault; supply a malicious file, key file, attachment, CSV import, or incoming URL; control a cloud server or network path; operate a phishing site or requesting app; or run local software with its existing OS permissions. These capabilities do not inherently grant the vault key, biometric approval, access to another sandbox, or update-signing authority. Reporting-policy exclusions do not erase the corresponding product and privacy boundaries.

Caches, pending uploads, and backups are scoped to the database. ### Assumptions, limitations, and open questions

- The OS, Keychain, authentication UI, cryptographic implementations, and signed release are trusted. Root/kernel compromise or unrestricted inspection of the app process exposes every unlocked database; per-session keys do not isolate databases from a process compromise. The [vulnerability reporting policy](../SECURITY.md#scope) has separate scope exclusions; those exclusions do not remove ordinary unlocked-device disclosure, cloud-provider behavior, or KDBX-version differences from design review.
- Each session has its own authentication grant and lock cycle. Locking one session invalidates only its grant and clears only its secrets; app-global lock events request locks for all retained sessions, subject to each session's policy and unsaved-work deferral ([DatabaseSessionStore](../KeeForge/ViewModels/DatabaseSessionStore.swift), [SecretAccessGate](../KeeForge/Services/Security/SecretAccessGate.swift)). Menu bar quick search serves only the database whose window was last focused; the SSH agent serves the chosen keys of every open, unlocked session, and a lock of one session withdraws only its keys; the browser bridge offers matches from every open, unlocked session that takes part in AutoFill, and a lock of one session withdraws only its matches.
- Session encryption does not conceal all in-memory content: arbitrary protected custom fields and unrecognized XML can retain plaintext, and Swift/framework copies cannot all be reliably erased. While a database opens or saves, the intermediate `KDBXDocument` holds every protected value, passwords included, as plaintext `String`s until the mapping seals them or the writer masks them, and reading and writing make further short-lived copies per value; a local save also parses the current file in full only to take its header ([KDBXParser.swift](../KeeForge/Models/KDBXParser.swift), [KDBXWriter.swift](../KeeForge/Models/KDBXWriter.swift), [LocalDatabaseSaver.swift:138](../KeeForge/Services/Persistence/LocalDatabaseSaver.swift#L138)). All are freed unwiped, but so is the decrypted payload, which holds the inner-stream key beside every masked value ([KDBXContainer.swift](../Packages/KDBXKit/Sources/KDBXKit/KDBXContainer.swift)), so wiping only the XML layer's copies would not reduce what memory left after lock reveals. [KDBXXML/AGENTS.md](../Packages/KDBXXML/AGENTS.md#protected-plaintext) records the change that would. The [Mac security model](../KeeForgeMac/SECURITY.md#secrets-in-memory) records these shared limitations.
- iOS auto-lock measures inactivity: foreground touches (including scrolling and buttons) and text-field/text-view edits in the app window extend the deadline, throttled to once per second. These observers retain no input contents and ignore inactive activity; background locking and the preserved deadline on return still apply ([IOSUserActivityObserver.swift](../KeeForge/App/IOSUserActivityObserver.swift), [session timer: resetInactivityTimer](../KeeForge/ViewModels/DatabaseViewModel.swift)).
- Mac automatic quick unlock is opt-in, needs Touch ID itself, and starts only on a foreground database opening, native app/window activation, or a screen unlock or session switch back while KeeForge stays active, with a key, visible window and no attached sheet. It rechecks eligibility and the captured lock cycle after activation observers finish; lock-cycle changes alone never raise a prompt. Cancellation and password fallback do not repeat automatically in the same cycle ([MacBiometricAutoUnlock.swift](../KeeForge/App/MacBiometricAutoUnlock.swift)).
- The Require Master Password interval bounds how long saved unlock keys live and are used; it is enforced when the app or AutoFill would read them, not by the Keychain. Its per-database entry date sits in the App Group defaults, so code that can write that container could postpone it. A clock set back past the interval counts as due, but a clock moved back by less shortens the elapsed time ([QuickUnlockKeychain.swift:112](../KeeForge/Services/Security/QuickUnlockKeychain.swift#L112)).
- Automatic Mac biometric unlock requires the registered key database window, excludes restoration, and uses one shared gate to prevent overlapping automatic prompts across windows. Background windows do not consume an attempt.
- Mac background locking defaults to Immediately for the strict policy; an explicit 1, 5 or 15 minute delay leaves sessions open while KeeForge is inactive. Returning within the delay cancels that deadline; returning after it has passed on the wall clock locks, so a timer delayed by App Nap cannot extend it. System screen lock, screensaver, sleep and fast user switching always request locks immediately and invalidate it; the LocalAuthentication hold is unchanged ([MacLockMonitor.swift](../KeeForge/Services/AppSupport/MacLockMonitor.swift)).
- On Mac, Auto-Lock Timeout offers 30 seconds, 1 minute, 5 minutes and Never, and defaults to 5 minutes; Immediately exists only on iOS, and a stored Immediately or no stored value reads as 5 minutes on Mac. Never starts no inactivity timer, and the default lock policy locks only on screen lock, screensaver, sleep or a user switch, so with Never and that policy unlocked databases stay open while the user stays logged in with the screen unlocked, until one of those events or a window close ([AutoLockTimeout](../KeeForge/Services/AppSupport/SettingsService.swift), [DatabaseViewModel.startInactivityTimer](../KeeForge/ViewModels/DatabaseViewModel.swift)).
- On Mac, the Authentication Grace Period defaults to Never Ask while no value is stored (iPhone and iPad default to Always Ask). After an unlock, revealing and copying protected values and releasing browser-bridge fills from that session then need no further device-owner authentication until the grant ends: on every lock request, including one that unsaved work defers, a failed or cancelled prompt, or a new unlock attempt. Under the default lock policy, switching to another app does not end it, so anyone at an unlocked Mac can reveal and copy every protected value of an open database. Always Ask or a bounded period restores the prompt, picking Never Ask needs a new authentication, and an unreadable stored value reads as Always Ask ([AuthenticationGracePeriod](../KeeForge/Services/AppSupport/SettingsService.swift), [SecretAccessGate](../KeeForge/Services/Security/SecretAccessGate.swift)).
- Under the strict Mac auto-lock policy, KeeForge's own system authentication prompt can keep all retained sessions open while unanswered. The monitor checks the foreground application's bundle identifier and system-volume path; another application coming forward requests a lock. After the prompt ends, KeeForge has two seconds to reactivate before locks are requested for all retained sessions. Screen lock, sleep, screensaver, session resignation, window closure, and inactivity locking still apply ([MacLockMonitor.swift:304](../KeeForge/Services/AppSupport/MacLockMonitor.swift#L304), [prompt completion:320](../KeeForge/Services/AppSupport/MacLockMonitor.swift#L320)).
- On iOS, a shield covers the app while it is in the background, including the app switcher's snapshot, and while the screen is recorded, mirrored, or AirPlayed, including while Face ID, Control Center, or notifications briefly report the capture as over and after the app becomes active again; while it is up it takes touches and closes the keyboard ([ScreenProtectionService.swift](../KeeForge/Services/Security/ScreenProtectionService.swift)). Turning off Hide During Screen Recording and Sharing (on by default) leaves the app, and anything it shows, visible to recording, sharing, mirroring, and AirPlay; the setting needs no authentication, like other app settings, and the background and app switcher shield stays. It relies on iOS reporting the capture, cannot cover what an overlay shows above it, and cannot stop a camera pointed at the screen. Screen-capture blocking on Mac is best effort, not a boundary against Screen Recording or Accessibility permission. Mac clipboard concealment is advisory and cannot prevent Universal Clipboard; a quit through `applicationShouldTerminate` clears a still-owned copy, but a force quit, crash or kill leaves it, since the clear timer dies with the process. iOS uses local-only pasteboard items that expire unless Clipboard Clear Timeout is Never; with Never, a copy the app made stays until a lock other than backgrounding or a later copy, and the verification code the AutoFill extension copies stays until a later copy, since the extension has no lock. Preview deletion is not secure erasure, and receiving apps may retain copies ([ClipboardService.swift:23](../KeeForge/Services/AppSupport/ClipboardService.swift#L23), [Mac clipboard:81](../KeeForge/Services/AppSupport/ClipboardService.swift#L81), [Mac screen privacy](../KeeForgeMac/SECURITY.md#screen-and-clipboard-privacy)).
- Network protection depends on the selected provider. WebDAV requires HTTPS by default, allows explicit HTTP opt-in, and refuses cross-origin redirects. FTP uses plaintext TCP, exposing its login and traffic metadata to the network; KDBX encryption protects vault contents, not transport credentials ([WebDAVURL.swift:19](../Packages/RemoteFileTransports/Sources/RemoteFileTransports/WebDAVURL.swift#L19), [WebDAVClient.swift:288](../Packages/RemoteFileTransports/Sources/RemoteFileTransports/WebDAVClient.swift#L288), [FTPClient.swift:128](../Packages/RemoteFileTransports/Sources/RemoteFileTransports/FTPClient.swift#L128)). The native Mac Connect sheet serves both launcher and Reconnect, blocks Cancel while connecting, clears passwords on end and late results, and shows both FTP warnings while plaintext FTP is allowed. - Cloud conflict protection differs by provider. FTP lacks atomic conditional writes. OneDrive overwrites above 4 MiB use upload sessions whose `If-Match` check occurs at session creation rather than commit, leaving a window for a concurrent remote write to be replaced ([FTPCloudProvider.swift:179](../KeeForge/Services/Cloud/FTPCloudProvider.swift#L179), [OneDriveCloudProvider.swift:682](../KeeForge/Services/Cloud/OneDriveCloudProvider.swift#L682)).

- Current code enables WebDAV and FTP on Mac, with Dropbox, OneDrive and Google Drive additionally available on iOS builds that opt in and configure OAuth ([CloudSyncModels.swift:60](../KeeForge/Services/Cloud/CloudSyncModels.swift#L60)); the maintained Mac security document agrees.

### Local replacement and key recovery

Unconfirmed/planned target evidence, source admission, key publication, retirement
and revocation remain fail-closed. A ready-to-retire certificate is established only
after target/association/required-source settlement, with durable new owner epoch
before withdrawal. Certified replay can finish owner CAS without a permanent target
SHA check; planned/unconfirmed replay cannot. Fully durable retirement deliberately
restores main's external restore/open/conflict behavior: no permanent cryptographic
antirollback protection is claimed. Source epochs and tombstones still fence stale
actors and preserve later ciphertext.

Local cache reads capture reference/epoch before IO. Scanner, healing/relink,
migration, creation and VM publication recheck current reference, actual bytes,
epoch and revocation under list lock → original/cache coordination → owner flock.
Recovery ciphertext and pending sources cannot be replaced by an older read or
recreated after removal. Idle key-file preferences update only current registry
fields; actual pending association intents retain their exact desired-field CAS.
No password/key-file bytes/session key/XML enter owner records.

A single authenticated ciphertext may remain in session RAM and clears on lock or
new unlock. Explicit encrypted draft export is independent of owner availability,
verifies the reopened full document/pool off main and never clears edits or grants
cleanup permission. Active recovery prevents destructive conflict reload/merge;
normal conflict actions resume after settlement. Native file grants, UI and physical
durability remain separate validation requirements.

### Effective resource inventory

Container paths below are relative to the OS-resolved location, not fixed device paths. They describe production behavior. Injected unit tests instead use `<temporary directory>/KeeForgeUnitTestAppGroup/group.com.keevault.shared` and the `group.com.keevault.shared.unit-tests` defaults suite. In production, failure to resolve the group directory falls back to the process temporary directory; defaults independently fall back to standard defaults if the suite is unavailable ([AppGroupContainer.swift:37](../KeeForge/Services/Persistence/AppGroupContainer.swift#L37)). Neither fallback guarantees app/extension sharing.

Pending local AutoFill snapshots also live under `pending-local-saves/<database UUID>/`.
New sources have an exclusive UUID parent and an unchanged timestamp `.kdbx` name;
legacy flat sources remain readable. `pending-local-save-owners/<database UUID>/`
contains a stable lock, permanent removal tombstone and versioned nonsecret retirement
receipts (relative identity, inode and SHA-512). Database removal revokes late local
writes before registry mutation and refuses to erase unresolved sources implicitly.
The coordinated replace holds this owner lock through its final receipt/revocation
check and replacement; the owner never takes the database-list lock. Partial source
retirement remains a recovery requirement, including missing payloads. Exact encrypted
source export is available without unlocking; destructive discard needs a separate
snapshot-specific confirmation and never follows from export failure. App Group denial
or unknown owner metadata blocks mutation instead of using the temporary fallback.
Source preparation persists a provisional owner before publishing ciphertext; shared-copy
installation and activation are distinct effects. Merge admission precedes its saver,
and surviving admission prevents automatic reencryption, including of later sources.
Known committed outcomes retain installed keys and SHA despite failed final sync or
coordination; unknown outcomes retain recovery ownership. Exact target re-observation
and durable removal of admitted sources precede idle publication. A visible idle
rename whose final sync fails is reported as bookkeeping uncertainty, not rollback.

Local master-key publication has its own barrier and a durable field-specific
association receipt. Epoch settlement retains exact new-target identity/SHA and any
unconfirmed target durability; later mutations reconfirm visible owner metadata under
flock and reject rollback/missing/foreign targets and incompatible associations. Late
old-epoch sources stay retained and ineligible. Valid encrypted reads, receipt exports
and an unlocked session's verified encrypted draft export remain separate from mutation
permission. Draft export keeps edits and uses the unlocked session's key; failed export
never authorizes destructive discard. Abandoning key publication revokes writes without
undoing an installed change. Native save completion and identity publication are withheld
on warnings; lock-cycle guards still prevent secret restoration.

These controls do not make database-list writes transactional or establish physical
power-loss behavior ([PendingLocalSaveStore.swift](../KeeForge/Services/Persistence/PendingLocalSaveStore.swift)).

## Cloud creation journal

New cloud databases and remote conflict copies retain encrypted payloads and nonsecret destination, reference and attempt metadata before create-only dispatch. An attempting record prevents an uncertain request from being sent again; only that request's response can supply a receipt. A known receipt permits local registration of a new database, while a conflict copy completes without changing the database list or the original. Dismissal stops a late response from registering through the dismissed creation flow. Cloud Recovery can export the exact encrypted payload, retry or explicitly discard an unchanged prepared record, and finish local work for confirmed receipts. Discard rechecks the exact record under its target and operation locks before deleting its encrypted copies. Attempting records cannot be retried or removed from that screen; they may represent a creation that succeeded remotely. The journal stores no passwords, keys or tokens ([CloudFileCreationCoordinator.swift](../KeeForge/Services/Cloud/CloudFileCreationCoordinator.swift), [PendingUploadQueue.swift](../KeeForge/Services/Cloud/PendingUploadQueue.swift)).

FTP can prove a creation conflict before the target rename; the prepared payload remains recoverable, and a conflict copy can try a numbered name after rechecking session authority. A failure during or after rename remains uncertain. FTP cannot prevent another client from creating the destination between its final check and rename.

## Cloud replacement journal

The cloud pipeline retains immutable encrypted KDBX snapshots and nonsecret intent/attempt/receipt metadata in the App Group before provider mutation. The pure journal policy gates admission and dispatch; adapters perform IO. Remote equality, a changed revision, an absent file, cancellation or timeout cannot prove that an earlier request has stopped. An uncertain dispatched request remains a fence and is not automatically resent. Confirmed responses support local reconciliation without provider mutation. An initiating unlocked session may retain the new composite key and key-file data in memory while a confirmed rekey awaits reconciliation. Ordinary cloud saves also bind optional express-key effects to their own preselected operation and output digest, original target and session action. A weak operation-scoped completion ticket carries no secret; the session must independently validate its action, lock cycle, target, epoch, operation and installed cache through the key-publication fence. Lock, retirement, competing authority or mutation clears the context, and unknown outcomes never authorize publication. Marker retirement synchronizes its namespace before deleting payloads. Explicit Z/A/B reconciliation authenticates the captured pending snapshots and remote bytes before a single-use RAM context can authorize replacement of the exact current cache. Cache coordination, immediate reference/commit-lock checks and local owner fencing remain held through replacement and exact source ownership transfer; remote baseline proof remains separate. The context carries no persisted state or Keychain permission, and changed/new sources or unconfirmed effects retain recovery ownership. Cloud-open metadata CAS rejection preserves historical authentication authority instead of importing a newer reference into older bytes; the final key-publication fence remains independent of readable snapshot access. Fresh authentication after full settlement does not inherit an obsolete invocation's restriction. A merge's enqueue notification is emitted after its owned source handoff exits all locks, preventing its own drainer from competing for that unfinished lease. Independent contention still fails closed; neither observation nor notification creates retry permission. Cleared reconciled validators require a remote byte check even if the baseline equals the local predecessor; an older reference hash cannot authorize overwrite by that equality.

New journal bindings capture the exact original cloud identity, operation, factor-preference fingerprint and head/epoch/date without copying keys or credentials. A confirmed rekey rechecks the bound marker and its original baseline, or its exact already-installed epoch, head, association and cache hash, under combined cache and registry coordination and immediate owner locks before deleting old keys or replacing cache. Before retirement, the same owner lock advances an idle pending-local epoch only after the exact installed rekey proof and durable registry publication; unresolved sources or key evidence prevent that handoff. Unconfirmed publication retains the journal and known ciphertext; unbound legacy data grants no automatic delivery authority. Authenticated legacy merge and export compatibility require their own verification and are not established by retaining bytes alone.

Delivery of an existing ordinary journal can tolerate a later read-only preference while retaining its bound cloud identity, factors and epoch; rekey authority remains strict. Legacy data without a known phase may be surfaced for recovery without gaining upload authority; a false-phase marker remains unchanged.

Explicit remote reads during pending delivery use a temporary encrypted snapshot and cannot replace the pending cache. Merge binds the exact authenticated remote baseline and source snapshots into a durable output before conditional source retirement. Confirmed journals cannot be removed by discard; only confirmed reconciliation owns that retirement. Cloud-open metadata CAS does not overwrite a newer epoch/reference, and a queued cache commit defers optional express-key effects without repeating encryption.


A journal decode/IO failure does not prevent reading valid cached credentials, but blocks mutation and key publication. Cache and Keychain effects validate current reference/epoch, target bytes and local revocation inside coordinated ownership. Stale parse/save callbacks cannot authorize their keys merely because their own session remains unlocked. After complete settlement, fresh authenticated restores retain the normal product behavior; no permanent cryptographic antirollback guarantee is added.

Provider limits remain: Google Drive has a window between its final revision and checksum check and commit. The revision history may omit evidence, and overwritten remote bytes may require the other device’s copy. FTP and weak WebDAV validators offer preflight checks, large OneDrive upload sessions do not enforce the final commit revision, and an acknowledged provider write is not a physical-storage durability proof. Dropbox and OneDrive replacement content uploads do not retry at the application layer after uncertainty; shipped create-only behavior is unchanged. URLSession or an intermediary may retry a PUT after a lost response, so a later WebDAV or OneDrive rejection does not prove the earlier request failed. FTP preflight mismatch can fence its own attempt before target installation; FTP post-install errors, generic transport errors and lost content responses remain uncertain. Shared registry serialization remains process-local outside the explicitly fenced cloud transactions; this draft does not implement global cross-process registry CAS. Cloud key publication performs coordination, hashing and keychain-only effects on the shared off-main worker. Cancellation or a deadline closes unclaimed permission; an already-claimed effect may finish later under its original authority, so timeout never proves no effects. Native recovery presentation, provider integration and power-loss behavior have not been established by static checks.

Automatic cloud key-file bookmark renewal defers while a pending upload exists, under the same commit lock used to publish upload intent. This keeps the bound preferences stable without preventing use of the resolved key-file URL. Explicit selection can rebind ready ordinary markers under that lock: each marker records authority for both the current and selected preference before the registry changes, and retires the old authority after confirmed publication. A partial transition blocks delivery until the current registry is durably reconfirmed and its matching authority retained. Uncertain, legacy and key-changing markers still require recovery; a new selection cannot settle an unknown remote outcome.

## Severity calibration (Critical, High, Medium, Low)

Severity applies to a validated failure with a demonstrated trust-boundary crossing. Impact, reachability, confidence, and missing evidence should be recorded separately.

| Severity | Example if validated | What would reduce or invalidate that assessment |
| --- | --- | --- |
| Critical | A broadly reachable update-verification bypass or remote exploit that enables large-scale extraction of unlocked vault secrets | Control of the already-trusted release-signing environment is a different prerequisite; replacing an appcast alone does not establish a signature bypass. |
| High | Authentication bypass releasing vault contents, cross-RP passkey use, or exploitable code execution from a vault opened through an ordinary supported flow | The attacker must gain access they did not already have. | Medium | Attacker-triggered recoverable vault unavailability, meaningful metadata leakage beyond the selected feature, or a write race that loses data under realistic conditions | Scope, required user actions, recoverability, and backups matter. | Low | Limited unintended non-secret disclosure or a minor security-relevant behavior with constrained impact | Authorized copying, expected optional favicon disclosure, and documented platform behavior alone are not vulnerabilities. |

subsequent shared-cache refresh/invalidation retain the actual resolved bookmark
scope while continuing to validate the installed identity and ciphertext. Read-key
workers separately report observed no-claim termination; a timeout, cancellation
or claimed effect cannot be treated as that proof to reopen AutoFill actions.
Session factors are applied before the unlock publication await, and later work
requires the same action identity even when a concurrent rekey keeps the lock cycle.

An early session update from a known local rekey receipt does not advance the
registry observation used to remove legacy metadata. Cleanup uses the captured
pre-save observation with the existing field CAS after the fenced Keychain effect;
a later registry change can reject cleanup without undoing or repeating that effect.

Auxiliary no-renew local resolution is also no-heal: it does not create ownership
state, rebind Documents references or reseed caches. Valid moved locations remain
readable; known Trash remains distinct from unavailable. The shipped default heal
is retained without claiming a durable registry transaction or issuing a renewal
receipt. Actual authenticated read renewal keeps its historical reference through
the final fence and applies only the same action’s bookmark after authorization.

A durable bookmark renewal cannot precede a source-restricted final publication:
its owner admission requires no recorded or filesystem sources in addition to the
existing idle/epoch/revocation checks. Deferral preserves valid file reading and
leaves the reference unchanged; it neither authorizes stale keys nor releases
source/admission barriers. Default heal remains the separately documented limit.

A source can arrive after bookmark-renewal admission. Read-key publication still
rejects that window. A bookmark-only reconciliation may preserve the same read’s
durable transition after exact authenticated target/reference/epoch checks, accepting
only verified eligible sources. Session action/cycle checks prevent late RAM promotion;
merge obtains new ownership and a new installed receipt. Failed proof retains sources
for explicit recovery and never adopts another actor’s current factors or epoch.

A local merge keeps its actual bookmark grant through installed-target bookmark
publication, exact source retirement and cache refresh. The field publisher is
coordinated with the new target and owner admission; a receipt’s canonical path is
never access authority. Its RAM-only completion prevents a late VM callback from
repeating retirement. An explicit same-session mutation can reconcile only its
own authenticated pending renewal after revoking the old read-key permission;
current target/reference/epoch checks and session lifecycle guards still apply.

Local-save recovery is exposed in iOS Database Details and native Mac Database Settings, including while locked. They share receipt-bound source export, confirmation wording, and explicit key-publication recovery. Mac export writes encrypted bytes directly to the chosen save-panel destination. A committed or unknown security-settings result replaces Save with Done; acknowledging it does not repeat encryption or replacement.

Native Mac cloud-creation recovery remains reachable from the Databases window even when no reference has been registered. This opens the same phase-specific recovery surface used on iOS; reaching it does not grant retry, registration, overwrite or discard authority.

An FTP creation failure before the target rename, including session setup, retains a prepared recovery record. Failures once rename starts remain uncertain because the target may have changed.
