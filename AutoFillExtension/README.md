# AutoFillExtension

This target provides password, passkey, one-time-code, and new-credential save/generate fulfillment through `AuthenticationServices`.

## Main Files

- `CredentialProviderCoordinator.swift` is the platform-neutral core: request handling (passwords, passkeys, one-time codes, save/generate-password), vault access and unlock orchestration, credential matching, passkey assertion, and the `cleanup()` teardown lifecycle. It must stay free of UIKit/AppKit so both the iOS and macOS shells can host it unchanged; it talks to the shell only through the narrow `CredentialProviderPresenting` protocol ("present this view", "ask this question", "complete with this credential/error").
- `CredentialProviderViewController.swift` is the thin iOS shell and extension entry point (whole file is `#if os(iOS)`): it forwards system requests to the coordinator, hosts the SwiftUI views in `UIHostingController`s, shows `UIAlertController` prompts, and relays completions/cancellations to the extension context. No matching or vault logic lives here.
- `CredentialProviderViewControllerMac.swift` is the macOS shell (`#if os(macOS)`). On macOS `ASCredentialProviderViewController` subclasses `NSViewController`, so this shell hosts `AutoFillSearchView` in an `NSHostingController`, shows `NSAlert` prompts for unlock / error / read-only, and sets `preferredContentSize`. It routes **every** completion, cancel, `NSAlert` dismissal, and window close (`viewDidDisappear` → `cancelActiveRequestIfNeeded()`) back through the coordinator so `cleanup()` always runs — window close has no iOS analogue. `viewDidAppear` must hand the coordinator its cue on a *later* main-loop turn, never synchronously: AppKit calls it from inside the window-ordering transaction and suppresses any `NSAlert.runModal()` started there, which silently turns the unlock prompt into a cancel. Extension-context calls go through a small `CredentialProviderRequestCompleting` seam so the shell's cleanup routing is unit-testable without the system harness.
- `AutoFillSearchView.swift` renders the searchable SwiftUI UI shown inside the extension (shared by both shells).
- `AutoFillEntryCreatorView.swift` renders the credential-creation UI used for save-password requests, strong-password generation follow-up, and picker-initiated creation. It is `#if os(iOS)` because save/generate-password are iOS-only (see capability notes below). Its `allowsPasswordEditing` flag separates the two callers: save-password requests carry the password the site already received, so the field stays disabled there; the picker-initiated flow unlocks it and adds a generate button (shared `PasswordInputRow`, so reveal comes with it).
- `AutoFillPasskeyCreatorView.swift` renders the shared passkey-registration confirmation UI (relying party, username, target database, editable title).
- `Localizable.xcstrings` — String Catalog (source language `en`, plus `de`, `fr`, `es`, `zh-Hans`, and `zh-Hant`) for both AutoFill extension targets.
- `InfoPlist.xcstrings` — localized Info.plist values (e.g. `CFBundleDisplayName`) for both AutoFill extension targets.
- `PrivacyInfo.xcprivacy` — Apple privacy manifest for both extension targets. The extensions collect nothing and make no network requests; the required-reason declarations (UserDefaults, file timestamps) come from allow-listed shared sources (`SharedVaultStore`, `SettingsService`, `FaviconService`). Revisit it when the allow-list changes.

## How It Works

- The extension resolves each request's target database through `../KeeForge/Services/Persistence/DatabaseListStore.swift` and reads the shared cached database copy from the App Group container. Requests that carry a record identifier (QuickType tap, silent fill, passkey/one-time-code by identity) unlock the database that owns the identity; identifier-less flows (manual search, save) use `DatabaseListStore.defaultAutoFillDatabase`. Databases with AutoFill disabled are treated as nonexistent, stale identities are cleaned up on tap, and with zero enabled databases the shells show `AutoFillNoEnabledDatabasesView` instead of an unlock prompt.
- **Proactive suggestions do not aggregate across databases on macOS.** `ASCredentialIdentityStoreState.supportsIncrementalUpdates` is false there (verified against a real enabled provider on macOS 26.5), which makes `saveCredentialIdentities` mean "pass all credential identities" and `removeCredentialIdentities` unsupported; store enumeration is unusable too, returning nothing or private `SFPasswordCredentialIdentity` objects with no readable `recordIdentifier`. So on macOS the system store holds exactly one database's identities — the most recently unlocked AutoFill-enabled one — and Safari suggests from that database alone. Record identifiers are still tagged and still resolve, so a tapped suggestion unlocks its owning database; the switcher below and `defaultAutoFillDatabase` are how the others stay reachable. `CredentialIdentityStoreManager` gates on the runtime flag rather than `#if os(macOS)`, so aggregation lights up on its own if a release starts reporting incremental support. The macOS AutoFill settings screen states the limit whenever more than one database is selected.
- With two or more AutoFill-enabled databases, `AutoFillSearchView` shows a toolbar database switcher (`CredentialProviderDatabaseSwitcherContext`, built by the coordinator). Picking another database runs its standard unlock flow and re-presents the same request against it; the previous database's vault state is retained until the new unlock succeeds, so cancelling the switch falls back to the previous database instead of ending the request.
- It reuses `../KeeForge/Models` plus a selected subset of service files declared explicitly in `../project.yml`.
- The shared model layer links the local `KeeForgeTwofish` package, so Twofish-encrypted databases use the same parser and cipher-preserving writer in the app and extension.
- Unlock can use stored composite keys plus biometrics for quick AutoFill, or fall back to interactive password entry.
- The identity-store mutation queue is process-local. The app and extension are separate processes, so their system-store operations can overlap; refreshes must stay idempotent and tolerate identities without the newer `recordIdentifier` Objective-C accessor returned by some macOS system objects. Those opaque identities are preserved conservatively; **Clear AutoFill Entries** in KeeForge removes them manually.
- Internal iOS modal dismissal is not request cancellation. Request generations invalidate late unlock continuations, and terminal completion or cancellation is delivered exactly once.
- Interactive requests are presentation-order independent: the coordinator waits while the shell is off screen and schedules pending UI as soon as it appears. Post-unlock presentations (picker, creators, alerts) route through `presentWhenActive`, which defers to the next `presentationDidBecomeActive()` when the shell is off screen (e.g. an unlock finishing while the biometric sheet is still handing back), so a successful unlock always ends in a completed credential or presented UI, never a dropped modal.
- Password and passkey requests both parse the database locally; the extension does not depend on the main app being open.
- `completeRequest(with:)` resolves KeePass `{REF:…}` field references in the filled username and password through `../KeeForge/Models/FieldReferenceResolver.swift`, built over `parsedRootGroup.allEntries` rather than `parsedEntries` because the referenced entry may be password-less or in a non-searchable group. The picker rows and QuickType identities still show the raw text; the write paths (`makeURLAdditionDraft`, save/creation drafts) never resolve.
- Expired entries are excluded from proactive identities and automatic password, passkey, and one-time-code fulfillment. They remain available in the interactive picker with an explicit warning and require a manual tap.
- One-time-code and password identities are published at different granularities: password identities collapse to the registrable domain (eTLD+1); one-time-code identities keep the entry URL's exact host, so an OTP field on `vt.example.com` is not answered with every entry under `example.com` (#70). Matching follows suit: `CredentialMatcher.orderedStrictMatchedEntries` walks the requested service identifiers in Apple's order (index 0 is most specific), returns exact-host matches ahead of child subdomains, and stops at the first identifier that matches anything. A single result fills without a picker; anything else goes to the picker, still populated from the broad `matchedEntries` set so URL/title substring candidates stay reachable — those are never filled without an explicit tap.
- Groups whose KDBX `<EnableSearching>` resolves to false are skipped entirely by the proactive identity store and the extension's own entry list. The filtering lives in one place, `KPGroup.autoFillEntries(excludingGroupID:inheritedSearchingEnabled:)`, called by all three AutoFill entry sources — `DatabaseViewModel.credentialStoreEntries`, `AutoFillSaveCoordinator.credentialStoreEntries`, and the coordinator's own parse. In-app search honors the same flag; browsing and the tag browser still show the group and its entries.
- Opt-in "Copy Verification Code on AutoFill" (`SettingsService.autoFillCopyTOTP`, App-Group-shared, default off): when a filled password entry also has a TOTP config, `completeRequest(with:)` generates the current code and copies it via `../KeeForge/Services/AppSupport/ClipboardService.swift` before `cleanup()` drops the session key. The copy goes through the coordinator's injectable `copyToClipboard` seam and inherits the App-Group-shared Clipboard Clear Timeout as a `UIPasteboard` expiration date, so it expires after the extension is gone. iOS only (`#if os(iOS)`): the macOS `ClipboardService` branch clears via an in-process timer that dies with the extension. The toggle lives in Settings → AutoFill (identifier `settings.autofill.copy-totp`). Because a no-UI extension cannot reliably write the pasteboard, `provideCredentialWithoutUserInteraction` escalates to `.userInteractionRequired` instead of filling silently whenever the setting is on and the chosen entry has a verification code.
- Save-password requests prefill a new entry via `../KeeForge/Services/AutoFill/AutoFillSaveCoordinator.swift`, save encrypted bytes through `../KeeForge/Services/Persistence/LocalDatabaseSaver.swift`, and enqueue `../KeeForge/Services/Cloud/PendingUploadQueue.swift` markers for cloud-backed databases before returning success.
- The password picker can also create an entry outright (#46), for the signup case. `AutoFillSearchView` shows the action only when the coordinator hands it a non-nil `onCreateEntry`, which `makeEntryCreationAction()` withholds unless the request is on iOS, against a writable non-KDBX-3.1 database, and carries a service identifier to derive the name and URL from — so passkey and one-time-code pickers stay selection-only. The draft comes from the same `AutoFillSaveCoordinator.initialDraft(for:username:)` the save-password path uses (generated password, no username). Save-password finishes with `completeSavePasswordRequest`; picker creation completes with an `ASPasswordCredential` built from the confirmed draft, so the originating form is filled. Both publish to QuickType via `saveNewEntry`, which repopulates the credential store on success.
- New entries land in `AutoFillSaveCoordinator.saveNewEntry`'s default group, `rootGroup.groups.first` — the real top-level group, never the synthetic KDBX Root (writing into Root corrupts databases for other KeePass apps; cf. keepassium/KeePassium#476). There is no group picker and no dedicated "AutoFill" group.
- Passkey registration (iOS and macOS): `prepareInterface(forPasskeyRegistration:)` mirrors the save-password flow (default AutoFill database, read-only and KDBX 3.1 rejection, deferred alerts) and, after unlock, cancels with `.matchedExcludedCredential` when an excluded-credentials descriptor matches a stored passkey for the relying party. Confirmation runs through `AutoFillPasskeyCreatorView`; the entry stores the KeePassXC `KPEX_PASSKEY_*` custom fields (secrets Protected) built by `../KeeForge/Services/Security/PasskeyCrypto.swift` (ES256 only). Ordering invariant: the database is saved first and `completeRegistrationRequest` runs only after the save succeeds, so the relying party never receives a credential that was not persisted.
- The picker can always fall back to the full list. `AutoFillSearchView` starts narrowed (matches, sibling-subdomain suggestions, or a coordinator-prefilled domain search) while `searchEntries` carries the whole fillable corpus; whenever the narrowing hides part of `searchEntries` it offers "Show All Credentials" (see `canShowAllEntries`), which matters most when matching finds nothing and the prefilled domain search renders an empty list. The action is view-local state, not a coordinator concern, and disappears on pickers whose `entries` already are `searchEntries` (passkey, single-entry).
- Password search keeps exact matches separate from possible sibling-subdomain matches. Registrable-domain boundaries use the embedded Mozilla Public Suffix List from the `ameshkov/swift-psl` package, shared by both AutoFill extension targets.

## Platforms And Targets

- Two extension targets share this folder: `KeeForgeAutoFill` (iOS, embedded in `KeeForge`) and `KeeForgeMacAutoFill` (macOS, embedded in `KeeForgeMac`). Both pull in `CredentialProviderCoordinator.swift` plus a shared allow-list of service/view sources (see Change Carefully). `MARKETING_VERSION` is in lockstep: all four product targets carry the same version and build number, and one release bump covers them together.
- `CredentialProviderCoordinator.swift`, `CredentialProviderViewControllerMac.swift`, and `AutoFillSearchView.swift` are also compiled into the `KeeForgeMac` app target so `KeeForgeMacTests` can unit-test the coordinator and the mac shell lifecycle. The coordinator alone is compiled into the iOS `KeeForge` app target (the iOS shell is not unit-hosted).
- Mac Info.plist is `InfoMac.plist`; mac entitlements are `AutoFillExtensionMac.entitlements` (both excluded from the iOS target's source glob so they are not bundled as stray iOS resources). `KeeForgeMacAutoFill` sets `ENABLE_HARDENED_RUNTIME: YES` with **zero** `com.apple.security.cs.*` exceptions. Its `keychain-access-groups` list mirrors the iOS `AutoFillExtension.entitlements` order exactly (single shared group); MSAL's keychain group is app-only and intentionally absent.

## macOS Capability Notes (macOS 26.5 SDK, verified against AuthenticationServices headers)

- **Passwords + passkeys**: advertised via `ProvidesPasswords` / `ProvidesPasskeys` in `InfoMac.plist`.
- **One-time codes**: advertised via `ProvidesOneTimeCodes`. `ASOneTimeCodeCredential`, `ASOneTimeCodeCredentialRequest`, and `completeOneTimeCodeRequest(using:)` require macOS 15, which is the Mac app and extension's deployment floor.
- **Save-password / generate-password**: `ASSavePasswordRequest`, `ASGeneratePasswordsRequest`, `ASGeneratedPassword`, `completeSavePasswordRequest`, and `completeGeneratePasswordRequest` are `API_UNAVAILABLE(macos)` on every macOS version. The coordinator's save/generate surface is `#if os(iOS)`; the mac shell's `presentEntryCreator` / `presentGeneratedPassword` / `completeSave…` / `completeGenerate…` are unreachable stubs. `Supports*PasswordCredentials*` keys are omitted from `InfoMac.plist`.

## Change Carefully

- Keep dependencies extension-safe. If the extension needs another service file, add it explicitly to **both** the `KeeForgeAutoFill` and `KeeForgeMacAutoFill` allow-lists in `../project.yml` (same path, same position — the two lists are order-locked and must stay byte-identical; see the "SHARED AUTOFILL ALLOW-LIST (maintenance invariant)" markers there).
- Mind the extension memory budget: AutoFill extensions get a system memory limit far below the app's, yet this one parses full KDBX files and runs Argon2 in-process. Two layers guard the KDF side. `loadEntries` pre-flights each unlock through `../KeeForge/Services/AutoFill/AutoFillMemoryLimit.swift`, comparing the header's Argon2 memory parameter against `os_proc_available_memory` and throwing before derivation starts; it rejects only what is certain to fail on this device, and the error surfaces through the ordinary `showErrorAndRetry` alert (the silent QuickType path escalates to `.userInteractionRequired` first) — retry cannot succeed and the message says so. Behind it, the coordinators pass `KDFExecutionPolicy.autoFillExtension` to every parse/save: a static ceiling on hostile KDF headers whose peak-memory bound sits well above any real extension allowance (so it never refuses a vault the runtime check or the app would allow) plus the shared total-work and parallelism budgets; it is also the only memory guard on macOS, where `os_proc_available_memory` does not exist. Beyond the KDF, avoid extra copies of decrypted payloads and anything that raises peak memory — large databases are the usual suspect.
- Keep `CredentialProviderCoordinator.swift` free of UIKit/AppKit imports and types. It is compiled into the `KeeForge` and `KeeForgeMac` app targets (see `../project.yml`) so `../KeeForgeTests/CredentialProviderCoordinatorTests.swift` can unit-test it (the only copy — `KeeForgeMacTests` has no folder of its own and compiles the same `KeeForgeTests` sources against the mac app host).
- Every completion path (success, user cancel, error alert dismissal, silent-request failure) must funnel through the coordinator's completion helpers so `cleanup()` — the extension's only "lock" — always clears the session key and parsed vault state.
- In passkey registration, keep the save-first-then-complete ordering: never call `completeRegistrationRequest` before the database save has succeeded, and never leave a registration request unanswered (bad cast / missing clientDataHash / no ES256 must still cancel with `.failed`).
- Changes to App Group storage, shared defaults, cached database copy semantics, or Keychain semantics usually affect both targets.
- Relevant tests are usually in `../KeeForgeTests/CredentialProviderCoordinatorTests.swift`, `../KeeForgeTests/CredentialProviderSaveTests.swift`, `../KeeForgeTests/CredentialProviderPickerCreationTests.swift`, `../KeeForgeTests/CredentialProviderRegistrationTests.swift`, `../KeeForgeTests/CredentialProviderShellMacTests.swift` (mac shell lifecycle, `KeeForgeMacTests` only), `../KeeForgeTests/CredentialIdentityStoreManagerTests.swift`, `../KeeForgeTests/CredentialMatcherTests.swift`, `../KeeForgeTests/PasskeyTests.swift`, and `../KeeForgeTests/SharedVaultStoreTests.swift`.
