# KeeForge browser extension

Manifest V3, plain JavaScript (classic content script, ES modules elsewhere), no packages. Requires Chrome-family 133+ or Firefox 130+ (WebCrypto X25519). Run `env -u NODE_USE_SYSTEM_CA node --test` here; `tools/build.sh` reads the marketing version in `../project.yml` and writes deterministic `build/chrome.zip`, `build/firefox.zip` and unpacked directories. Python 3 and Node with WebCrypto X25519 are needed for development. The root `.gitignore` already ignores `build/` directories.

## Load for development

Run `tools/build.sh`. In Chrome enable Developer mode at `chrome://extensions`, choose Load unpacked, and select `build/chrome`. In Firefox open `about:debugging#/runtime/this-firefox`, choose Load Temporary Add-on and select `build/firefox/manifest.json`. The manifest's development `key` gives the unpacked Chrome copy a fixed ID (see Development ID below); the store-assigned Chrome ID is added to the native-host allowlist later.

Both archives use the same permissions and resources; the Firefox build removes Chrome-only `world` and `use_dynamic_url` keys (Firefox content scripts are isolated by default). Chrome 121+ ignores `background.scripts` and runs `background.service_worker`; Firefox uses `background.scripts` as an event page. Both support `background.type: "module"` at our minimum versions (Chrome 92+, Firefox 112+). See [MDN background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background) and [Mozilla compatibility data](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/background.json). [X25519 compatibility](https://github.com/mdn/browser-compat-data/blob/main/api/SubtleCrypto.json) sets the higher browser minimums. Real-browser verification is separate from the Node suite; see Real-browser checks below.

## Manual native mock

`tools/mock-host.mjs` is a real stdio native-messaging host backed by `test/mock-app.js`. It does no network I/O and writes only framed protocol objects on stdout. It automatically allows pairing and serves disposable demo credentials. Options: `--decline`, `--busy`, `--pending`, `--locked`, `--empty`, `--mixed`, `--hold-credential`, `--unavailable` (a mock `launch` makes it available). `unlock` is acknowledged but does not unlock, like the real app until the user unlocks there. App keys and registered clients last only for the host process; after it exits, pair again. With `--control <dir>` (used by the inline browser check) the mock instead keeps its app key and pairings in `<dir>/identity.json` across processes, reads `<dir>/state.json` (`available`, `scenario`, `credentialDelay` in ms) on every frame so a test can lock, unlock, stop or start the "app" live, ignores `launch`, and appends every frame and decrypted request type/origin to `<dir>/log.jsonl`. To exercise persistent pairing, use a debug build of KeeForge with the browser set up in Settings ▸ Browsers. Do not use the mock with real vault data.

`tools/e2e-client.mjs --host <path>` drives this extension's `Connection` against a real host binary over pipes, one JSON command per stdin line and one JSON result or event per stdout line; The host gets only a browser's environment (`PATH`, `HOME` from the user database, `USER`, `LOGNAME`, `SHELL`, `LANG`). `KeeForgeMacUITests/MacBrowserBridgeUITests` starts it through `tools/e2e-client-launcher.sh` with the host embedded in KeeForge.app.

`tools/e2e-browser.mjs --host <path> [--browser <path>] [--domain <name>]` is the browser half of `KeeForgeMacUITests/MacBrowserExtensionUITests`, started through the same launcher. It loads this directory with `Extensions.loadUnpacked` into a disposable headless Chromium (the manifest key gives `pihelgeaeflnpjjdajbdmfmcpgeoefbf`), writes `com.keevault.browser.json` for that host only into the temporary profile's `NativeMessagingHosts` folder (Chrome reads per-user hosts from `<user-data-dir>/NativeMessagingHosts`), and serves `test/pages/inline.html` as `https://<domain>` (default `alpha.example.com`) through `--host-resolver-rules` to a loopback port with a throwaway certificate pinned by `--ignore-certificate-errors-spki-list`. Chrome starts with the same minimal environment, so it launches the host as a browser would. Commands (one JSON line each, with `id`; replies `{id, done, result}` or `{id, done: false, error, message}`): `probeHost`, `start`, `openLogin`, `clickKey {field}`, `menuState`, `waitMenu {state, title?, timeout?}` (states `unpaired`, `locked`, `app-unavailable`, `empty`, `error`, `loading`, `logins`), `menuPair` (returns the pairing tab's code), `waitPaired`, `menuUnlock`, `menuFill {title}`, `fields` (password inputs as length and SHA-256 only), `clearFields`, `closeMenu`, `popup` (width and rows), `screenshot` (base64 PNG) and `quit`. Browser search: `--browser` or `KEEFORGE_E2E_BROWSER` used as given, else standard Chromium apps in `/Applications` and `~/Applications`, else Chrome for Testing under `~/Library/Caches/KeeForge-E2E` (`npx @puppeteer/browsers install chrome@stable --path ~/Library/Caches/KeeForge-E2E`) or `~/.cache/puppeteer`; none fails `start` with `browser-missing`. `tools/chrome-cdp.mjs` holds the Chrome, certificate, page-server and menu helpers it shares with `tools/inline-browser-check.mjs`. To exercise every command without the app, point `--host` at an executable wrapper of `tools/mock-host.mjs --control <dir>`.

The inline browser check installs a native-host manifest only inside its temporary Chrome user-data directory. Other tools do not install one. To set one up manually, create an executable wrapper with an absolute path to your Node binary and an absolute path to `tools/mock-host.mjs`, then point the browser's native-host registration at that wrapper. The host JSON is:

```json
{
  "name": "com.keevault.browser",
  "description": "KeeForge development mock",
  "path": "/absolute/path/to/mock-wrapper",
  "type": "stdio",
  "allowed_origins": ["chrome-extension://YOUR_UNPACKED_CHROME_ID/"]
}
```

For Firefox replace `allowed_origins` with `"allowed_extensions": ["browser-extension@keeforge.com"]`. On macOS the per-user registration directories are `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/` and `~/Library/Application Support/Mozilla/NativeMessagingHosts/`; use `com.keevault.browser.json`. Installing either is a manual developer action, not part of the build. The browser handles native framing for extension code; only the standalone mock handles stdio framing.

## UI and fill seams

Extension pages call `chrome.runtime.sendMessage({type, ...fields})`. Popup/pair APIs accept only those exact extension-page URLs; inline/content APIs have their own sender/session checks described below. Responses are plain objects; failures are `{ok:false,error:code}`. `getState` (with `reconnect:true` on popup opening/retry, omitted for pairing polling) and `launchApp` return `{state,reason}`. States: `host-missing`, `app-unavailable`, `unpaired`, `pairing`, `ready`, `error`. `startPairing({name})` sends the detected browser label and returns `{code}` after reveal; poll `getState` for completion or decline/busy/timeout reason. At the connection layer it returns `{code,result}` with a completion promise. `getTarget()` probes the active tab and returns the inspected `{tabId,frameId,documentId,origin,token}`. `getMatches({tabId,frameId,token})`, `fill({tabId,frameId,token,entry,db,totp?})`, `reveal({entry,db})`, `unlock({db?})`, and `forgetPairing` round out the API. `frameId` defaults to 0. Matches are returned to the caller without any background cache. The app enforces that credential requests were offered on this connection.

Background starts without opening a native port. First use opens it; 60 seconds without active work closes it. Pairing and pending requests keep it busy until completion. Each request uses a fresh id; credential timeout is 120 seconds, all others 10 seconds. Timeout closes the session, avoiding acceptance of late replies. `hostCommand('connect')` retries an unavailable relay without launching the app. `launchApp` also fronts an already-running app; it uses a fresh connection without a prior hello before sending the host launch command.

`targetDocument` reads the tab through `tabs.get` and inspects the requested frame using `scripting.executeScript` in the explicitly selected isolated world. Host permissions allow HTTPS and loopback frames, including cross-origin frames; `activeTab` remains available for the toolbar path. Inaccessible frames still fail closed. No page-supplied or UI-supplied origin is used. Non-HTTP(S), non-loopback HTTP, and opaque documents are rejected. The target is checked again after authentication. Chrome provides `documentId`; Firefox did not add it until 153, so Firefox 130–152 needs frame-id targeting plus the in-frame token and origin checks in the adapter. See [Mozilla injection compatibility](https://github.com/mdn/browser-compat-data/blob/main/webextensions/api/scripting.json). UI fields never select a credential origin.

The entry point supplies the isolated-world `fillDocument` injection adapter. It targets the inspected document (using `documentId` where supported), verifies the expected origin and document token again inside the injected function, and returns only completion. Code-only filling asks the app for the code alone and sends only it into the chosen frame; login filling sends only user name and password. It neither retains the credential nor returns it to the popup. The core clears the reply object's fields even if the adapter throws, and `fill` returns only `{ok:true}`. Without an adapter, filling fails before requesting a credential. JavaScript strings and browser/GC internal copies cannot be securely zeroed; clearing references is the retention boundary.

`KeyStore` accepts storage with asynchronous `read()`, `write(record)`, `clear()`; production uses one atomic IndexedDB record and tests use structured-cloning memory storage. Both stored CryptoKeys are non-extractable. WebCrypto initially generates an exportable public half, so it is reimported non-extractable and its public bytes are stored alongside it for protocol messages. Forgetting clears the record and closes the session.

`test/vectors.test.js` reads the Swift-owned `test/vectors.json` directly. Missing or unrecognised vectors fail. It checks identity, commitment, pairing code, both derived keys, and the recorded plaintext/envelope pairs in both directions. Do not edit the fixture from JavaScript work.


## Popup and filling

Click the key button in a login, first-step user-name or verification-code field, or press Alt+Down (Option+Down on Mac) in that field, to open the inline menu. The toolbar action remains available, as does Ctrl+Shift+L (Command+Shift+L on Mac). The shortcut only opens the popup. Browser or OS shortcut conflicts may require assigning it in the browser’s extension shortcut settings.

The background probes all accessible frames, choosing the focused frame when it contains a visible editable input. The popup can take focus from the page, so without a focused frame it chooses the frame the user last clicked or typed in (trusted events the content script timestamps), provided a visible editable input is still that frame's active element; otherwise the top frame. For the toolbar path, a child frame the user has not touched is never selected. Host permissions allow matching cross-origin frames; inaccessible frames fail closed. The probe supplies no origin. The background derives it independently, pins the selected target during the popup session, and rechecks document and origin after a credential reply. The popup displays the serialized origin, including any port, and marks subframes. Only the chosen frame receives a credential, after final in-frame origin and document-token checks. Matching and filling require the current popup selection token; after worker restart or idle expiry, the popup selects again before showing rows. A lost-pin fill never retries the credential action automatically.

Every selection stores a fresh 256-bit random token on the document’s isolated-world global. It is passed only between extension contexts and isolated-world injections, never through DOM attributes, page messaging or native requests. Probing, inspection and filling explicitly use `world: 'ISOLATED'`; this relies on the browser isolating that global from page JavaScript and retaining it for the document’s lifetime. Selection, matching, post-authentication inspection and the fill itself check the token. Browsers with `documentId` additionally check and target it; older Firefox targets one `frameId` and uses the same token checks to reject same-origin document replacement. JavaScript strings and browser-internal message copies cannot be securely zeroed.

Probe and fill use the same self-contained function for visibility and open shadow roots. They reject clipped/masked fields and ancestors conservatively, including partial clip paths or masks, zero-size ancestors, hidden overflow with no visible intersection, hidden visibility/content, inert trees and closed details. This can refuse a field that is partly visible or uses `display: contents`; the extension does not guess at complex painted geometry. Passwords require `type=password` both at selection and immediately before writing; user names accept text/email/tel, and codes accept text/tel/number inputs. Each write rechecks type, visibility, connection, owner document, token and origin. A failed recheck stops further writes and reports not filled; an earlier username write cannot be undone safely. Open shadow roots are traversed recursively and focus follows their active elements. Closed shadow roots are inaccessible and unsupported.

Exact matches precede a separate possible-match section. Multiple databases get separate headings within each section. Enter fills the first login, Up/Down selects a login, and Tab reaches code and reveal actions. A code action fills only a verification code. Retryable popup errors offer a localized Try Again button, and reopening after disconnect or timeout tries a fresh connection. Pairing polling does not reconnect over a terminal result. Waiting for a credential shows “Confirm in KeeForge”; the popup requests no close until filling succeeds. Browser-enforced popup dismissal when focus moves to another app remains outside extension control.

Pairing opens a separate tab, shows the browser label sent to KeeForge, and displays the comparison code until the app accepts or declines, with a line telling the user to switch to KeeForge if it does not come forward. Browser naming uses available brands, user agent and optional Brave detection; browsers hiding their identity (notably Arc and Vivaldi) may appear as Chrome. No extra permission is requested.

All nine locales ship under `_locales/`; zh-Hans maps to zh_CN and zh-Hant to zh_TW. Pages use external scripts/styles only and system fonts. `theme.css` owns the shared light/dark tokens and `kf-row`, `kf-login`, `kf-label`, `kf-title`, `kf-username`, `kf-avatar`, `kf-code`, `kf-section`, `kf-primary`, `kf-secondary`, `kf-state` and `kf-waiting` classes. Popup-specific layout stays in `popup.css`, the inline menu's in `inline.css`, pairing layout in `pair.css`; `src/rows.js` renders login rows and group headings for both popup and menu.

`images/icon.svg` (48/128, popup header, pairing page) and the pixel-grid `images/icon-16.svg` (16/32) simplify the app’s gold key on its navy rounded tile. After changing either, run `env -u NODE_USE_SYSTEM_CA node tools/render-icons.mjs`; it renders the committed transparent PNGs deterministically in headless Chrome through CDP, without dependencies. `images/key.svg` is a single-path monochrome key; it and the other glyphs in `images/` (code, reveal, lock, alert, check, page, link, power) are CSS masks with `background: currentColor` (`kf-icon glyph-*`), so they follow light/dark tokens. An `<img>` does not inherit `currentColor`; consumers such as the in-field menu should use the mask rather than assuming it does.

`env -u NODE_USE_SYSTEM_CA node tools/screenshot-ui.mjs [output-directory]` loads the unpacked extension through `Extensions.loadUnpacked` in headless Chrome, then captures the actual popup and pairing pages with runtime replies stubbed before their modules run. It covers all popup and pairing states in light/dark, German/Japanese/Russian matches and long states, the other locales’ matches/setup copy, forced row hover and real keyboard selection, 50-row scrolling with a fixed header, and the icons on light/dark toolbars at 1x/2x. The default destination is `build/screenshots/`. Every page capture is also asserted: nothing extends past the viewport or scrolls horizontally, no element clips its text unless it ellipsizes on purpose or scrolls, and visible non-decorative text has at least 4.5:1 contrast with its painted background (`tools/layout-probe.mjs`); any failure exits nonzero. These assertions, not pixel comparison, are the visual regression gate, because reference images break with every Chrome or font update while the layout rules do not; `screenshots.json` records the intended checks. Review every generated image before claiming visual validation. Both tools use a disposable profile under the OS temporary directory, block external host resolution, stop their Chrome process and remove the profile. `CHROME` selects another Chromium executable. No native-host registration is installed.

## Owner browser walkthrough

Run this checklist in both real Chrome and Firefox with a disposable `tools/mock-host.mjs` host. Node results do not establish real-browser behavior.

- [ ] Re-register/restart with `--decline`, `--busy`, and `--pending`: verify declined, busy, and 120-second timeout reasons. A fresh mock process forgets clients; use the pairing tab directly or clear the extension’s development IndexedDB before each new mock process.
- [ ] On an HTTPS disposable form, open the menu from the key button (and with Option+Down) in user-name, first-step, password and code fields: rows, code-only and user-name-only fills, refresh after pairing, unlock and launch, close-on-fill and focus return. In Firefox, check the two-click Fill confirm. With the real app, verify Touch ID through the menu, a page entering the back/forward cache and a background restart while Touch ID waits, the menu inside a modal dialog, and right-to-left pages.
- [ ] On an HTTPS disposable form, open the popup, click a login, then test Enter, Up/Down, Tab, code-only filling and Show in KeeForge. Unlock and reveal only acknowledge; with `--control`, `state.json` switches the scenario. verify actual window selection with the real app later.
- [ ] With `--hold-credential`, verify “Confirm in KeeForge” remains while the request waits and eventually times out. With the real app, verify Touch ID success/cancellation and popup behavior when the OS moves focus.

- [ ] Browser pages, file URLs, ordinary HTTP, and pages without editable fields show a one-line reason. Loopback HTTP remains allowed by the protocol.
- [ ] Assign/test the shortcut in each browser. It opens a visible popup and never fills on its own.

## Real-browser checks

`tools/ci.sh` runs every check in order, exactly as the `browser-extension` job in `.github/workflows/tests.yml` does: the Node tests (failing if any test is skipped or none ran), `sync-content.mjs --check`, `build.sh` twice with identical archive hashes, `check-build.mjs`, `render-icons.mjs --check`, then `browser-check.mjs`, `inline-browser-check.mjs`, `screenshot-ui.mjs` against `build/chrome` and `firefox-check.mjs` against `build/firefox`. It prints PASS/FAIL and the time per stage, bounds each stage with a timeout, exits nonzero on any failure, and writes logs and screenshots to `$CI_OUT` (default `build/ci/`). `tools/ci.sh inline-chrome firefox` runs only the named stages (run `build` first). It takes about two and a half minutes on a recent Mac and needs Node, Google Chrome and Firefox.

Every tool finds its browser through `findBrowser`/`findFirefox` in `tools/chrome-cdp.mjs`: the same search as the end-to-end driver above (Chromium apps in `/Applications` and `~/Applications`, then Chrome for Testing caches), then `google-chrome-stable`, `google-chrome`, `chromium`, `chromium-browser` or `firefox` on `PATH` for Linux. The development checks take an explicit `CHROME` or `FIREFOX`, used as given and never falling back; the end-to-end driver takes `--browser` or `KEEFORGE_E2E_BROWSER` (set by the Mac UI test) under the same rule. `EXTENSION_DIR` points them at another extension directory, as `ci.sh` does with the built output; by default they use this source tree (Firefox: `build/firefox`).

`tools/check-build.mjs` checks the last build: each zip equals its unpacked copy byte for byte, holds exactly the shipped files (no `test/`, `tools/`, docs or package files) with the same bytes as the source, carries the source manifest without the development `key`, stamped with `project.yml`'s `MARKETING_VERSION` (Firefox also without `use_dynamic_url` and `world`), and contains every file the manifest, pages and stylesheets reference. `tools/render-icons.mjs --check` renders the PNGs without writing them and fails when more than 0.1% of a PNG's pixels differ by more than 8 levels from the committed file; if a Chrome update ever re-rasterizes edges beyond that, re-render and commit.

`env -u NODE_USE_SYSTEM_CA node tools/browser-check.mjs` runs the fill and probe code from `src/fill.js` against the pages in `test/pages/` in headless Chrome (temporary profile, localhost only) and exits non-zero on any mismatch. It needs Google Chrome installed and is not part of `node --test`.


`SHOTS=/path/to/main-checkout/scratch/<dir> env -u NODE_USE_SYSTEM_CA node tools/inline-browser-check.mjs` loads this directory's shipped manifest (no test-only permissions) with `Extensions.loadUnpacked` over `--remote-debugging-pipe --enable-unsafe-extension-debugging` (`--load-extension` is ignored by current Chrome). It registers `tools/mock-host.mjs --control` in a temporary profile's `NativeMessagingHosts` folder, serves `test/pages` on loopback HTTP and on HTTPS with a throwaway self-signed certificate (`openssl`, `--ignore-certificate-errors` for that profile only), drives everything with trusted CDP mouse and keyboard input, and checks: buttons only in real user-name/password/code fields, first-step e-mail and readonly-until-focus password fields (not search or newsletter fields), on a 20,000-element page, inside a modal dialog, popover and fullscreen element, but not in small or sandboxed frames; their geometry (scroll, resize, later insertion, hiding, a site's show-password control) and their own colour on a transparent-text field; untrusted clicks ignored; no background or native traffic before the first click; not-paired, locked, no-logins, not-running and confirm states with automatic refresh after pairing, unlock and launch; login, code-only and user-name-only fills, close-on-fill and focus return; Alt+Down; occluded and transparent menus refusing clicks and Enter; moving the form or page under an open menu closing it before a click 80 ms later; a second frame load closing it; a page listening to every message receiving nothing; a fixed frame size whatever the rows; a page stopping every capture listener still closing the menu on outside click and Escape; the popup closing an open menu; the menu's subresources loading with only inline.html web accessible; a cross-origin frame matched with its own origin; that a web page cannot frame or fetch popup.html, pair.html or inline.html; and main-world isolation (`window.frames` is empty). It saves light and dark screenshots at 2x to `$SHOTS`, then kills Chrome and the mock hosts and deletes the profile. Chrome still starts its own updater helper. It also opens the real toolbar popup with `chrome.action.openPopup()` in the logins, locked, no-logins, not-running and host-missing states and requires a 340 px viewport with nothing overflowing or clipped (a 340 px tab cannot show the popup collapsing, which happens when its CSS uses viewport-relative widths), and runs the `tools/layout-probe.mjs` overflow, clipping and contrast assertions on each menu state in light and dark. A click within 300 ms of the menu becoming visible or re-rendering is refused by design, so menu actions first wait 700 ms; a second click is allowed at most twice per run and printed as a note, so a menu that refuses settled clicks fails instead of passing on retries.

`env -u NODE_USE_SYSTEM_CA node tools/firefox-check.mjs` (after `tools/build.sh`) installs `build/firefox` temporarily over WebDriver BiDi (`webExtension.install`, `MOZ_REMOTE_ALLOW_SYSTEM_ACCESS=1`, disposable profile) and checks that the button is drawn, a trusted click embeds the styled menu (host-missing state) and keeps it open, the page receives no message and sees no extension URL, `window.frames` hides the menu, and even a page that knows the UUID cannot load any other packaged file. Firefox reads native-host manifests only from the real per-user folder, so pairing and filling (including the two-step confirm) were not exercised there.

## Inline permissions and security

The owner-approved in-field flow uses host permissions and persistent isolated content scripts, registered at document_start, on all HTTPS sites and HTTP localhost/127.0.0.1/[::1], in every matching frame. This grants ongoing access to those pages; it is broader than activeTab. activeTab is kept so the toolbar path still works where the user restricts site access to "on click" or, in Firefox, has not granted host access. No ordinary remote HTTP, file or browser-internal URLs are allowed. No extension code makes network requests. The app wire protocol is unchanged.

Before a trusted button click, discovery does not contact the background or native app. It reads field types/hints/layout only. Every site gets the same key glyph, regardless of pairing, database state or matching entries. The script registers its capture listeners (pointerdown, keydown, focus, navigation) at document_start, before any page script, so a page's own capture listeners cannot stop them; everything else waits for the DOM, and a document creates no host, observer or timer until it has an input (a child-list observer that reads the live input count and, at most twice a second after a change, looks for inputs in open shadow roots, observing up to 100 of them; plus focus on an input in an open shadow root). Sandboxed opaque-origin frames get nothing; frames smaller than the menu (256×196 CSS px) get no buttons and are left to the toolbar popup. One host holds a closed shadow root; inputs are never wrapped/restyled or given new attributes. The host is zero-sized and fixed at the viewport origin; its children are fixed-positioned. (A viewport-sized overlay, even transparent and pointer-events:none, counts as occluding every child frame for IntersectionObserver visibility tracking, which made menus in frames unusable.) It is a child of documentElement, or of the open modal dialog, fullscreen element or open popover holding the fields: a modal dialog makes everything outside it inert (a popover shown above it stays unclickable), so with a modal or fullscreen element open only fields inside it are decorated. At most 20 buttons are drawn, 16 to 20 px depending on field height, with the glyph in theme.css's muted colour chosen by the field's effective background luminance, never the page's text colour. Discovery examines at most 400 inputs (found with `querySelectorAll('input')` in the document and each open shadow root, however many other elements there are) at most twice a second. Besides password, user-name and one-time-code fields it decorates a lone e-mail or user-name-like field (type email, or id/name/autocomplete with user/login/email/account/identifier) in a form with no password and no other text field, except where the field, its form or a `role=search` ancestor mentions search/query/newsletter/subscribe/coupon/promo; a newsletter box without such hints is decorated (cheap heuristics cannot tell). Such a field fills only the user name: the app still releases the full login to the extension (the wire protocol has no user-name-only request), but only the user name enters the page. Readonly-until-focus password fields are decorated; the write focuses them first and refuses if they stay readonly. Geometry follows events: mutations (child lists, and an attribute filter of layout-relevant attributes) and scroll, resize, focus, toggle, fullscreen and colour-scheme changes start a 30-frame burst; attribute churn and transitions/animations unrelated to a decorated field get at most four single updates a second, so continuously animating pages cause no frame loop. There is no poll; fields in shadow roots attached later appear on the next mutation or when focused. To avoid a site's own trailing control (show-password eye, clear button), the script hit-tests the field's trailing edge with `elementsFromPoint` in the field's root and moves left of any small element drawn over it (up to three); the key hides if it would not fit. Controls with pointer-events:none are not detected. Closed roots remain unsupported. After an extension update or removal the orphaned copy removes its UI.

The content script keeps an actual reference to the clicked field in its isolated global. `openInlineMenu` derives tab/frame/document/origin from MessageSender and independent isolated inspection, creates a fresh document pin and unpredictable menu token, and replaces the tab's prior session. `inlineMenu({token,action,...ids})` is accepted only from this extension's exact inline.html in the same tab, for the current session; the first menu document to call owns the session and a call from any other document closes it. Actions are state, launchApp, pair, unlock, reveal, fill and close. State fetches matches only for that pinned origin; code fields filter hasTotp and always request code-only credentials. The existing credential path rechecks origin, document id and pin after device-owner authentication and inside the native-setter injection. Successful fill revokes the menu, closes only the recorded frame through `tabs.sendMessage` (frame and document id) and returns focus to the field; Escape does the same. Dismissal/navigation also revoke it. Opening the toolbar popup closes the tab's inline menu before its selection replaces the document pin. Worker restart loses all sessions and requires reopening the menu.

Matching rows render only inside the cross-origin extension iframe. No titles, usernames, match existence or counts go to the content script/page, and the menu frame posts nothing to the page: no size (the frame is a fixed 320×264 CSS px card, smaller only when the viewport is), no close (closing goes menu → background → `tabs.sendMessage` to the recorded content frame), so a page learns neither the extension origin (on Firefox a per-install UUID) nor a window handle to the menu. Chrome and Firefox both leave the menu frame out of `window.frames`. What a page can still observe: that the host element exists and where the buttons and the menu card are (by hit-testing; the card's box depends only on the field position and viewport), when the menu opens and closes (including focus leaving the page and the field being refocused), and the filled values afterwards. The page can detect or remove the injected host, but cannot access its closed root, iframe URL/token or extension DOM through normal page APIs. The browser's own debugging tools are privileged and can inspect it. As with any password manager, the destination page can read values after filling.

Inline actions (rows, code, reveal, unlock, open, pair, Try Again, and Enter, which activates the focused button) require trusted events, a visible document, the menu fully visible (within one pixel, because sub-pixel frame offsets clip a fraction) without a break for 300 ms, 300 ms since opening and 300 ms since the rows last changed. Where available, IntersectionObserver uses trackVisibility with delay 100 and visibility requires isVisible; in real Chrome a pointer-events:none overlay, opacity 0 on the host and opacity 0.1 on the page all stopped trusted clicks and Enter from filling. Firefox lacks visibility-v2, so it cannot see an opaque overlay or transparent embedding: there the first click on a row only arms it and the fill needs a second click on a Fill button at a random horizontal offset within the row, after the same 300 ms, so a blind decoy cannot predict where the second click must land (Chrome keeps one click). Keyboard users on Firefox press Enter twice; a page cannot send keys into the menu. Because a page could slide a row under the cursor, the content script checks the field's and the frame's boxes on every frame while a menu is open (and on every mutation) and closes the menu if either moves by more than a pixel (scrolling included), the viewport or URL changes, its host's style is altered, the field stops being visible, or the frame loads a second document (navigated or replaced). A move made by a page script and a click in the same animation frame remain a theoretical gap: a mouse-down inside the menu frame is not delivered to the page, so the page has to guess. The app's origin matching and device-owner gate remain mandatory. A top-level inline page is inert. While open and visible, polling once a second and on focus brings newly unlocked/paired/started app state into the menu without another icon click. Credential requests show Confirm in KeeForge and are never retried automatically.

The manifest CSP applies to all extension pages, so an inline meta policy cannot relax its frame-ancestors directive. Measured in Chrome 158: with `frame-ancestors 'none'` the content script's iframe of inline.html is refused ("refused to connect"), so the manifest allows HTTPS and loopback HTTP ancestors. That relaxation covers every extension page, but popup.html and pair.html are not web accessible: a web page's iframe of either, or of inline.html at its static URL, becomes `chrome-extension://invalid/` ("This page has been blocked by Chrome") and `fetch` of all three fails. The content script's iframe uses `runtime.getURL` (the static ID) and still loads; the page itself never learns a usable URL because of `use_dynamic_url`. Only inline.html is listed: the menu's own stylesheets, script and images are loaded by the extension document and need no listing in Chrome or Firefox (both checks verify the styled menu). The menu also loads on a page whose own CSP is `default-src 'none'; frame-src 'none'; style-src 'none'` with Trusted Types required. In Firefox 160 a web page's iframe of popup.html or pair.html stays `about:blank` and fetching them fails, but inline.html is framable and fetchable by anyone who knows the per-install `moz-extension` UUID (Firefox has no dynamic URL); such a copy has no session token and the background refuses it. The menu no longer posts to the page, so pages do not learn the UUID from it, and no other packaged file is web accessible. No meta relaxation or extra webRequest/declarativeNetRequest permission is used.
